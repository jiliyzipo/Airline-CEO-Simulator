# CEO 视角重构 · 设计定稿 v1.0

> 状态：**已定稿（P20 愿景与主页补齐 已落地）**
> 日期：2026-09-09
> 定位：把游戏从「操作型部门模拟」重构为「决策型 CEO 模拟」，对齐 Football Manager 的成熟交互范式。

---

## 1. 背景与核心问题

当前游戏的核心问题：玩家同时扮演了 CEO、运营经理、定价员、排班员、机务总监——定价（n49）、排班（n42/n43）、航班环构建（n36）等均需 CEO 亲自上手，偏离「CEO 带领团队」的定位。

重构目标：把玩家拉回到 CEO 的决策位置，让部门负责人承担执行职能，前端只呈现信息与待决策事项。

---

## 2. CEO 四动作模型

玩家的全部信息流收敛为四个动作，其中「收件箱」是主循环。

| 动作 | 载体 | 说明 |
|---|---|---|
| **接收** | 收件箱 | 部门负责人提交的数据/报告；管理机构检查要求；公众媒体反馈；突发事件警报 |
| **查看** | 邮件正文 | 点击邮件中的关键词 → 跳转详情页（FM 同款） |
| **决策** | 邮件内按钮 | 邮件附按钮，CEO 选择符合决策的指令发出（批准/暂缓/拒绝/追加条件） |
| **交流** | 顾问 | 点击「顾问」输入需求，AI 分析并反馈，随后调出对应页面 |

### 2.1 邮件类型（固定化）

1. **部门汇报**：携带决策建议（如「建议 SZX-LAX 定价 ¥1450，竞对已降至 ¥1380」），而非纯数据表。
2. **监管要求**：局方检查、适航、航权等。
3. **公众媒体**：舆情、品牌、公关。
4. **突发事件警报**：IRROPS、安全事件、油价冲击等，最高紧急权重。

### 2.2 关键词跳转规范

- **单一数据源**：邮件数字与详情页数字必须来自同一份 `GameState`/子系统数据，禁止复制。
- **上下文锚点**：关键词跳转带参数（如 `n41 + routeId=SZX-LAX`），直达目标详情，而非总览页。
- **白名单化**：只有存在对应详情页的词才可点（人名→人员档案，航线→航线详情，城市→经济指数，飞机→飞机详情）。
- **全局映射表**：`术语 → pageId` 映射表，邮件与顾问 AI 共享同一份。
- **面包屑返回**：复用 `NavigationRouter` stack，从邮件跳入也压栈、可返回。
- **详见按钮区**：邮件底部提供显式按钮（与正文关键词并列），兼顾效率与沉浸。

## 3. 部门后端化原则

几大部门职能隐藏在**后端自动运行**，前端只呈现运行信息。部门负责人自动执行职能，结果通过邮件汇报 CEO，等待决策。

### 3.1 两条硬约束

- **汇报必须携带决策建议**：否则玩家感觉在看自动播放的看板。
- **子页「降级」而非「删除」**：现有 100+ 部门子页从「导航常驻项」降级为「邮件点进去的详情视图」，功能保留、入口改变。

## 6. 核心数据模型设计

### 6.1 统一人事档案 `PersonnelData`

将现有 `ExecutiveData` 泛化为统一结构，**避免负责人与员工两套数据**：

```
PersonnelData
  ├─ id / fullName / age / nationality / traits[]
  ├─ baseSalary / loyalty / efficiencyBonus
  ├─ rank        ← 实习生/专员/主管/负责人/总监
  ├─ potential   ← 成长潜力（决定晋升速度）
  └─ department  ← 归属部门
```

- 负责人 = `rank` 高的角色；员工 = `rank` 低的同构对象。
- 现有 70 名负责人 = `rank=负责人` 初始池。

### 6.2 关键岗位实例化 + 群众抽象化（已确认）

- **关键岗位**（副手、组长、高潜人才、未来负责人候选）→ 独立角色对象，完整档案，可点击、可培养。
- **普通员工**（如客舱 100 人）→ 聚合统计：`编制 100 / 实有 87 / 平均满意度 72% / 缺编影响效率`。
- 候选人池只实例化「关键岗候选人」，群众求职者用「池 + 统计」表示。

### 6.3 员工角色生成器

- 系统自动生成角色，属性参照负责人资料设计。
- 各部门编制参照现实航司编制。
- 职业介绍所 = 负责人候选 + 员工候选统一入口。
- 开局自动分配各负责人/员工，玩家可解雇个人、从职业介绍所雇佣。

### 6.4 城市经济指数（已确认：离线）

- 本地静态表（JSON/ScriptableObject 打进 Resources）初始化 GDP/人口/客货吞吐/OD 客流。
- 之后由游戏内模型动态演化（开航线、宏观周期改变供需），不联网。
- 作为 `n35 RPM 评估台` 与开线决策的输入，而非独立展示。
- 保留玩家手动更新离线表的入口；初始覆盖范围：枢纽 + 已开航城市。

### 6.5 机队三来源

| 来源 | 现金流结构 | 退出方式 |
|---|---|---|
| 新机购买 | 一次性大额现金 + 资产折旧 | **退役**：转售/拆解，回收残值 = 购价 × max(10%, 100−机龄×3)% |
| 融资租赁 | 低首付（10%）+ 每月租金（1.2%）+ 期满买断价（接 LoanManager 按月现金流） | **退租**：产权在出租人，不回收残值；提前解约属违约，违约金 = 剩余租期租金 × 30%（名义租期 10 年，随已付期数递减至 0） |
| 经营租赁 | 纯每月租金（2.2%）、无资产、灵活退租（期短、单价高） | **退租**：交还出租人，零成本灵活退（设计稿「灵活退租」的发点就在这） |

二手市场：季度动态货架，机龄 5–15 年、寿命剩余、折扣 30–60%，随机性与劣质陷阱（老机龄 → 高维修成本）。
二手引进同样是**买断**（付全款）→ 退出走「退役」。

> 术语分叉的根因（2026-10-13 修订）：租赁机的所有权在出租人手里，公司无权「退役」别人的资产，
> 只能「退租」。旧口径把租赁机按自有飞机退役并照发残值 —— 经营租赁零首付，租进来当天退役即可
> 白得整机目录价，是凭空造钱的口子；本轮同时收口（`FleetManager.TryRetireAircraft` 按 `source` 分路）。

### 6.6 CEO 合同（已确认：计入现金流 + 解雇失败）

- 合同期限 + 董事会满意度 → 续约/解雇。
- **CEO 被解雇 = 游戏失败**（接 BoardManager + n26 财年结算）。
- CEO 周薪**计入公司现金流**（已确认），但数值须设为象征性小量级（年薪 ¥30–80 万），避免高薪死循环。
