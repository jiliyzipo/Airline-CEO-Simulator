## 1. 触发问题

CEO 在 `人员 → 人力职能 → 招聘策略弹窗`（`n99`）里看到四个渠道方案（`ⓐ 批量校招 / ⓑ 猎头挖角 / ⓒ 海外引进 / ⓓ 内部转岗`），每个都标注了人均成本、招聘周期、成功率。但批复招聘后，**这些人从不以具体人物的形式出现在任何界面上**；而 `人员 → 职业介绍所`（`n112`）却有一张完整的候选人表（部门 / 空缺职位 / 姓名 / 国籍 / 期望年薪 / 聘请）。

需求因此提出：能否把四个渠道的人物并入职业介绍所的候选人列表。

## 2. 现状诊断

### 2.1 渠道线：只有一个计数器，没有人物

### 2.3 内部转岗：只有一个枚举值

## 3. 结论：这不是「合并」，是「渠道实体化」

严格来说，本需求当前**无法直接执行**——四个渠道没有产出任何 `PersonnelData`，没有"人"可以并进列表。

因此建议把需求重新表述为三步：

1. **实体化**：让渠道真正产出带 `source` 标签的候选人对象（写回 `staffPool`）。
2. **合并**：把这些候选人按来源分组呈现在 `n112`。
3. **分流**：同一张表内按「是否总监」区分 CEO 直聘 / 转呈人力两种行内动作。

其中第 1 步是**唯一的实质性工作**，第 2 步是 UI，第 3 步是授权边界的重新划定。

| # | 冲突 | 说明 | 解决方向 |

## 5. 推荐方案

### 5.1 数据模型变更（**已落地**）

`PersonnelData` 新增三个字段 + 一个时间折算方法：

```csharp
/// <summary>来源渠道：market / campus / headhunt / overseas / internal。
/// 旧档读出可能为 null/空，一律按 market 处理，见 HrEconomics.NormalizeSource。</summary>
public string source = "market";
/// <summary>内部转岗交接期截止（UTC ticks）。</summary>
public long handoverUntilTicks;
/// <summary>运行/职能序列的批量招聘人员，不占编制、不参与关键岗效率统计。</summary>
public bool isOperational;

public const int HandoverDays = 14;
public const float HandoverEfficiencyScale = 0.7f;
public float EfficiencyAt(long nowTicks)
    => handoverUntilTicks > nowTicks ? efficiencyBonus * HandoverEfficiencyScale : efficiencyBonus;
```

`Vacancy` 新增三个字段：

```csharp
public long startUtcTicks;   // 本期招募发起时刻
public long dueUtcTicks;     // 本期候选人到位时刻（旧档为 0 → 视作立即到位）
public int inPool;           // 已落池、尚待 CEO 决定的候选人数
```

- **不新增** `internalEligible` 之类的持久标志位：内部转岗的可选性完全由 `rank != "负责人" && !onMarket && !IsOccupied(p.id) && 存在同职级缺口` 实时推导，避免旧档状态漂移。
- **旧档零迁移**：所有 `source` 消费点统一走 `HrEconomics.NormalizeSource()`，`null`/空 → `market`。
- `PersonnelData` 与 `Vacancy` 均为直接序列化，加字段向后兼容：旧档读出 `null`/`0` 分别视为 `"market"` / "立即到位"。
- `SeedCatalogHeads` 已有 `Find(gs, e.id)` 去重，不会把合并进来的人误当目录负责人重复灌入。

### 5.2 落池时机（**已落地：日级 Tick**）

候选人**不会**在发起招聘的瞬间出现在列表里，否则 `n99` 的成功率/周期立刻失去意义（等于立等可取）。`RecruitLeadWeeks` 现在是候选人落池的到期日：

```
批准招聘（LaunchRecruitment）
  → Vacancy.dueUtcTicks = now + RecruitLeadWeeks(channel) × 7 天
  → HrManager.TickDay（日级推进）到期时：
       PersonnelGenerator.CreateForRole() × (剩余需求 − 池中人数)，写 source = 渠道标签，落池
       dueUtcTicks += 一个渠道周期（持续输送，但池量永不超过剩余需求）
  → RecruitNow / HireCandidate 对池内候选人逐一掷成功率
       成功 → 入编并计入人数
       失败 → ReleaseCandidate 移出人事池
```

推进方式选定 **选项 B**：接入日级推进（`TimeManager` 中与 `StaffRecruitment.Tick` 并列），复用同一套时间语义。

### 5.3 UI 规格（`n112`，**已落地**）

1. **来源筛选胶囊**（顶部）：`待聘总监 / 校招 / 猎头挖角 / 海外引进 / 内部转岗`，复用 `HrEconomics.SourceName` 不另造术语。
2. **表增第 6 列「来源」**：颜色编码周期差——猎头（4 周）偏红=快而贵、校招（24 周）偏灰=慢而廉、海外（12 周）黄、内部转岗绿。
3. **行内按钮双语义**：
   - `CanCeoHire(p)` → `聘请`（沿用 `mgr.HireFromMarket(id)`）
   - 渠道候选人 → `录用` / `退回`（`HrManager.HireCandidate` / `RejectCandidate`）
   - 内部转岗 → `调岗`（`HrManager.TransferStaff`）
4. **分页**：10 行/页 + `◀ 上一页 / 下一页 ▶` + 直达「去人事履行 →」。
5. **内部转岗行**：部门列为**目标部门**，职位列显示目标岗位 +（调入），薪资列显示**调岗增量**（`+N.N 万`）而非完整年薪——否则与外部候选人在视觉上不可比。

### 5.4 非总监候选人如何呈现（**已按条件折叠落地**）

最终实现为 **5 个来源筛选胶囊**（而不是文档草案里的 6 个，因为「全部」在条件折叠下就等于「待聘总监」，两个页签会造成歧义）：

```
待聘总监 | 校招 | 猎头挖角 | 海外引进 | 内部转岗
```

| 页签 | 数据来源 | 行内动作 |
|---|---|---|
| 待聘总监（默认） | `onMarket && rank=="负责人" && !IsOccupied && source=="market"` | `聘请` → `mgr.HireFromMarket`（与改动前**行为完全一致**） |
| 校招 / 猎头挖角 / 海外引进 | `onMarket && source == 该渠道标签` | `录用`（CEO 确认人选，人力办入职）/ `退回`（移出人事池） |
| 内部转岗 | 规则实时推导：`!onMarket && rank!="负责人" && !IsOccupied && 存在同职级空缺` | `调岗`（直接授权，因属内部人事决定） |

**关键约束**：非总监行**不提供管理岗直聘**。渠道候选人的「录用」只是确认这个人选、由人力办理入职，**不能**借此被任命为管理岗——`StaffRecruitment.CanCeoHire` 的授权边界因此保持成立。

**为什么默认只列总监**：`n112` 原表 11 行就见底（底注还挂着"仅显示前若干名"的欠账）。无差别平铺会把列表变成几十上百行的招聘网站，让 `StaffRecruitment` 好不容易建立的"CEO 只批总监"边界名存实亡。条件折叠既保护 CEO 注意力，又让渠道真正可被检视比较。

## 6. 平衡性设计

### 6.1 来源属性分布（决定合并有无玩法价值）——**已落地**

如果并进来的人属性完全随机，"按来源筛选"就只是个显示位置移动，零玩法收益。因此 `PersonnelGenerator.ApplySourceProfile` 给不同来源分配了不同分布：

| 来源 | 潜力 | 年薪 | 忠诚 | 效率(即战力) | 体感定位 | 落地 |
|---|---|---|---|---|---|---|
| 校招 | ×0.85 | ×0.75 | ×1.10 | ×0.80 | 便宜、慢、要养 | ✅ |
| 猎头挖角 | ×1.15 | ×1.45 | ×0.90 | ×1.10 | 快、贵、易被再挖 | ✅ |
| 海外引进 | ×1.05 | ×1.30 | ×0.95 | ×1.10 | 稀缺岗位来源，有适应期 | ✅ |
| 内部转岗 | 维持基准 | 调岗 +20% | 维持基准 | 维持基准 | 零外部费用，代价在编制与交接期 | ✅ |
| 待聘总监（market） | 维持基准 | 现状 | 现状 | 现状 | 现行为基准 | ✅ |

### 6.2 内部转岗的抑制（**已落地**）

`内部转岗` 原值 **2 周 / 85% 成功率 / $500 人均**——一旦实体化会立刻变成**最强的无脑通道**。现行抑制手段：

- **外部费用归零**：`RecruitCostPerHire(3) = 0`（无外部方收费）。但代价转移为：

### 10.3 机组战力乘数（已接通，含漏洞修复）

`GameState.CrewQualityMultiplier` → `LiveClockSimulator.Land` 的航线落地利润，与 `monthlyRevenue` 同口径缩放（否则季结按 `monthlyRevenue×3` 轧差时会把缩掉的部分补回来）。按 `SimUtc.Date.Ticks` 做日缓存，人员变动时 `InvalidateCrewCache()` 当天生效。

**修复的反向激励漏洞**：`CrewQualityMultiplier(filled<=0)` 曾返回 `1f`（「未建机组 = 完全中性，既有数值基线一字不变」）。但航班调度**从不校验是否有机组**，于是：

| 情形 | 修复前乘数 |
|---|---|
| 0 名机组 | **1.000**（免费满利润） |
| 校招机组（战力 0.384 < 达标线 0.48） | 0.952（**被判折损**） |

即「永不雇机组」**严格支配**「雇校招机组」，所有渠道都是净亏损 —— 渠道系统形同虚设。这个倒挂是 `tools/balance --channels` 的 Part B 跑出来的。

**修复**：新增 `CrewUnstaffedMultiplier = 0.85f`，`filled<=0` 时返回它。不变量（由 `HrSafPlayModeTests.CrewQuality_UnstaffedIsStrictlyWorstThanAnyCrew` 全域扫描锁定）：

```
CrewUnstaffedMultiplier(0.85) < CrewQualityMin(0.88) <= 任何已建机组的乘数
```

这条不等式是**结构性成立**的，不依赖调参运气：`EfficiencyMin = 0.30` → 最烂机组 `delta = -0.18` → 乘数 `0.91`，仍高于 `CrewQualityMin`。于是两级激励都成立：**要不要招**（招任何人 > 不招）、**招哪个渠道**（猎头 1.019 > 内转 1.000 > 校招 0.952）。修复后最差的已建机组仍优于未建机组 **+12.0%**。

配套防线：
- `avgEfficiencyBonus <= 0f` 不再退回中性 —— 否则「有人但战力数据坏掉」= 白拿满利润；`NaN` 显式返回 `CrewQualityMin`。
- `GameState` 里三处硬编码 `return 1f`（含缓存初值 `_crewCacheValue`）全部改为走权威函数的「未建机组」分支，避免两处定义漂移重新开出漏洞。

**刻意不把覆盖率的"惩罚因子"乘在质量上**：若乘数 = 覆盖率因子 × 质量因子，则低覆盖 + 低战力（校招）会出现「招几个人比一个不招更亏」的**陷阱区**（需覆盖 >37% 才回本）。

### 10.3.1 编制覆盖率插值 + 接管局继承机组（2026-10-08 修订）

**发现的第二处口径分叉**：接管局（`TakeoverWorldBuilder.Apply`）只写机队 / 航线 / 贷款 / 遗留议题，**从不生成人员**；`PersonnelGenerator.GenerateAll` 只补管理序列关键岗（全部 `isOperational=false`）。于是 `PilotFilled = 0` → `filled<=0` 的保底分支被触发，**玩家接手的航司那 8 条正在运营的航线被当成「一架机组都没有」**，无条件吃满 ×0.85；而同一家航司的叙事层由 `crewVacancyPercent` 驱动着「机组人员短缺 15%」——该字段此前**只被写、从没被算**（唯一读取点是遗留议题文案与选司页文案）。

实测代价（北辰快线 · 10 架窄体 · 缺员 15%）：季度收入 518.67 万 → 未打折应为 610.20 万，**每季被多扣 91.5 万**，而同期盈利仅 44.58 万/季 —— 折损额是全部利润的 **2 倍多**。

**两处修订**：

1. **覆盖率改为线性插值**（不是惩罚因子）：

```
乘数 = CrewUnstaffedMultiplier + (质量乘数 − CrewUnstaffedMultiplier) × 覆盖率
覆盖率 = CrewCoverage(filled, establishment) = clamp(filled / establishment, 0, 1)
```

   三个性质：① `filled=0` → 恰好 0.85（保底最劣）；② `filled>0` → 严格 >0.85（招任何人都不亏）；③ 对 `filled` **单调不减** → 不存在陷阱区。因此「机组人员短缺 X%」终于有真实代价。`establishment<=0` 时覆盖率视作 1，退化为纯质量口径 —— 与两参重载（tools/balance / 纯公式自测在用）完全一致。

2. **接管局播种继承机组**：`PersonnelGenerator.SeedInheritedCrew(gs, vacancyPercent)` 按 `OperationalEstablishment(岗位, 在役机队, 宽体, 座位) × (1 − 缺员率)` 生成飞行员 / 乘务员 / 机务工程师，`onMarket=false`、`isOperational=true`、`source = SourceInherited`。北辰快线实况：编制 80 飞行员 → 在册 68 → 乘数 **0.9775**（不再是 0.85）。

| 新来源标签 | 语义 | 必须遵守的两条不变量 |
|---|---|---|
| `SourceInherited = "inherited"`（「继承在册」） | 接管局继承的在册机组 | ① **不进** `OperationalPayrollMonthlyWan`（薪酬已含在 240 万/机/年的存量聚合口径内，计入即双计）；② **不计入** `OverseasCrewCount`（不是海外引进渠道，国际航线准入仍须海外引进或考取 `intl_ops`） |

配套：`ApplySourceProfile` 把 `SourceInherited` 与 `market`/`internal` 并列早退，否则会落到 else 分支被贴上「国际经验、适应期」特性标签。旧档迁移在 `SaveManager.MigrateInheritedCrew`，判据保守：**仅当**「接管局 + 在役机队 >0 + `crewVacancyPercent` >0 + 运行序列一个人都没有」才补，只要玩家在旧档里招过任意一名机组就不动。

**UI**：`HrSubpagePanel` 的机组警示拆开两个独立抓手（缺编 / 战力），显示「机组覆盖 85%（68/80）→ 航线利润 ×0.98」，否则玩家不知道该招人还是该培训。

> **从零开局（非接管）保持不变**：`staffPool` 里确实没有任何建模机组，开局航线利润仍按 ×0.85 计 —— 这是 10.3 漏洞修复的刻意取舍，且现在会随招聘按覆盖率**平滑回升**到 ×1.00，不再是一个只能靠「招满 80 人」才跳出的悬崖。

> **剩余口径说明**：`hr.totalHeadcount` 已于 2026-10-08 改为派生值（随机队缩放，见 §14.2），故继承机组的薪酬与人数现在同属「聚合口径」两侧，不再一有一无。

### 10.4 飞行员编制按机队推导（已接通）

### 10.7 渠道收益差（`tools/balance --channels` 实测）

样本：6 名「飞行员」· 人才紧缺指数 60 · 成本系数 ×1.10

| 渠道 | 累计成本(万) | 总耗时(天) | 3年TCO(万) | 万/战力点 | 战力乘数 |
|---|---|---|---|---|---|
| 批量校招 | 1.76 | 336 | 19.86 | **17.24** | 0.952 |
| 内部转岗 | 0.00 | 0 | 28.80 | 20.00 | 1.000 |
| 海外引进 | 15.84 | 420 | 48.14 | 30.39 | 1.019 |
| 猎头挖角 | 13.20 | 84 | 48.97 | 30.92 | **1.019** |

| 批量校招 | 0.748 | 6.00 | 74.8 | 0.384 |
| 猎头挖角 | 0.980（触顶 clamp） | 11.60 | 61.2 | 0.528 |

## 14. 变更：全公司总人数改为派生（2026-10-08）

### 14.1 问题

`hr.totalHeadcount` 是默认 450 的**固定值**，与机队规模脱节。而它的兄弟口径 `LaborCostAnnualWan`（§10.2 已接通）是 `240 万/机/年 × 在役机队`——**成本随机队走、人数却钉死**。后果：

| 消费者 | 失真 |
|---|---|
| `UnionCostWan`（按人头计费） | 20 架机队的「让步」成本按 450 人计 = 360 万，正确应为 1800 人 × 0.8 = **1440 万**，低报 **4 倍**。劳资决策在大航司被系统性低估。 |
| `TrainingRoi`（按人均预算） | 人均 = 预算 / 人数。人数少报 → 人均虚高 → ROI 虚高，大航司的培训投入显得比实际更划算。 |

### 14.2 落地

新增 `HrEconomics.HeadcountPerAircraft = 90f`（锚点与 `DefaultAnnualLaborCostWan` **同源**：5 机 ↔ 450 人 ↔ 1200 万/年，人均 2.67 万美元/年）与：

```csharp
public static int EffectiveHeadcount(int activeAircraftCount, float perAircraftHeads, int additiveHeadcount)
```

与 `EffectiveAnnualLaborCostWan` **完全同构**（`费率 × 规模 + 增量`），故两者随机队同步缩放。

`HrState` 新增三个字段（`headcountPerAircraft` / `headcountAdditive` / `headcountMigrated`），`totalHeadcount` 降级为**旧档迁移来源**——与 `laborCostWan` → `laborCostPerAircraftWan` 的处理完全一致。迁移函数 `HrManager.MigrateHeadcount` 与 `MigrateLaborRate` 逐行同构，含「无机队时保底每机人数 + 旧总数转增量」的分支。

实值出口为 `GameState.TotalHeadcount`（派生属性，与 `LaborCostAnnualWan` 相邻）。三个消费者全部改读派生值，`HrSubpagePanel` 显示改为带构成的文案（`在编 1812 人（机队基准 1800 + 招聘增量 12）`），否则玩家看到数字随买/退飞机跳变会以为出错。

**增量与基数不重叠**：渠道招聘到岗者进 `headcountAdditive`（其薪酬在 `OperationalPayrollMonthlyWan`，聚合之外）；§10.3.1 的继承在册机组**不进**增量（其薪酬在聚合之内，已由每机人数代表）。

### 14.3 平衡影响

- **基准不变**：5 机基准航司 5 × 90 = 450 人，与旧值一字不差；`tools/balance` 基线自检不变（该工具此前硬编码 `headcount = 450`，现改为 `EffectiveHeadcount(fleetCount, 0f, 0)`，5 机场景结果相同）。

- **从零开局**：青禾航空 3 机 = 270 人（旧值 450），工会成本随之下降——此前对小航司是**高报**。

## 17. 变更：来源芯片收进过滤抽屉 + 投机候选池（TalentMarket）（2026-10-11）

### 17.1 触发（两张截图合成的两个疑问）

1. 「目前全部来源的待聘人员都**都来自市场**，我希望来源包含『猎头挖角』『海外引进』『内部转岗』，而上面红框的这三个标签则取消。」
   —— 名单里「来源」一列整列打印「市场」，是**两个缺陷叠在一起**：① 顶栏那排来源芯片占了一整行，玩家不点它就永远停在「全部来源」，而「全部来源」的并集判定里，渠道候选人此前根本没人生成过；② 于是「来源」列的短名一律落到 `_ => "市场"` 这个兜底分支上。玩家读到的不是「他们都是市场来的」，而是「这一列没接上」。
2. 「目前这个待聘名单都是总监岗位（…由人力总监提交 CEO 决策）…我希望系统能依照开发文件中的人员候选库编写规律，生成更多的角色，不定时释放到市场/猎头挖角/海外引进/内部转岗/校招这些来源中。请分析这样可行吗？」
   —— 名单之所以只有总监，是因为池里的两类人各自被一道闸门挡住：人才市场的总监（`DataBase.LoadExecutives` 的 70 人候选库，负责人级）与 `StaffRecruitment` 的呈请候选人（不带 `source` → 归入人才市场 → 但**非负责人** → 被 `AcceptedInAnySourceView` 的「人才市场只收负责人」分支滤掉）。两条路都不产出「渠道来源 + 非总监」的人。

### 17.4 落地二：`TalentMarket`（投机候选池）

新增 `Unity Project/Assets/Scripts/Logic/TalentMarket.cs`（纯静态，无实例状态）。

**与 `StaffRecruitment` 的分工**（两者产物都写进 `gs.staffPool`，只靠 `source` 区分）：

| | `StaffRecruitment` | `TalentMarket` |
| :--- | :--- | :--- |
| 补什么缺口 | **编制缺口**（玩家呈请 → 渠道周期 → 收件箱审批） | **候选供给**（人力主动释放 → 玩家挑选） |
| 玩家角色 | 被动审批者 | 主动挑选者 |
| 产物来源 | 人才市场（不带 `source`，非负责人） | 仅渠道来源（校招 / 猎头 / 海外） |

两者**互不透支**：`StaffRecruitment` 的人被 `AcceptedInAnySourceView` 的「人才市场只收负责人」挡住，进不了介绍所名单；`TalentMarket` 的人带渠道标记，不会被收件箱的审批链路重复放行 —— 于是「同一个人既能从收件箱批准、又能从名单录用」这种双入口不会出现，`TalentMarket` 的类注释里把这条写成了不许拆的护栏。

**释放节拍**：每月 **1 日与 16 日**（`IsReleaseDay`）。选半月一拍而不是「每 30 天」是为了**不看 epoch** —— 读档任意时刻重放都落在同一天，没有隐藏状态可漂。

**渠道上限**：`CampusCap = 5` / `HeadhuntCap = 3` / `OverseasCap = 2`。够挑（一页 8 行）但淹不掉名单。上限按**同来源 `onMarket` 总量**算，因此玩家自己呈请落池的人也占额度：呈请一批 12 名校招生之后，本类会安静补到满为止，不会叠成两倍。

**渠道 → 职级映射**（`OpeningsFor`，决定「来源」这一列到底有没有信息量）：

| 渠道 | 职级 | 对应 `SourceStatMultipliers` 的口径 |
| :--- | :--- | :--- |
| 校招 | 专员 | 便宜、成型慢（0.85 潜力 / 0.75 薪资 / 0.8 效率，24 周到岗） |
| 猎头挖角 | 主管 / 副手 | 即战力、贵、易被再挖（1.15 潜力 / 1.45 薪资 / 0.9 忠诚，4 周） |
| 海外引进 | 运行岗 + 稀缺主管 | 国际航线准入要海外引进的机组（1.30 薪资，有适应期，12 周） |

- 映射**从编制表现算**（`StaffEstablishment.Roles(dept)`）而不是写死清单：编制表日后增删岗位时渠道供给自动跟上，不必两处改。
- **总监席永不由渠道产生**（`StaffRecruitment.IsDirectorRank` 同一口径）：那是 CEO 直接任命的专属职权，渠道不许绕过。
- 三类运行岗（`CrewPosts`：飞行员 / 乘务员 / 机务工程师）是编制表之外的**批量岗**（只由机队规模定编制，排不进 `Roles`），故单独补：校招补新人、海外补持证者；**猎头不碰运行岗** —— 批量岗挖角的经济性应由「呈请招聘」的渠道成本来体现。

**为什么刻意不加存档字段**：① 池量上限由 `staffPool` 派生 → 重复执行天然幂等；② 触发只看日历 → 读档重放不漂；③ 于是**老档不需要任何迁移**，读档时 `EnsureSeeded` 播一次种，之后按日历补齐。（`EnsureSeeded` 要求三渠道**全空**才补：若按来源逐个补，玩家把某渠道雇空后存档再读就白得一批。门槛抬到雇光 10 人的代价远高于收益，不给刷的动机。）将来若要加「候选人在池里待久了会流失」，那必须给 `PersonnelData` 加时间戳字段，届时再评估。

**挂载点**：`HrManager.TickDay` 内调 `TalentMarket.TickDay`（与招聘管道共用同一条日级时钟，不另起时钟）；`DepartmentManager.BootstrapOpeningTeam`（新局）与 `SaveManager.LoadGame`（读档）各调一次 `EnsureSeeded`。

### 17.5 落地三：录用闸门放宽（编制缺口直录）

`HrManager.HireCandidate` 原闸门是「必须能定位到一条进行中的招聘案（`Vacancy`）」，这对投机候选池是**死路** —— 池里的人不属于任何一次呈请，玩家会在名单里点到一个永远失败的「录用」。现把闸门剥成纯函数 `EvaluateHire(gs, p) → HireVerdict`（`ok / reason / viaVacancy / dept / rank / roomLeft`），`HireCandidate` 只负责按其判定执行入职：

```
verdict = EvaluateHire(gs, p)
  vac != null → 走招聘案（needed / hired 账本），余量 = needed − hired
  vac == null → 退回编制缺口判定 OpeningFor(gs, p, out dept, out rank, out room)
                 room <= 0 → 拒绝：「…编制已满，无法再录用（可在〔人力〕页复查编制…）」
```

`HireCandidate` 同时收一个显式 `gs` 的静态重载（原实例方法转发 `GameState.Instance`），理由见 §17.6。

- **有招聘案时不再叠一层编制缺口判定**：招聘案的 `needed` 在发起时已被「编制 − 在职 − 在途」裁剪过，此时二次判定会让「刚呈请 12 名飞行员（在途 12 已占满编制余量）→ 候选落池后反而录不进」。
- `OpeningFor` 内部按岗位性质分两口径（这是它区别于 `RecruitRoomLeft` 的地方）：**运行岗** → 编制由在役机队规模派生（编制 − 在职 − 在途）；**编制席** → `StaffEstablishment` 配额 − `CountFilled` 已在位人数。岗位名对不上编制表时返回 `false`（例如旧档里的自由文本职务），调用方不得据此放行。
- 编制席的部门识别两段式：先认候选人自带的 `department`（`CreateForRole` 按编制表写入，正常第一步即命中），再退化为全公司搜同名职务取**余量最大**者 —— 退化分支是给「玩家用调岗把在编员工换过部门」之后留在池里的候选兜底。

**顺带修掉的一个口径错位**：`ConfirmHire` 此前**只有一个 `operational: true` 的分支**（因为录用入口只有运行岗）。渠道把编制席（会计主管 / 收益管理主管…）放进池之后若仍标 `true`，玩家会雇到一个「**在编却不算在编**」的主管：不占编制表名额、薪酬不入 `OperationalPayrollMonthlyWan`、也不参与部门关键岗效率。现加 `operational` 形参，由 `HireCandidate` 传 `IsCrewPost(p.jobTitle)`；`StaffRecruitment` / 内部转岗两条既有链路仍传默认 `true`，行为不变。

另：录用**副总监**（`rank == "副手"`）时自动调 `DepartmentManager.AppointDeputy` —— 副总监席的「在任」记在 `DepartmentManager.deputyId` 上、不数 `staffPool`，不代办这一步玩家会看到一个「履新了但副总监席位仍然空着」的部门。

**连带修掉的僵尸记录**：`StaffRecruitment.RejectOffer` 走 `ReleaseCandidate`（从 `gs.staffPool` 里**移除**该候选人实体）。此前只置标记不摘除，被退回的候选会作为幽灵记录长期留在池里，`PoolCount` / 名单计数都会虚高。

### 17.6 护栏：`LogicSelfTests` R19

为了让上表两条**入职链路**断言真能跑（而不是在 `GameState.Instance` 取不到时静默跳过），`HrManager` 侧做了两处拆分：

- `EvaluateHire(GameState, PersonnelData) → HireVerdict`：把「能不能录」从「录了之后做什么」里剥出来，成为纯函数（`ok / reason / viaVacancy / dept / rank / roomLeft`）。

这么拆的直接原因：编辑器自检里 `AddComponent` 不触发 `Awake`，`GameState.Instance` / `HrManager.Instance` 都取不到，第一版用例只能打印「跳过入职链路」的告警 —— 一条**永远不执行**的断言比没有断言更糟（它看起来是绿的）。

## 18. 变更：顶栏读数带来源小下拉 + 过滤面板去掉遮罩（2026-10-11 晚）

### 18.1 触发（一张截图 + 一句陈述）

CEO：「点击『来源：全部』后，会显示灰底和右侧的过滤条件弹窗。」

**我想换个来源，按下一个看起来像标签的东西，结果是半屏名单被盖住并蒙了一层灰。**

### 18.2 诊断：不是 bug，是上一轮把入口做重了

§17.3 把 6 个来源芯片从顶栏收进过滤抽屉时，顺带把顶栏读数接成了「点开整个过滤抽屉」的入口。
当时只考虑了「玩家看不出在看哪个来源，也不知道去哪换」，没考虑代价：

1. **读数长得像标签，却点了会弹东西** —— 无从预期（末尾没有 ▾，没有任何可点线索）；
2. **换一个来源却要打开整个过滤抽屉** —— 抽屉盖住内容区右侧 42%，且那层
   `(0,0,0,0.28)` 的 Scrim 盖住左侧 57%，等于**换来源这个动作的代价是看不见名单**；
3. **Scrim 是一颗按钮，它同时吃掉点击** —— 抽屉开着时，连「点人名开档案」都做不到。

第 3 条是上一轮就存在的旧行为（`HEAD` 里就有 `Scrim`），但在 §17.3 之前，
换来源走顶栏芯片、不必开抽屉，所以它很少被撞上；芯片一收进抽屉，玩家每次换来源都要穿过它。

### 18.3 裁定（两条）

| 入口 | 行为 | 理由 |
| --- | --- | --- |
| 顶栏「来源：… ▾」 | 弹出 **6 档来源小下拉**，选完即收 | 换来源是高频轻动作，一击展开一击选中；末尾 ▾ 把「可点」写在脸上 |
| 「来源 / 过滤 · 招聘条件 ▾」 | 打开过滤抽屉，**去掉那层灰** | 调条件时要一边看名单一边改，压暗 + 吃掉点击正好挡住抽屉存在的理由 |

两处写的是**同一份状态** `_src`（不各存一份），只是入口快慢之分；两者互斥开合
（同开会让「选中的是哪一处」读不出来）。

### 18.4 「点面板外收起」为什么只在抽屉上让步

CEO 要的是「去掉灰底、名单看得清、还能点人名、面板外点击仍可收起」——
前三项在本面板里同时成立，第四项与小下拉相反地**只在过滤抽屉上放弃**，原因是 UGUI 的机制而非取舍：

- 收起要靠一层全屏透明接收层（旧 `Scrim`）。UGUI 的点击判定要求
  `pointerEvent.pointerPress == pointerUpHandler`；接收层若吃掉 pointerDown，
  抬起时手指已落在**同一帧被重建出来的行**上，两者不相等 → 那一击必然丢失。
  也就是说「点外收起」与「外点穿透到名单」在 UGUI 里**不可兼得**（除非自己重派发事件，
  代价是 press/hover 反馈全丢）。这里按 CEO 的明确要求取「能点人名」。
- 过滤抽屉改由 `✕`（面板右上）与顶栏那颗开关（会变成「收起过滤 ✕」）关。

小下拉**保留**这层接收层：它是瞬时控件，「点别处＝取消」是通用预期，
吃掉那一击的代价只是「想点人名得点第二下」，换来的是它一定收得掉、不会留一块挡着名单的浮层。

### 18.5 又一处灰：悬停提亮把 alpha 一起提了（同日同一个下午被发现）

§18.4 说「小下拉保留一层透明接收层，代价只是『想点人名得点第二下』」。CEO 随即追问：

> 为什么光标移到下拉菜单外面的区域就会变成灰色？

那层灰确实就是接收层 —— 但**不是我写的那层**，而是全项目共用的一个悬停反馈：

```csharp
// UIHoverBrighten.OnPointerEnter（旧）
_image.color = Color.Lerp(_preHover, Color.white, 0.22f);
```

`Color.white` 的 alpha 是 **1**，而接收层的底色是 `(0,0,0,0)`。
于是在 `a=0 → a=0.22` 之间插值的结果不是「提亮」，而是**凭空画出一层 22% 灰**，
盖住底下的名单文字 —— 报障截图里那块灰正好铺满整屏接收层（下拉本身画在它上面，故不灰）。

**为什么这不是「接收层的锅」**：`UIFactory.Button` 会**无条件**给每个按钮挂上该组件，
而全项目有一批按钮的底色本就是「透明但可点」的点击区：

| 位置 | 底色 | 悬停旧行为 |
| --- | --- | --- |
| `RecruitmentOfficePanel` 名单姓名（点名开档案） | `(0,0,0,0.01)` | 姓名字面浮出一块灰 |
| `RouteDetailPanel` 航线行 | `(0,0,0,0)` | 整行浮出灰 |
| `HRPanelUI` 部门卡标题 | `(0,0,0,0.01)` | 标题浮出灰 |
| `DepartmentInfoPanel` 人名 | `(0,0,0,0.01)` | 人名浮出灰 |
| `RecruitmentOfficePanel` 来源下拉接收层 | `(0,0,0,0)` | **整屏浮出灰**（本次报障） |

也就是说这是一个**早于 §18、遍布全项目的既有缺陷**，只是本例的接收层铺满整屏，
把它从「名字上一小块灰」放大成「半屏灰雾」才被看见。

**修法（改在根因，不改在下游）**：提亮只动 RGB，`alpha` 原样保留。

```csharp
// UIHoverBrighten.OnPointerEnter（新）
Color lifted = Color.Lerp(_preHover, Color.white, 0.22f);
lifted.a = _preHover.a;
_image.color = lifted;
```

语义上也更对：「提亮」是把**已经画出来的**底色变亮，不是把没画的画出来。
对不透明按钮（`a=1`）本行与旧行为完全等价；对半透明按钮（如 `NavIdle` `a=0.92`）
这才是正确的「变亮」——旧写法顺带把它们的透明度也推向 1，那不是任何人的设计意图。

**副作用（已知并接受，待补）**：姓名 / 航线行 / 部门卡标题这些点击区，原先靠那块灰
充当「可点」的提示。灰没了，提示也就没了。若后续要给它们补反馈，应改成文字层动作
（如姓名下划线或文字提亮），而**不是**回到给透明底面上色 —— 那正是本次要修的东西。

**护栏**：新增 PlayMode 用例 `UiHoverBrightenPlayModeTests.HoverBrighten_LiftsRgbButNeverAlpha`：

- ① 不透明按钮悬停 **仍须提亮**（防止「修好」的方式变成干脆不提亮，白丢反馈）；
- ② 透明点击区悬停 **alpha 必须仍为 0**（报障点）；
- 离开后精确还原。

只写 ② 不够：若拿到手的组件根本没在跑，② 也会绿 —— 所以 ① 同时充当
「这个 handler 真的在跑」的证据，使本用例不会退化成一条永远为真的断言。

**红 → 绿证据**（两次实跑，同一用例）：

```
# 临时回退 lifted.a = _preHover.a（out/pm_hover_before3.xml）
BEFORE_FIX -> total=1 passed=0 failed=1
  透明点击区悬停不得把 a=0 提成半透明灰 —— 那会在光标处凭空盖出一层灰雾
  Expected: 0.0d +/- 9.99e-05d
  But was:  0.2199999988079071d      ← 正好是 22% 灰，报障现象在测试里复现

# 恢复修复（out/pm_hover_after.xml）
AFTER_FIX -> total=1 passed=1 failed=0
```

**踩到的坑（值得记住）**：本用例第一版按接口取组件 ——
`solid.GetComponent(typeof(IPointerEnterHandler)) as IPointerEnterHandler` ——
结果**假绿/假红都不对**：`Selectable`（`Button` 的基类）**自己也实现了 `IPointerEnterHandler`**
来处理高亮态，而它在组件表里排在 `UIHoverBrighten` **之前**
（实测 `allTypes=RectTransform,CanvasRenderer,Image,Button,UIHoverBrighten`），
于是拿到的是 `Button`，调它的 `OnPointerEnter` 根本不打桩到本组件 —— 表现为「提亮没发生」。
必须按**具体类型** `GetComponent<UIHoverBrighten>()` 取。
这也正是 ① 那条断言的价值所在：它当场把「handler 没在跑」暴露了出来，
否则②会以「什么都没发生」的形式蒙混过去。

### 19.2 落地一：翻页 → 滚动

原先 `RowsPerPage = 8` + `第 x / y 页`。73 名候选人要翻 10 页，而「换个来源再扫一眼」
这类动作本身是扫读，翻页把扫读切成了十段。

- 列表改为 `UIFactory.VerticalScrollArea`（复用既有helper，与航线 / 机队 / 邮件箱同一套），
  **全部行一次性建出**（数十行量级，无需虚拟化），右侧常驻滚动条。
- 表头提升为 `ListHeader`，画在滚动区**之外** —— 滚动时列名始终可见。
- 翻页行让出的高度归列表，列表上沿紧贴表头下沿（`ListYMin = 0.010` / `ListYMax = 0.719`）。
- `_page` / `RowsPerPage` / `DrawPager` 全部删除；各筛选芯片里的 `_page = 0` 一并删除
  （改筛选会重建列表，滚动位置自然回到顶部，这正是想要的行为）。

**一个必须写下来的坑：滚动区比表头窄 16px。**
`VerticalScrollArea` 会给视口右边内缩 16px（给滚动条让位），而表头若仍按满宽画，
右端几列就会与数据行错开十几像素 —— 行是 11 号字，这个偏移看得见。
解法是把「表格右边界」`ListXMax = 0.961` 与「让给滚动条的宽度」`BarWidthPx = 16`
写成常量，**表头容器与滚动区各自按同一组常量定位**，于是两处算出的可用宽度恒等：

```csharp
// 表头容器：右侧同样内缩 16px → 宽度恒等于滚动视口宽度
new UIFactory.Anchor(new Vector2(0f, 0f), new Vector2(ListXMax, 1f), Vector2.zero, new Vector2(-BarWidthPx, 0f))
```

列宽仍按比例（`0.180 / 0.372 / …`），但因为两处宽度恒等，比例落到像素上是同一个位置。
滚动条整体落在数据区**之外**（视口右缘之后），不压住「来源」列。

  | 内部转岗（在编可调岗） | 在职 | `TryFindTransferTarget` 的目标 + 「（可调入）」 |

- 「现状」只有两值，是**故意**的：它是本页下一跳的分流判据（待聘 → 聘请 / 录用；在职 → 转岗），
  写多了反而把判据淹掉。所以它用弱色（`TextMuted`）——一句状态，不是数据。
- 内部转岗行写「（可调入）」是必要的：那一行的 `偏好工作` 是**目标**，而 `现状` 已经说了「在职」，
  不标注就会被读成他已经坐在那把椅子上（与 §14 里「非在职者副标题不得打印『部门 · 职位』」
  是同一个坑，只是那次是措辞，这次是列义）。

## 21. 变更：全池读数收进工具栏，KPI 条只剩四张全局卡（2026-10-12 晚）

### 21.1 触发

> 两个「全部来源 73 人」是重复了吗？

是，而且是**字面上的同一个值**，不是两个口径碰巧相等：

```csharp
if (gs != null) DrawKpiStrip(gs, rows.Total, pool);   // 数值 = $"{SrcLabel} {tabTotal} 人"
DrawToolbar(rows.Total);                              // 计数 = $"{SrcLabel} · {total} 人"
```

同一次 `Refresh()` 把 `rows.Total` 传给两处，拼出来的串只差一个分隔符：

| 位置 | 渲染 |
| --- | --- |
| KPI 首卡数值 | `全部来源 73 人` |
| 工具栏计数 | `全部来源 · 73 人` |

只差一个 `·` 的重复比原样重复**更坏**：它会让人去找两者的差别，而差别并不存在。

它是怎么变成两份的：§15 把 `数值 = 当前来源人数` 放上首卡，当时的恒等搭档是**页码行**（`共 N 人`）；
§19 删页码行时只删了那一份，这条恒等式就留下了两个端点。

### 21.2 定案（CEO 三选：`drop_card`）

> 删掉 KPI 首卡整张，全池与渠道候选并进工具栏读数；KPI 条只留四张全局卡。

选它的理由：**筛选数该待在改变它的控件旁**。KPI 条其余四张本来就是全局口径
（在途招聘 / 运行岗缺口 / 空缺率 / 人力成本），只有首卡随筛选变化 —— 那是本条里唯一的异类。
控件在工具栏，数就跟着控件走。

### 21.3 落地

- `DrawKpiStrip(gs, tabTotal, pool)` → `DrawKpiStrip(gs)`；首卡删除，其余四卡索引 0..3。
- `DrawToolbar(total)` → `DrawToolbar(total, pool)`，读数合成一行：
  `全部来源 · 73 人　全池 73 人 · 渠道候选 10 人`
  分隔符有意分两级：组内 ` · `、两组之间用全角空格，两段不会被读成一串并列项。
  读数框右端从 `0.640` 放到 `0.740`（文本变长；`Filter` 开关在 `0.780`，仍不重叠）。
- **KPI 卡必须重算间距**：`KpiCard` 原为 `x0 = 0.002 + i * 0.2`、宽 `0.196`。5 卡刚好铺满，
  减到 4 卡后若沿用会在右端空出一整张卡的位置，四张卡挤左边、看着像有一张加载失败。
  改为由 `KpiCount = 4` 派生：`w = (1 - 2·pad - (n-1)·gap) / n`（`pad = 0.002` / `gap = 0.054`）。
- 清掉一处**过期注释**：`Refresh()` 里「全池统计只算一遍，KPI 与**页码行**共用」——页码行 §19 已删。

### 21.4 为什么默认视图下仍会同时看到两个 73（以及为何不算重复）

默认筛选是「全部来源」，而**全池**与**未筛的池**此时是同一个集合，所以两个数必然相等。
这不是重复而是两个口径名的并列（§15 已辨析过这对关系），故两个数各自带自己的标签：

- `全部来源 · 73 人` —— 当前**筛选结果**
- `全池 73 人` —— **池子规模**（不受筛选影响）

它们**可以不等**：`pool.Listed` 数的是 `onMarket && !占岗`，而「全部来源」视图还包含
内部转岗者（`InternalCandidates`，这些人 `onMarket == false`）。所以两个数并列是有信息量的。
