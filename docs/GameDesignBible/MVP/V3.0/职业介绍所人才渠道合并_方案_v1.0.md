## 1. 触发问题

CEO 在 `人员 → 人力职能 → 招聘策略弹窗`（`n99`）里看到四个渠道方案（`ⓐ 批量校招 / ⓑ 猎头挖角 / ⓒ 海外引进 / ⓓ 内部转岗`），每个都标注了人均成本、招聘周期、成功率。但批复招聘后，**这些人从不以具体人物的形式出现在任何界面上**；而 `人员 → 职业介绍所`（`n112`）却有一张完整的候选人表（部门 / 空缺职位 / 姓名 / 国籍 / 期望年薪 / 聘请）。

需求因此提出：能否把四个渠道的人物并入职业介绍所的候选人列表。

## 2. 现状诊断

### 2.1 渠道线：只有一个计数器，没有人物

四渠道的全部差异集中在 `HrEconomics` 的三组数字上：

### 2.3 内部转岗：只有一个枚举值

`channel == 3` 在系统里的唯一存在形式，是 `HrEconomics.RecruitCostPerHire(3) => 500f` 和 `ChannelName(3) => "内部转岗"`。**没有任何"现职员工被调岗"的实现**：没有原部门编制扣减、没有交接期、没有调岗审批。

## 3. 结论：这不是「合并」，是「渠道实体化」

严格来说，本需求当前**无法直接执行**——四个渠道没有产出任何 `PersonnelData`，没有"人"可以并进列表。

因此建议把需求重新表述为三步：

1. **实体化**：让渠道真正产出带 `source` 标签的候选人对象（写回 `staffPool`）。
2. **合并**：把这些候选人按来源分组呈现在 `n112`。
3. **分流**：同一张表内按「是否总监」区分 CEO 直聘 / 转呈人力两种行内动作。

其中第 1 步是**唯一的实质性工作**，第 2 步是 UI，第 3 步是授权边界的重新划定。

## 5. 推荐方案

### 5.1 数据模型变更（**已落地**）

`PersonnelData` 新增三个字段 + 一个时间折算方法：

```csharp
/// <summary>来源渠道：market / campus / headhunt / overseas / internal。
/// 旧档读出可能为 null/空，一律按 market 处理，见 HrEconomics.NormalizeSource。</summary>
public string source = "market";
/// <summary>内部转岗交接期截止（UTC ticks）。</summary>
public long handoverUntilTicks;
/// <summary>运行/职能序列的批量招聘人员，不占编制、不参与关键岗效率统计。</summary>
public bool isOperational;

public const int HandoverDays = 14;
public const float HandoverEfficiencyScale = 0.7f;
public float EfficiencyAt(long nowTicks)
    => handoverUntilTicks > nowTicks ? efficiencyBonus * HandoverEfficiencyScale : efficiencyBonus;
```

`Vacancy` 新增三个字段：

```csharp
public long startUtcTicks;   // 本期招募发起时刻
public long dueUtcTicks;     // 本期候选人到位时刻（旧档为 0 → 视作立即到位）
public int inPool;           // 已落池、尚待 CEO 决定的候选人数
```

- **不新增** `internalEligible` 之类的持久标志位：内部转岗的可选性完全由 `rank != "负责人" && !onMarket && !IsOccupied(p.id) && 存在同职级缺口` 实时推导，避免旧档状态漂移。
- **旧档零迁移**：所有 `source` 消费点统一走 `HrEconomics.NormalizeSource()`，`null`/空 → `market`。
- `PersonnelData` 与 `Vacancy` 均为直接序列化，加字段向后兼容：旧档读出 `null`/`0` 分别视为 `"market"` / "立即到位"。
- `SeedCatalogHeads` 已有 `Find(gs, e.id)` 去重，不会把合并进来的人误当目录负责人重复灌入。

### 5.2 落池时机（**已落地：日级 Tick**）

候选人**不会**在发起招聘的瞬间出现在列表里，否则 `n99` 的成功率/周期立刻失去意义（等于立等可取）。`RecruitLeadWeeks` 现在是候选人落池的到期日：

```
批准招聘（LaunchRecruitment）
  → Vacancy.dueUtcTicks = now + RecruitLeadWeeks(channel) × 7 天
  → HrManager.TickDay（日级推进）到期时：
       PersonnelGenerator.CreateForRole() × (剩余需求 − 池中人数)，写 source = 渠道标签，落池
       dueUtcTicks += 一个渠道周期（持续输送，但池量永不超过剩余需求）
  → RecruitNow / HireCandidate 对池内候选人逐一掷成功率
       成功 → 入编并计入人数
       失败 → ReleaseCandidate 移出人事池
```

推进方式选定 **选项 B**：接入日级推进（`TimeManager` 中与 `StaffRecruitment.Tick` 并列），复用同一套时间语义。

### 5.3 UI 规格（`n112`，**已落地**）

1. **来源筛选胶囊**（顶部）：`待聘总监 / 校招 / 猎头挖角 / 海外引进 / 内部转岗`，复用 `HrEconomics.SourceName` 不另造术语。
2. **表增第 6 列「来源」**：颜色编码周期差——猎头（4 周）偏红=快而贵、校招（24 周）偏灰=慢而廉、海外（12 周）黄、内部转岗绿。
3. **行内按钮双语义**：
   - `CanCeoHire(p)` → `聘请`（沿用 `mgr.HireFromMarket(id)`）
   - 渠道候选人 → `录用` / `退回`（`HrManager.HireCandidate` / `RejectCandidate`）
   - 内部转岗 → `调岗`（`HrManager.TransferStaff`）
4. **分页**：10 行/页 + `◀ 上一页 / 下一页 ▶` + 直达「去人事履行 →」。
5. **内部转岗行**：部门列为**目标部门**，职位列显示目标岗位 +（调入），薪资列显示**调岗增量**（`+N.N 万`）而非完整年薪——否则与外部候选人在视觉上不可比。

### 5.4 非总监候选人如何呈现（**已按条件折叠落地**）

最终实现为 **5 个来源筛选胶囊**（而不是文档草案里的 6 个，因为「全部」在条件折叠下就等于「待聘总监」，两个页签会造成歧义）：

```
待聘总监 | 校招 | 猎头挖角 | 海外引进 | 内部转岗
```

| 页签 | 数据来源 | 行内动作 |
|---|---|---|
| 待聘总监（默认） | `onMarket && rank=="负责人" && !IsOccupied && source=="market"` | `聘请` → `mgr.HireFromMarket`（与改动前**行为完全一致**） |
| 校招 / 猎头挖角 / 海外引进 | `onMarket && source == 该渠道标签` | `录用`（CEO 确认人选，人力办入职）/ `退回`（移出人事池） |
| 内部转岗 | 规则实时推导：`!onMarket && rank!="负责人" && !IsOccupied && 存在同职级空缺` | `调岗`（直接授权，因属内部人事决定） |

**关键约束**：非总监行**不提供管理岗直聘**。渠道候选人的「录用」只是确认这个人选、由人力办理入职，**不能**借此被任命为管理岗——`StaffRecruitment.CanCeoHire` 的授权边界因此保持成立。

**为什么默认只列总监**：`n112` 原表 11 行就见底（底注还挂着"仅显示前若干名"的欠账）。无差别平铺会把列表变成几十上百行的招聘网站，让 `StaffRecruitment` 好不容易建立的"CEO 只批总监"边界名存实亡。条件折叠既保护 CEO 注意力，又让渠道真正可被检视比较。

## 6. 平衡性设计

### 6.1 来源属性分布（决定合并有无玩法价值）——**已落地**

如果并进来的人属性完全随机，"按来源筛选"就只是个显示位置移动，零玩法收益。因此 `PersonnelGenerator.ApplySourceProfile` 给不同来源分配了不同分布：

| 来源 | 潜力 | 年薪 | 忠诚 | 效率(即战力) | 体感定位 | 落地 |
|---|---|---|---|---|---|---|
| 校招 | ×0.85 | ×0.75 | ×1.10 | ×0.80 | 便宜、慢、要养 | ✅ |
| 猎头挖角 | ×1.15 | ×1.45 | ×0.90 | ×1.10 | 快、贵、易被再挖 | ✅ |
| 海外引进 | ×1.05 | ×1.30 | ×0.95 | ×1.10 | 稀缺岗位来源，有适应期 | ✅ |
| 内部转岗 | 维持基准 | 调岗 +20% | 维持基准 | 维持基准 | 零外部费用，代价在编制与交接期 | ✅ |
| 待聘总监（market） | 维持基准 | 现状 | 现状 | 现状 | 现行为基准 | ✅ |

### 6.2 内部转岗的抑制（**已落地**）

`内部转岗` 原值 **2 周 / 85% 成功率 / $500 人均**——一旦实体化会立刻变成**最强的无脑通道**。现行抑制手段：

- **外部费用归零**：`RecruitCostPerHire(3) = 0`（无外部方收费）。但代价转移为：
- **原部门编制缺口**：调岗改写 `department`/`jobTitle` → `StaffEstablishment.CountFilled` 立即 -1 → `StaffRecruitment.EnsureVacancies` 自动重建该岗招聘案。**缺口只是被搬了个位置，不是被消灭。**
- **交接期 14 天**：`handoverUntilTicks`，期间 `EfficiencyAt()` 返回 `efficiencyBonus × 0.70`，经 `TrainingGrowthLogic.DeptStaffLift` 拉低目标部门效率。
- **限制池**：只能调 `rank != "负责人"` 且未被 `DepartmentManager.IsOccupied` 占管理岗的在编员工；目标必须是**同职级的既有缺口**。

### 10.3 机组战力乘数（已接通，含漏洞修复）

`GameState.CrewQualityMultiplier` → `LiveClockSimulator.Land` 的航线落地利润，与 `monthlyRevenue` 同口径缩放（否则季结按 `monthlyRevenue×3` 轧差时会把缩掉的部分补回来）。按 `SimUtc.Date.Ticks` 做日缓存，人员变动时 `InvalidateCrewCache()` 当天生效。

**修复的反向激励漏洞**：`CrewQualityMultiplier(filled<=0)` 曾返回 `1f`（「未建机组 = 完全中性，既有数值基线一字不变」）。但航班调度**从不校验是否有机组**，于是：

| 情形 | 修复前乘数 |
|---|---|
| 0 名机组 | **1.000**（免费满利润） |
| 校招机组（战力 0.384 < 达标线 0.48） | 0.952（**被判折损**） |

即「永不雇机组」**严格支配**「雇校招机组」，所有渠道都是净亏损 —— 渠道系统形同虚设。这个倒挂是 `tools/balance --channels` 的 Part B 跑出来的。

**修复**：新增 `CrewUnstaffedMultiplier = 0.85f`，`filled<=0` 时返回它。不变量（由 `HrSafPlayModeTests.CrewQuality_UnstaffedIsStrictlyWorstThanAnyCrew` 全域扫描锁定）：

```
CrewUnstaffedMultiplier(0.85) < CrewQualityMin(0.88) <= 任何已建机组的乘数
```

这条不等式是**结构性成立**的，不依赖调参运气：`EfficiencyMin = 0.30` → 最烂机组 `delta = -0.18` → 乘数 `0.91`，仍高于 `CrewQualityMin`。于是两级激励都成立：**要不要招**（招任何人 > 不招）、**招哪个渠道**（猎头 1.019 > 内转 1.000 > 校招 0.952）。修复后最差的已建机组仍优于未建机组 **+12.0%**。

配套防线：
- `avgEfficiencyBonus <= 0f` 不再退回中性 —— 否则「有人但战力数据坏掉」= 白拿满利润；`NaN` 显式返回 `CrewQualityMin`。
- `GameState` 里三处硬编码 `return 1f`（含缓存初值 `_crewCacheValue`）全部改为走权威函数的「未建机组」分支，避免两处定义漂移重新开出漏洞。

**刻意不把覆盖率的"惩罚因子"乘在质量上**：若乘数 = 覆盖率因子 × 质量因子，则低覆盖 + 低战力（校招）会出现「招几个人比一个不招更亏」的**陷阱区**（需覆盖 >37% 才回本）。

### 10.3.1 编制覆盖率插值 + 接管局继承机组（2026-10-08 修订）

**发现的第二处口径分叉**：接管局（`TakeoverWorldBuilder.Apply`）只写机队 / 航线 / 贷款 / 遗留议题，**从不生成人员**；`PersonnelGenerator.GenerateAll` 只补管理序列关键岗（全部 `isOperational=false`）。于是 `PilotFilled = 0` → `filled<=0` 的保底分支被触发，**玩家接手的航司那 8 条正在运营的航线被当成「一架机组都没有」**，无条件吃满 ×0.85；而同一家航司的叙事层由 `crewVacancyPercent` 驱动着「机组人员短缺 15%」——该字段此前**只被写、从没被算**（唯一读取点是遗留议题文案与选司页文案）。

实测代价（北辰快线 · 10 架窄体 · 缺员 15%）：季度收入 518.67 万 → 未打折应为 610.20 万，**每季被多扣 91.5 万**，而同期盈利仅 44.58 万/季 —— 折损额是全部利润的 **2 倍多**。

**两处修订**：

1. **覆盖率改为线性插值**（不是惩罚因子）：

```
乘数 = CrewUnstaffedMultiplier + (质量乘数 − CrewUnstaffedMultiplier) × 覆盖率
覆盖率 = CrewCoverage(filled, establishment) = clamp(filled / establishment, 0, 1)
```

   三个性质：① `filled=0` → 恰好 0.85（保底最劣）；② `filled>0` → 严格 >0.85（招任何人都不亏）；③ 对 `filled` **单调不减** → 不存在陷阱区。因此「机组人员短缺 X%」终于有真实代价。`establishment<=0` 时覆盖率视作 1，退化为纯质量口径 —— 与两参重载（tools/balance / 纯公式自测在用）完全一致。

2. **接管局播种继承机组**：`PersonnelGenerator.SeedInheritedCrew(gs, vacancyPercent)` 按 `OperationalEstablishment(岗位, 在役机队, 宽体, 座位) × (1 − 缺员率)` 生成飞行员 / 乘务员 / 机务工程师，`onMarket=false`、`isOperational=true`、`source = SourceInherited`。北辰快线实况：编制 80 飞行员 → 在册 68 → 乘数 **0.9775**（不再是 0.85）。

| 新来源标签 | 语义 | 必须遵守的两条不变量 |
|---|---|---|
| `SourceInherited = "inherited"`（「继承在册」） | 接管局继承的在册机组 | ① **不进** `OperationalPayrollMonthlyWan`（薪酬已含在 240 万/机/年的存量聚合口径内，计入即双计）；② **不计入** `OverseasCrewCount`（不是海外引进渠道，国际航线准入仍须海外引进或考取 `intl_ops`） |

配套：`ApplySourceProfile` 把 `SourceInherited` 与 `market`/`internal` 并列早退，否则会落到 else 分支被贴上「国际经验、适应期」特性标签。旧档迁移在 `SaveManager.MigrateInheritedCrew`，判据保守：**仅当**「接管局 + 在役机队 >0 + `crewVacancyPercent` >0 + 运行序列一个人都没有」才补，只要玩家在旧档里招过任意一名机组就不动。

**UI**：`HrSubpagePanel` 的机组警示拆开两个独立抓手（缺编 / 战力），显示「机组覆盖 85%（68/80）→ 航线利润 ×0.98」，否则玩家不知道该招人还是该培训。

> **从零开局（非接管）保持不变**：`staffPool` 里确实没有任何建模机组，开局航线利润仍按 ×0.85 计 —— 这是 10.3 漏洞修复的刻意取舍，且现在会随招聘按覆盖率**平滑回升**到 ×1.00，不再是一个只能靠「招满 80 人」才跳出的悬崖。

> **剩余口径说明**：`hr.totalHeadcount` 已于 2026-10-08 改为派生值（随机队缩放，见 §14.2），故继承机组的薪酬与人数现在同属「聚合口径」两侧，不再一有一无。

### 10.4 飞行员编制按机队推导（已接通）
「飞行员」不在 `StaffEstablishment.Roles` 里，故 `Vacancy.needed` 曾完全由玩家口径决定且**可无限累加**（推高 `UnionCostWan` 与 `TrainingRoi`）。现按 `HrEconomics.OperationalEstablishment`（窄体 8 人/架、宽体 +2、机务 6 人/架、乘务按座位）推导编制，`LaunchRecruitment` 按「编制 − 在职 − 在途」封顶 `needed`，扩机队后编制自动上调。

### 10.5 海外引进的专属生态位（已接通）

`RoutePermitLogic.MissingPrerequisite` 新增缺口码 **2**：国际/地区航线发证要求至少 1 名「海外引进」渠道到岗的运行序列人员（`GameState.OverseasCrewCount` / `HasOverseasQualification`）。校招/猎头/内转都不提供该资质。

**为什么必须有这条**：Part B 显示海外引进在成本与战力两个口径下都不占优（单位战力成本 30.4 万/点，被猎头的即战力支配）。没有生态位它就是纯劣势选项。有了这道硬前置，它从「被支配」变成「国际航线的必需渠道」。

缺口码顺序为 **航权(1) → 海外资质(2)**，`InboxManager` 两处（`AcceptRoutePermit` 与周期 tick）均已处理码 2，标签「国际运行资质」。

### 10.6 配额旁路修复

### 10.7 渠道收益差（`tools/balance --channels` 实测）

样本：6 名「飞行员」· 人才紧缺指数 60 · 成本系数 ×1.10

| 渠道 | 累计成本(万) | 总耗时(天) | 3年TCO(万) | 万/战力点 | 战力乘数 |
|---|---|---|---|---|---|
| 批量校招 | 1.76 | 336 | 19.86 | **17.24** | 0.952 |
| 内部转岗 | 0.00 | 0 | 28.80 | 20.00 | 1.000 |
| 海外引进 | 15.84 | 420 | 48.14 | 30.39 | 1.019 |
| 猎头挖角 | 13.20 | 84 | 48.97 | 30.92 | **1.019** |

落池属性（`ApplySourceProfile` 实际产物，含 clamp）：

| 渠道 | 潜力 | 年薪(万) | 忠诚 | 战力 |
|---|---|---|---|---|
| 批量校招 | 0.748 | 6.00 | 74.8 | 0.384 |
| 猎头挖角 | 0.980（触顶 clamp） | 11.60 | 61.2 | 0.528 |
| 海外引进 | 0.924 | 10.40 | 64.6 | 0.528 |
| 内部转岗 | 0.880 | 9.60 | 68.0 | 0.480（交接期 14 天 ×0.70） |

## 14. 变更：全公司总人数改为派生（2026-10-08）

### 14.1 问题

`hr.totalHeadcount` 是默认 450 的**固定值**，与机队规模脱节。而它的兄弟口径 `LaborCostAnnualWan`（§10.2 已接通）是 `240 万/机/年 × 在役机队`——**成本随机队走、人数却钉死**。后果：

| 消费者 | 失真 |
|---|---|
| `UnionCostWan`（按人头计费） | 20 架机队的「让步」成本按 450 人计 = 360 万，正确应为 1800 人 × 0.8 = **1440 万**，低报 **4 倍**。劳资决策在大航司被系统性低估。 |
| `TrainingRoi`（按人均预算） | 人均 = 预算 / 人数。人数少报 → 人均虚高 → ROI 虚高，大航司的培训投入显得比实际更划算。 |

### 14.2 落地

新增 `HrEconomics.HeadcountPerAircraft = 90f`（锚点与 `DefaultAnnualLaborCostWan` **同源**：5 机 ↔ 450 人 ↔ 1200 万/年，人均 2.67 万美元/年）与：

```csharp
public static int EffectiveHeadcount(int activeAircraftCount, float perAircraftHeads, int additiveHeadcount)
```

与 `EffectiveAnnualLaborCostWan` **完全同构**（`费率 × 规模 + 增量`），故两者随机队同步缩放。

`HrState` 新增三个字段（`headcountPerAircraft` / `headcountAdditive` / `headcountMigrated`），`totalHeadcount` 降级为**旧档迁移来源**——与 `laborCostWan` → `laborCostPerAircraftWan` 的处理完全一致。迁移函数 `HrManager.MigrateHeadcount` 与 `MigrateLaborRate` 逐行同构，含「无机队时保底每机人数 + 旧总数转增量」的分支。

实值出口为 `GameState.TotalHeadcount`（派生属性，与 `LaborCostAnnualWan` 相邻）。三个消费者全部改读派生值，`HrSubpagePanel` 显示改为带构成的文案（`在编 1812 人（机队基准 1800 + 招聘增量 12）`），否则玩家看到数字随买/退飞机跳变会以为出错。

**增量与基数不重叠**：渠道招聘到岗者进 `headcountAdditive`（其薪酬在 `OperationalPayrollMonthlyWan`，聚合之外）；§10.3.1 的继承在册机组**不进**增量（其薪酬在聚合之内，已由每机人数代表）。

### 14.3 平衡影响

- **基准不变**：5 机基准航司 5 × 90 = 450 人，与旧值一字不差；`tools/balance` 基线自检不变（该工具此前硬编码 `headcount = 450`，现改为 `EffectiveHeadcount(fleetCount, 0f, 0)`，5 机场景结果相同）。
- **大航司修正**：接管局（北辰快线 10 机）= 900 人（旧值 450），工会「让步」成本 360 → 720 万。与营收同比例（720/9320 ≈ 7.7%，与 5 机基准的 360/4660 一致），故决策的相对权重不变。
- **从零开局**：青禾航空 3 机 = 270 人（旧值 450），工会成本随之下降——此前对小航司是**高报**。

### 14.5 HR 存档接通（2026-10-08，同一轮内解决）

**发现**：`gs.hr` **完全没有持久化** —— `SaveManager` 的 `Key*` 常量表里没有 HR 键，全文件搜不到任何 `gs.hr` 读写。`HrState` 每次启动都是 `new`，以下状态**跨存档全部丢失**：

- `trainings`（在培项目 / 完成率 / `memberIds` / `certId` / `enrolledTicks` / `durationQuarters`）
- `vacancies`（在途招聘 / `dueUtcTicks` / `inPool`）
- `trainingCenterLevel` / `trainingCenterBuildLevel` / `trainingCenterBuildDoneTicks`（培训中心等级与在建工期）
- `union`（`satisfaction` / `strikeCountdown` / `cbaExpiresIn`）、`strikeRisk`、`trainingBudgetWan`、`employeeSatisfaction`、`trainingRoi`、`lastCompNote`

这不只是「丢了几个数字」——**它是 §10.3.1～§14.2 那一整套培训/证照 UI 的釜底抽薪**：§14.2 的在培名单、`TrainingHubPanel` 的施工倒计时、`StaffProfilePanel` 的持证列表，读档后全都会退回开局态；而 `MigrateLaborRate` / `MigrateHeadcount` 两条旧档迁移路径在**生产环境永远不会触发**（只在自测里被显式构造的旧档命中）。

**落地**：

- `SaveManager` 新增 `KeyHr = "ACEO_Hr"`，登记进 `AllSaveKeys`；写档用既有的 `HrSave { state = gs.hr }`（`HrTypes` 里本就备好了这个包装类，此前从未被使用）。
- 读档紧跟 `staffPool` / `MigrateInheritedCrew` 之后（迁移需要机队与人事池已就位），`try/catch` 兜底后调 `HrManager.EnsureState(gs)` 补 null 容器并跑迁移。旧档无本键 → 空串抛异常 → 落 `new HrState()` → **行为与改动前逐位一致**，无回归。
- 顺带修掉清档漂移：`ClearGameSaveMenu` 此前自己维护一份硬编码键表，与 `SaveManager.AllSaveKeys` 漂移，**漏清 19 个键**（`ACEO_StaffPool` / `ACEO_StaffRecruits` / `ACEO_UsedMarket` / `ACEO_CityEconomy` / `ACEO_UsdCny` / `ACEO_SpeedLevel` / `ACEO_FlightRings` / `ACEO_LiveQIncome` …）。清档后人事池与汇率会带着上一局的数据重新开局 —— 现改为直接消费 `SaveManager.AllSaveKeys`（该字段本就是 `public`），新增存档字段只需在 `SaveManager` 登记一次，此类漂移从根上消除。
- 自测：`LogicSelfTests` 新增 `HrSave` 往返核验 —— 逐字段断言 `trainings`（含 `List<string> memberIds`）、`vacancies`、`union`、`talentIndex`、培训中心等级/工期、两条迁移标记全部无损（`JsonUtility` 对嵌套 `[Serializable]` + `List<T>` 有静默丢字段的历史，故必须实测而非假定）；并断言空串读取**抛异常**（由 `SaveManager` catch 兜住）而不是返回半个对象。

**边界**：`memberIds` 指向已离职者时由 `TrainingGrowthLogic.ResolveTargets` 跳过（`p == null || p.onMarket`），故「存档 → 炒人 → 结业」不会空引用。
