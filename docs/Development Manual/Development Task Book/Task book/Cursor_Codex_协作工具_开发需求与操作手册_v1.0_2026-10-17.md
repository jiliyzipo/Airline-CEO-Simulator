## 1. 发给 Cursor 的开发指令

请在现有项目中开发一套**本地项目协作工具**，让 Cursor 的开发交付与 Codex 的工程检测使用同一套任务编号、源码版本、状态和证据。

先读取 `docs/ProjectManifest.md`、当前阶段任务书、最新交接与现有回归工具，按本文实现第一阶段 MVP。保留工作区所有既有修改、未跟踪文件及待确认删除项，不清理、不重置、不自动提交或推送。

交付应包含：命令行程序、共享状态格式、开发/检测交付格式、版本失效检查、并发控制、隔离验收衔接、两端规则与可选 Hooks 适配、中文操作说明和自动化验收。先做可手动调用的完整闭环，再接 Hooks；MCP 服务属于后续阶段。

不要开发另一个航空游戏功能，不要重写现有 Unity 业务，也不要把完整聊天同步当成此工具的实现目标。完成工具后生成开发交付，交给 Codex 独立检测；Cursor 不代替 Codex填写验收通过。

## 2. 要解决的问题与成功标准

现在的风险包括：两边不知道谁在修改哪个任务；模型切换或新对话丢失上下文；开发完成与检测通过混用；检测后源码又变但任务仍显示绿色；两端同时写进度；不同 Unity 实例或测试污染玩家数据。

工具交付后的成功标准：

1. 用户能一眼看到“谁在做什么、哪一版待检测、检测是否仍适用于当前代码”。
2. Cursor 完成开发后，Codex 能读取交付并检测固定源码快照。
3. 检测失败能带任务号、缺陷号、实际结果退回 Cursor。
4. Cursor 修改后旧报告仍保留，但新代码自动显示待复验。
5. 换模型、换聊天后，读取同一状态即可继续，不需要重新搬运全部聊天。
6. 即使 Hooks 不支持、被关闭或漏触发，手动命令仍能完成全部流程。

本地文件更新能很快被另一端读取，但**文件变化不代表正在运行的模型已自动读取或理解**。必须显示对方最近确认读取的 revision；不能把磁盘已更新写成双方都已知晓。

## 3. 职责与修改边界

### 3.1 Cursor 开发方

负责功能代码、业务修复、资源配置及相关设计文档；领取任务、维护开发交付、解释影响范围、处理 Codex 提出的缺陷。

DeepSeek、Qwen、GLM、GROK 的切换只改变交付记录中的 model 字段，不另建四套任务状态。默认同一任务只有一位开发持有人，不让多个模型同时覆盖同一文件。

开发方可以写“已实现，待检测”，不能写“Codex 已通过”。开发自测结果要保留为自测，不能作为独立验收结果冒名导入。

### 3.2 Codex 检测方

负责读取任务与交付，检查代码及工程状态，编写或维护检测用例和检测工具，执行隔离回归，发布检测报告与缺陷。

**默认不修改生产业务代码、玩法参数、场景及正式资源。** 发现业务问题先退回 Cursor。用户明确授权 Codex 修复时，作为一次有记录的角色例外处理：记录授权说明、修改文件、新版本及重新检测，不静默改变分工。

Codex 新增测试或修复测试夹具时须记录验证工具版本；不得为了得到绿色而删除有效断言、忽略失败或降低业务门槛。

### 3.3 用户

决定优先级、验收范围、设计争议、范围变更及是否提交/推送；保存并关闭用户 Unity。工具不代替用户做设计裁决或 Git 发布操作。

角色标签是协作规则；若使用同一 Windows 账户，它不是防恶意伪造的安全认证。工具要检查调用方的声明角色与允许动作，并保留审计记录；不能声称提供了操作系统级身份隔离。

第一阶段使用现有 Node.js 环境，优先 Node 标准库；Windows 的 PowerShell 负责衔接现有 Unity 脚本。不要求数据库、Docker、云服务、额外模型 API 或付费账号。

项目规则、工具源码、配置示例和必要协作证据应可进入版本；本机路径配置、锁、缓存、密钥和大体积快照不进入版本。具体清单必须写入交付，不自动暂存或提交。

不要把新的业务状态写进 `docs/ProjectManifest.md` 的每一段。该文件继续作入口，链接到自动生成的 CURRENT.md。当前任务书仍是任务范围和验收条款的依据，新工具不另造一份相互冲突的任务清单。

## 5. 任务与状态模型

沿用现有任务号，例如 T03.8；修复或进一步细分使用 `T03.8-F001` 等明确关联编号。每个任务必须有 scope、验收条件和依赖，不能只有一句“修好”。

### 5.1 两组状态必须分开保存

开发状态：`todo / developing / ready_for_review / rework`。  
检测状态：`not_run / queued / running / passed / failed / blocked / cancelled`。

另存以下独立信息，避免把互不相同的情况塞进一个字段：

- `freshness`：`current / stale / unknown`，表示报告与当前版本的适用性。
- `blockers`：阻塞原因，例如 Unity 被占用、依赖恢复失败、等待设计裁决。
- `coverage`：每条验收条件分别通过、失败、未执行或不适用，并附证据。
- `lastAcknowledgedRevision`：Cursor、Codex 最近实际确认读到的状态版本。

推荐流转：

```text
待开发 → Cursor开发中 → 交付待检测 → Codex检测中
                                      ├─ 失败 → Cursor修复 → 新交付
                                      ├─ 阻塞 → 处理条件后重新检测
                                      └─ 通过 → 当前版本验收通过
源码/验证基线发生相关变化 → 旧报告保留，新版本待复验
```

### 5.2 完成与失效规则

- 开发方无权直接把独立检测状态改成 passed。
- 有必需用例未执行、缺失结果文件、未知覆盖或未解决的必需条件时，不得显示整项完成。
- 一个阶段报告成功，不自动让 T01～T06 全部打勾。
- 源码已变化时，历史报告仍是“该旧快照通过”；当前代码显示待复验，不篡改历史通过结果。
- 任务范围/验收条件变化也可能使验收失效，即使源码未变。
- 文档排版或不相关资料变化不应一律要求全套 Unity 重跑；影响范围无法判断时显示待确认，不能猜测无影响。

## 6. 必需数据与不可覆盖记录

### 6.1 任务定义

至少包含：schemaVersion、projectId、taskId、title、revision、开发/检测状态、负责人、scope、acceptanceCriteria、dependencies、blockers、createdAt、updatedAt、来源任务书及条款定位。

### 6.2 开发交付单

每次开发完成创建新的 deliveryId，至少包含：任务号、任务定义 revision、开发工具及模型、变更摘要、修改/新增/删除文件、业务风险、开发自测结果、已知缺口、分支与 HEAD、是否有未提交/未跟踪文件、源码清单及指纹、推荐检测配置、快照路径、生成时间。

存在 Git 提交时记录提交号；没有提交时，完整工作区白名单文件清单和哈希同样有效。**不得为了生成交付而自动提交。**

### 6.3 独立检测报告

每次检测创建新的 reviewId，至少包含：对应 deliveryId、任务号和 revision、检测工具版本、验证工具指纹、受测快照指纹、环境、具体命令、每项退出码、真实断言数、跳过数、结果文件路径及哈希、覆盖条款、未覆盖范围、缺陷列表、开始/结束时间。

退出码 0 只是证据之一。必须同时判断 XML/JSON 结果、失败断言、预期成功标记及任务覆盖；缺失结果不能算通过。

### 6.4 缺陷与事件

缺陷至少包含：issueId、taskId、受影响交付、复现输入、预期/实际、证据、严重度、建议修复归属、状态及关闭该缺陷的后续检测。

事件包含唯一 eventId、projectId、revision、时间、actor、动作、关联 taskId/deliveryId/reviewId、父事件及数据摘要。开发/检测记录只追加；纠错通过新记录关联旧记录，不静默覆盖旧证据。

派生的 CURRENT.md、待办摘要和任务书勾选由同一个程序根据这些记录生成，不由两个模型分别重写。

## 7. 版本、指纹与源码快照

这是 MVP 必须实现的核心，不能只比较 Git HEAD。当前项目存在大量未提交和未跟踪的必需文件，相同 HEAD 不代表相同工程。

### 7.1 指纹范围

采用版本化的白名单和确定性排序，统一相对路径/分隔符，用文件实际字节的 SHA256 计算；明确处理新增、删除、改名、`.meta`、`.asmdef`、Packages、ProjectSettings、场景及资源。

区分三类指纹，并保留完整文件清单：

1. **实现指纹**：游戏代码、场景、资源、包锁及影响构建/运行的设置与工具。
2. **验证指纹**：测试代码、回归入口、检查脚本、用例配置与断言基线。
3. **验收合同指纹**：本任务的范围、必需条件、证据要求。

不能一刀切排除所有 Editor 代码：有的 Editor 工具影响构建和资源，需要归入实现。测试与业务混在同文件时，该文件计入双方范围。无法可靠分类时保守纳入，不为了避免复验偷偷缩小白名单。

Codex 补充测试后应更新验证指纹，报告明确“用哪套测试验证哪版实现”；不能把 QA 新增测试误写成 Cursor 的业务交付。验证工具变化后，旧结果对当前验证基线的适用性也必须重新判断。

现有 `Baseline_2026-10-17.json` 使用综合源码指纹，必须保留其版本含义。新格式增加 schemaVersion/fingerprintPolicyVersion，不能把旧综合哈希直接当作新分类哈希比较。

### 7.2 不参与实现指纹的内容

排除 Library、Temp、Logs、Builds、obj、bin、专用 out 快照、协作运行缓存、事件、检测结果和生成状态页，避免“写报告→指纹改变→再写报告”的循环。普通资料文档单独记录；验收合同变化按前项处理。

本地配置、个人路径、密钥不得进入可分享快照。检查失败只指出文件和字段，不打印密钥内容。遵守现有资源许可和个人字体排除约定。

### 7.3 快照与变化期间的行为

- 交付时先扫描清单，导出隔离快照，再核对源和副本；复制期间源变动则重试或明确失败，不能交付混合版本。
- 测试读取固定快照，不能一边读取 Cursor 正在改动的主工程一边宣布结果适用于整版源码。
- Cursor 可以继续在主工程开发其他任务；不能修改正在检测的固定快照。
- 验收结束时重新核对当前实现/验证/合同。A 快照通过但工作区变为 B 时，显示“A已通过；B待复验”。
- 报告必须区分“本地源码快照通过”和“Git干净检出通过”，后者没有实际执行时始终为 false。

## 8. 要开发的命令行接口

以下是**待实现的接口约定**，不是现有命令。可调整参数拼写，但语义与操作说明必须保持一致，全部支持 `--help` 和机器可读 `--json` 输出。

```powershell
node tools/collab/cli.mjs doctor
node tools/collab/cli.mjs init
node tools/collab/cli.mjs status
node tools/collab/cli.mjs sync
node tools/collab/cli.mjs ack --actor cursor --revision <revision>
node tools/collab/cli.mjs claim --task T03.8 --actor cursor --expected-revision <revision>
node tools/collab/cli.mjs deliver --task T03.8 --actor cursor --summary-file <file>
node tools/collab/cli.mjs review-start --delivery <deliveryId> --actor codex --profile <profile>
node tools/collab/cli.mjs review-run --review <reviewId> --actor codex
node tools/collab/cli.mjs review-finish --review <reviewId> --actor codex --evidence <file>
node tools/collab/cli.mjs release --task T03.8 --actor cursor
node tools/collab/cli.mjs watch
```

接口要求：

- doctor 只读检查项目根、依赖版本、客户端/Hook 能力、Unity 路径及状态可读性；缺失能力给出具体说明，不自动安装或修改全局配置。
- init 生成项目级配置和初始结构，重复执行不得覆盖已有规则/状态；从现有任务书导入前展示映射和冲突。
- sync 重新检查文件变化、状态 revision、报告适用性并生成摘要，不提交、不执行 Unity。
- claim 原子领取，第二个开发者领取同任务须失败并显示持有人；允许独立任务同时开发，但须检查文件范围冲突。
- deliver 校验任务、交付信息及稳定快照，生成不可覆盖记录；缺验收条件或快照不稳定则失败。
- review-start 固定交付、验证基线、检测配置并领取检测资源；它本身不表示测试已经执行。
- review-run 调用允许的检测配置，记录 stdout/stderr、退出码和结果文件，支持失败/取消/中断后的明确状态。
- review-finish 只能从受测指纹匹配的真实证据生成结论，禁止仅传一个 `--passed` 就验收通过。
- release 释放任务占用，不删除交付或检测报告。
- watch 只监听变更、汇总状态和提示待复验，默认不自动运行 Unity、不触发提交、不擅自发消息或启动另一端模型。

命令错误必须返回非零。区分参数错误、状态冲突、资源被占用、检查失败、证据不完整；具体退出码在 PROTOCOL.md 固定。外部工具的原始退出码另存，不能被协作程序掩盖。

## 9. 并发、文件写入与恢复

共享状态采用单一写入服务或带锁的命令事务。Node 本地锁可用排他创建实现；写文件采用同目录临时文件、落盘后原子替换，配合 revision/CAS 检查，不能两个进程最后写入者覆盖前者。

锁需记录 owner、PID、机器、开始时间和心跳；过期不等于可以直接清除。PID 被复用、进程无法核实或用户实例仍在时，显示待处理。恢复命令必须只处理本工具的锁和临时文件，不能删除 Unity 工程锁。

被中断的 review 标记 blocked/cancelled 或 interrupted 原因，不得留作 passed；恢复读取已有步骤与证据，不能把未执行的后半段自动补成成功。重复 Hook/命令按 eventId 或幂等键去重，重复写入不能造成重复领取、重复检查或重复勾选。

MVP 只要求同一台电脑、同一工作区的可靠协作。不同 worktree、不同电脑需单独设计共享事件存储/同步方案，不能依赖 `.gitignore` 中的本机锁跨机器生效。

## 10. 与现有工程检查的衔接

优先适配现有入口，不把它们复制成第二套实现：

- `tools/semcheck/run.js`、`run.test.js`、`gen.js`、两个语义编译工程、`enccheck.js`。
- `tools/slotcheck/slotcheck.csproj`。
- `tools/regression/export-baseline.js`。
- `tools/regression/RunUnityTests.ps1`、`RunUnityRegression.ps1`。
- `tools/balance/AirlineCEO.Balance.csproj`。
- `docs/handoff/verification/2026-10-17/Verification.json` 及 XML/CSV，作为历史证据格式参考。

现有导出器存在固定日期的报告名、目的目录约束和综合指纹；需要参数化为每次唯一 delivery/review 输出，并为新格式做兼容适配。不能覆盖 2026-10-17 历史清单或假定现有导出器已经支持任意 `out/` 路径。

检测配置建议有 compile、slot、unity-edit、unity-play、r42、startup、balance 等固定白名单；任务声明必需配置和覆盖条款。不同任务不必每次全部运行，但跳过必须有范围依据。不能拼接交付单中的任意字符串为 shell 命令，使用固定程序及结构化参数。

语义检查的生成 csproj 包含本机 Unity/Library 引用。换机需要 Unity 导入、生成工程、运行 gen.js 和 dotnet restore；doctor 应检查这些条件，不把旧机器引用当作可复现依赖。

### Unity 必须遵守

1. 在能真实读取 Windows 进程的环境中检查占用。沙箱空进程列表不能证明无 Unity。
2. 检测到用户 Unity 时，状态为“等待用户保存关闭”，不能自动强杀、关闭或删锁；用户关闭后由 resume/review-run 重新检查。
3. 用户 Unity 被占用期间可以执行不依赖该资源的静态检查，但不能把 Unity 检查标为完成。
4. 隔离副本使用专用 companyName/productName，确认 PlayerPrefs、persistentDataPath、存档与已学习词库不会指向玩家工程。
5. 禁止用完整 `LogicSelfTests.Run()` 替代隔离回归，该入口含清空词库行为；R42 使用既有独立入口。
6. Unity 批处理串行执行；多任务也只能持有一个 Unity 检测资源锁。采用最小保守策略时，任何 Unity 在运行就暂缓批处理。
7. 不得因接管压测正常触发经营终局，就自动宣称长线平衡健康。60组合出现危险结果及退出码1必须如实保留。

## 11. 双端规则与 Hooks

### 11.1 共同规则

提供短 `AGENTS.md`，要求两边在开始任务、领取任务、交付、检测结束和准备勾选前读取 CURRENT 与相关记录；先 sync，再 ack 所读 revision。新会话和换模型后也执行同样流程。

已有 AGENTS.md 或 Cursor 规则时先合并并保留用户内容；不要覆盖或生成两套互相矛盾的项目规则。若 `.cursor/rules` 只作入口，应链接共同协议，而非复制所有条款后分别维护。

### 11.2 Hooks 适配

Cursor 文件编辑结束/任务结束、Codex 会话开始/工具操作结束/回合结束等事件，在当前版本支持时调用同一个协作 CLI。适配器只负责转换事件，不维护第二份状态。

文件事件采用约1～3秒防抖；事件触发后更新变更与 freshness，不能推断“任务完成”。开发任务结束时可以生成交付草稿，但只有字段齐备且稳定快照生成成功才发布正式交付。

Hooks 的事件名、配置方式、是否能注入上下文以当前安装版本实际验证为准。不得把 Cursor 的配置直接复制成 Codex 配置。会话开始不支持自动注入时，用共同规则要求主动读取；完全不支持 Hooks 时仍提供手动 sync/交付入口。

只启用项目级配置，初始化时列出准备写入的文件。全局用户配置修改必须另获明确授权；不得由安装脚本顺带更改权限、安全策略、自动审批或 API Key。

### 11.3 实时同步的验收范围

本地 watch 开启且无错误时，保存相关文件后5秒内刷新磁盘状态；对方确认读取后更新 ack。未读的一端明确显示“状态已更新，对方尚未确认读取”。不能承诺把任意变化实时塞进一个正在生成回答的模型上下文。

Hooks 不负责自动发送跨应用聊天。若以后需要自动唤起检测、调模型或发通知，应作为额外功能单独授权和设计。

## 12. 与现有任务书的同步

用配置显式映射 taskId 到任务书文件、子项及验收条件。Markdown 勾选不能靠模糊全文替换实现；找不到唯一目标或条款已变更时停止并报告冲突。

本工具只在对应条款全部满足且当前报告适用时更新勾选。总任务必须满足所有必需子项及额外总验收条件。T02 的“Git干净检出未验证”必须继续阻止总项勾选，即使本地导出启动通过。

源码改变使先前验收失效时，当前任务书恢复待复验状态并保留旧日期/证据关联；不删除旧报告。用户手工修改条款或勾选发生冲突时显示待核对，不能静默覆盖。

首次迁移现有 T01～T06 时必须保留当前“已验收/部分验收/未覆盖”的实际差别；不能把 99 项 PlayMode 和 25 项 EditMode 的历史成功直接当作新工具已验收或所有游戏任务已完成。

## 13. 用户以后如何操作

以下操作以 Cursor 完成本工具并经 Codex 验收为前提。日常优先用自然语言指令，不要求用户手工编辑 JSON。

### 13.1 首次安装与初始化

1. 把本文发给 Cursor，使用第1节的开发指令。开发期间继续保留现有工作区，不提交、不清理。
2. Cursor 完成后，要求提供工具开发交付单、测试结果、实际可用命令及未完成项。
3. 把交付 ID 或交付路径发给 Codex：“请按这份需求独立验收协作工具，默认不改生产业务代码。”
4. 检测通过后，运行 doctor/init；用户确认导入的任务和规则没有覆盖旧内容。若需改全局配置，单独决定是否授权。
5. 两端都打开同一个项目根。先使用手动闭环演练一个示例任务，再启用 watch/已验证的项目 Hooks。

### 13.2 每天开始工作

打开 CURRENT.md 查看当前任务、持有人、最新交付、检测结果、版本是否过期及阻塞。

给 Cursor：

> 先同步并确认读取最新协作状态。领取任务 T03.8，按任务书范围开发；不改变时间比例，不提交。完成后生成开发交付，交给 Codex 检测。

给 Codex：

> 先同步并确认读取最新协作状态。读取最新待检测交付，按其必需配置做独立工程检测；不修改生产业务代码，失败请生成缺陷并退回 Cursor。

工具应在双方回复中带出 taskId、deliveryId/reviewId、revision 与版本状态，便于用户核对双方是否真的在同一任务上。

### 13.3 Cursor 开发完成以后

查看交付摘要，确认范围没有扩大。将 deliveryId 发给 Codex即可，不再手动复制整个聊天。MVP 不会自动替用户发送这条消息。

Cursor 若换模型，告诉新模型：

> 读取共同规则、CURRENT和任务Txx的最新交付/缺陷，先ack当前revision，继续同一任务；不要另建重复任务。

### 13.4 Codex 开始检测时

若出现“Unity被占用”：用户自行保存并关闭Unity，再告诉Codex“我已关闭Unity，请重新检查并继续”。Codex重新检查后才启动批处理，先前的关闭表态不作为以后关闭用户实例的永久授权。

检测读取隔离快照。此时可以让Cursor开发另一个不冲突的任务；若修改了同一实现，旧快照继续检测但当前版本显示待复验。不要让两个工具同时修改相同业务文件。

### 13.5 检测失败

把 reviewId 或缺陷号交给Cursor：

> 按检测报告REV-xxx修复ISSUE-xxx。保持原验收标准，修复后创建新的开发交付，不覆盖旧报告，也不要自行勾选独立验收通过。

修复后将新deliveryId交给Codex复验。CURRENT应能显示缺陷在哪次交付被修复、在哪次检测被关闭。

### 13.6 检测通过

先看“当前版本仍适用”及未覆盖范围。只有相应验收条件都满足，才看到对应条款勾选。用户希望保存版本时另行明确说：

> 审阅本次交付所需文件，按范围有选择地提交；不要带入无关修改。

推送也应明确授权。工具不会因为passed而自动提交或推送。

### 13.7 对话中断、换电脑或状态丢失

同机新对话先读共同规则和CURRENT，然后sync/ack。状态异常先运行doctor和恢复命令，不手删锁或报告。

换电脑需要转移已经审阅的源码及必要协作记录，恢复Unity/.NET依赖后重新doctor；本机锁和缓存不搬运。Git尚未跟踪的文件不会因推送自动出现在另一台电脑，必须单独核对源码集合。

### 13.8 不依赖模型时的手动入口

Cursor必须提供最终可直接复制的命令和PowerShell包装。基本操作只需“查看状态、同步、交付、开始/恢复检测、查看报告”，参数应有清晰提示，不让用户手写复杂JSON。

watch应显示PID/工作目录/运行状态，并提供明确停止方式（前台Ctrl+C或仅终止本工具自己启动的指定PID）。默认不安装开机启动或后台常驻服务。
