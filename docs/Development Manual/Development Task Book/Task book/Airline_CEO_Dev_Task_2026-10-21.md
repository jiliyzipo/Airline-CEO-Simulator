#### 2026-10-22 R1 首轮实测：K01.4 **未通过** → 缺陷已修复，待复测

**报障原话：** 「取消北京—上海：回函没有相关的按钮。」

**实际现象：** 命令台回执为

```text

```

**根因（两处口径撞在一起）：**

| 位置 | 问题 |
|---|---|
| `CeoCommandRouter.Route` ① | 关线判据写成 `HasAny(CloseWords) && (Has("航线") \|\| Has("航"))` —— 要求句子里出现「航线 / 航」。CEO 最自然的说法 `取消北京—上海` **一个都不带**，于是第一道闸直接放行到下一条 |

| `DeptReportLogic.RouteQuery` | 按本线台账写答复件 → `QueueOpsQueryAnswer` 投递**汇报件**，回执还写着「未改动本线运力」 |

也就是说：**同一句「取消」，在关线闸门眼里不算指令，在问句闸门眼里算提问。**
两套词表各认得一半，中间那条缝正好是最常见的说法。

**修复：** 关线判据改为「命中关线动词 **+ 可解析城对**」，不再要求出现「航线」二字；

## 11. K08 · 接管选司读数：现金跑道（2026-10-21 新增）

**动机：** 选司界面的「跑道 X 月」是玩家判断接管难度的主要读数之一。K05 复核时发现它在★3/★4 上退化成现金原值（1200.0 月 / 2000.0 月），等于把「谁现金多」冒充成「谁更耐烧」。

**根因：** `TakeoverWorldBuilder.FillWorld` 写作
`cashRunwayMonths = cash / Mathf.Max(1f, monthlyCost − monthlyRevenue * 0.35f)`。
收入可抵部分覆盖成本时，`Mathf.Max(1f, …)` 把分母夹成 1，`cash / 1` 就成了现金数本身。

**落地：**

- `AirlineProfile` 新增 `monthlyNetBurn`、`cashRunwayUnbounded`；`cashRunwayMonths` 仅在无上限为 false 时有意义（注释写明）。
- 净烧钱 ≤ 0 时置 `cashRunwayUnbounded = true`，`cashRunwayMonths = 0`（不写哨兵数字）。
- 新增 `TakeoverWorldBuilder.RunwayText(profile)` 作为**唯一展示口径**：无上限 → 「无净烧钱」；≥120 月 → 「120 月以上」；否则 `F1` 月。
- `AirlineOverviewUI.Metrics` 改用它；`BuildIssues` 只在有上限时判断 `< 6 月`（避免对不烧钱的航司报「现金跑道告急」）。
- `--routeinventory` 增加断言：每家航司必须二选一自洽 —— 无上限 ⇔ 净烧钱 ≤ 0；有上限 ⇒ `cash / netBurn` 与读数一致（容差 0.05）。

**实测（seed 无关，98 家）：**

| 星级 | 家数 | 净烧钱均（万/月） | 跑道读数 |
|---|---|---|---|
| ★2 | 53 | 20.0 | 24.9 月 |
| ★3 | 33 | 1.0 | 120 月以上 |
| ★4 | 6 | −27.3 | 无净烧钱（6/6） |
| ★5 | 6 | 61.5 | 8.4 月 |

**遗留观察（未改，属平衡裁定）：** ★3 的净烧钱只有 1.0 万/月、★4 全体为负 —— 这是「收入抵减按 35% 计 + 月成本取 `cash*0.08` 与人机数下限」这套粗糙档案模型的结果，不是跑道公式的错。若要让星级真正对应燃钱速度，需要重定 `monthlyCost`/抵减系数，属设计裁定。

## 12. K09 · 星级分档重定：让每档都有真实燃钱速度（2026-10-21）

**为什么必须重定**：K08 修完读数后暴露的不是显示问题，而是**成本模型与账本不同源**。预览用
`max(现金×8%, 机队×4.5 + 航线×2) − 35%×收入`，而接管落盘后 `Apply` 把 `monthlyCost` 写进
`gs.monthlyBurnRate`，维护/租金/人力另算、航线收入 100%（×机组战力 0.85）入账。
两套公式必然对不上：预览说「1200 月」，接手第一周就开始吃紧。

**落地**

1. **预览口径 = 账本口径**（`TakeoverWorldBuilder.FillWorld`）：
   `净烧钱 = 总部开销 + 机队维护 + 月租 + 存量人力 − 航线收入×0.85 − 过渡业务收入`
   - 总部开销：`HqOverhead(fleet) = 80 + 机队 × 2`（万美元/月）——这台值会被 `Apply` 原样写进 `gs.monthlyBurnRate`。
   - 机队维护：`FleetEconomics.MonthlyMaintenance(aircraft)`（含机龄与二手系数）。
   - 人力：`HrEconomics.EffectiveAnnualLaborCostWan(fleet) / 12`（240 万/机/年 = 20 万/机/月）。
   - 收入：`Σ dailyProfit×30 × 0.85 + Σ 过渡 rate×30`，与 `GameState.monthlyRevenue` 同一乘数。
2. **档位 = 寿命**：新增 `TargetRunwayMonths(difficulty)` —— ★2 8 / ★3 6 / ★4 4 / ★5 3 月。
   各档开局现金改为按实测净烧钱反推：**1120 / 1770 / 3140 / 4400 万**（原 500 / 1200 / 2000 / 500）。
   旧现金在真实烧钱速度下只够 3.6 / 4.1 / 2.6 / **0.3** 月 —— ★5 接手当天就死，★2 一开局就在危机线以下。
3. **维护口径收拢为一份**：`FleetManager.MonthlyMaintOf` 自带「机龄 5%/年」硬编码，而
   `FleetEconomics`/UI/运力测算走 `EconomyBalanceParams.MaintAgeUpliftPerYear = 6%` ——
   同一架飞机在 FleetUI 与 FleetSubpagePanel 印两个数、账本按第三个数扣钱。
   现统一为 `FleetEconomics.MonthlyMaintenance`，费率取 **5%**（以账本为准，避免动经济数值本身）。
4. **断言**（`--routeinventory`，全部 PASS）：
   - 每档平均跑道落在目标 ±20% 带内，且逐档严格递减；
   - 每档无「无净烧钱」航司（分档必须真的烧钱）；
   - 净烧钱与跑道自洽（`cash / netBurn`）。
5. **界面**：选司列表行补上「跑道 X.X 月」（原来只有现金，玩家看不出档位差别）；
   概览「财务」页改为「月收入 / 月成本（总部 + 机队维护/租金/人力 拆分）/ 每月净烧钱 · 跑道」。

的派生属性（机组乘数、停飞剔除、过渡业务日结）与预览分叉，离线断言永远看不见。
所以还需要一条「先 Apply、再真推进季度」的运行时链路。

**用例**：`Unity Project/Assets/Tests/PlayMode/TakeoverSolvencyTests.cs`
（`[ValueSource]` 跑 6 个场景：4 档预设 + 批次 A 的 `hub_ZUH` / `hub_NGB`）

**第一版为什么全红（写进留档，避免重犯）**：第一版在推进 `DaysPerQuarter×1440` 分钟后再取现金，
而这一整段**包含季末结算**——还本付息、外部事件、险损都在最后一天一次性发生。于是
「一季实扣 500.9 万 vs 账本预期 398.3 万」被当成账本失真，实际是**测量窗口跨过了季度边界**。
教训：**「每月烧 X 万」只能对着季内逐日计提去量**，一次性项必须分开记。

**第二版的分段**

| 段 | 长度 | 含什么 | 断言 |
|---|---|---|---|
| 季中 | 89 天 | 只含逐日计提（固定成本 / 航线落地 / 过渡业务日结） | 实扣 = 经营烧钱 × 89/30（±10%） |
| 季末 | 1 天 | 还本付息、外部事件、险损、联盟 | 只断言不 NaN、跨季成功、不即死；差额与新增日志全部打印 |

其余断言：

| 断言 | 含义 | 失败说明什么 |
|---|---|---|
| 经营烧钱 ≤ 预览经营烧钱 × 1.02 | 账本烧钱**不得**高于预览 | 界面承诺的跑道比真实更紧（玩家被误导） |
| 经营烧钱 ≥ 预览 × 0.70 | 也不能低太多 | 两边已不是同一套成本项，读数失去参考价值 |
| 预览月均还本付息 = 落盘贷款月供（±0.5） | 偿付项取对了 | 跑道把债务压力算错 |
| `cashRunwayMonths = cash / monthlyNetBurn` | 跑道与净烧钱自洽 | 读数与公式脱钩 |

`ledgerBurn` 在测试内按 `monthlyBurnRate + 维护 + 租金 + CEO + 运行岗 + 存量人力 − 航线收入 − 过渡收入`
现场求和，逐项对齐 `GameState.EffectiveMonthlyBurn`（但**不去负**，因为跑道公式需要带符号净值）。
若将来给 `EffectiveMonthlyBurn` 增删成本项而忘了改这里，断言会立刻失衡 —— 这是刻意的耦合。
每个场景还会打印每条航线的**执飞资格**（机号 / 班次 / 班期 / 是否持续性停飞），用来区分

**落地**

**已定位的一处口径分歧（K10 第二轮：已确认并修复）**：落盘后的航线被
`CloneRoute → SyncFlightsFromPrimary` 压成「单班/日」，`flight.dailyProfit = GrossDailyProfit`
（即 **净日利润 + 航线周期固定成本**）；`LiveClockSimulator.Land` 每趟付一半，去程 + 回程 = 一个毛贡献。
而 `ApplyDailyFixed` 只扣总部/维护/租金/人力，**从不扣 `RouteData.FixedDailyCostWan`**。
于是「实际现金入账 = 毛贡献」而 `monthlyRevenue` 是「净日利润」——预览把烧钱算**高**了
Σ `FixedDailyCostWan`。远程网络（★4/★5）此项最大，故星级越高偏差越大。
修复：`Land()` 每航段 `pnl -= FixedDailyCostWan / FlightCount × 0.5`，与 `pnl *= 0.5f` 同口径。

### 18.3 D2 第二步已实施：★2 改为连续标度（2026-10-22）

**裁定**（用户，2026-10-22）：连续标度 —— 机队/航线/现金随客流连续变化，**跑道统一 8 月，★2 仍是一档**。

**为什么不做 ★2a/★2b/★2c**：本作的「档位」就是跑道
（`TargetRunwayMonths` = 8/6/4/3 月）。子档只改规模不改跑道 → 时间压力完全相同，只是给同一难度贴三个标签；
子档连跑道一起改 → `difficulty` 要扩到 6~7 个值，而 `TakeoverWorldBuilder` 里 `<=2 / ==3 / ==4 / >=4`
这类分支有 8 处（机组缺员、四种过渡业务、宽体比例、机队机型、利率），每处都要重新裁定语义，
外加 UI 标签与 K10 跑道带整轮重解。连续标度以**一档之差的工作量**解决克隆问题。

**改了什么**（`PresetAirlines.ScaleStartup`，仅对 `stars <= 2` 生效）

```text
u = clamp01((pax − 3) / (40 − 3))      // 客流归一化，40 = ★3 下界
机队 = 2 + round(u × 6)                 // 2 → 8 架
航线 = 1 + round(u × 4)                 // 1 → 5 条
机队 ≥ 航线 + 1                         // 过渡业务要抽 1 架，见 BuildFleet
现金 = 1044 + 193 × 机队                // 万元
```

**现金为什么要拟合而不是拍**：第一版写成 `1434 × (机队/3)^1`（现金与机队成正比），实测跑道
**5.54~11.16 月（均值 9.10）**，落差过大。原因是烧钱增长慢于机队 —— 机队 2→8 只让净烧钱涨 2.07 倍
（168.6→348.9），现金却涨了 4 倍。实测「运营烧钱 B（= 净烧钱 − 还本付息）」与机队近似线性
（2→148 / 3→166 / 4→186 / 5→194 / 6→231 / 7→268），存在**固定截距**（总部开销 80 万固定、
租赁与保费按机队摊），再按闭式解 `cash = 8B/0.8275 ≈ 9.67B` 折算，得 `1044 + 193×机队`。
