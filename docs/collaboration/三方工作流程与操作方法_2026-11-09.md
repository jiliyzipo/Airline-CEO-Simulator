# 用户、Codex、Cursor 三方工作流程与操作方法

版本：v1.2 · 生效日期：2026-11-09（补充技术裁决、操作请求与卡片边界） · 适用项目：Airline-CEO-Simulator

## 1. 这套流程解决什么

用户用日常语言、截图、操作现象和期望效果提出需求，不负责把问题翻译成技术方案。Codex 负责理解意图、形成规范和任务、与 Cursor 对齐方案、监督实现是否偏离；Cursor 负责在约定范围内开发、自测与反馈；用户最终在 Unity 中目测和操作，判断效果是否符合自己的意思。

用户不需要先判断问题属于 UI、数据还是业务逻辑，也不需要亲自裁决两个代理之间的技术争议。

这是项目协作约定，不是自动拦截 Cursor 修改的程序。默认由用户转交任务与反馈；没有真实工具回执时，两端不得声称已自动发送、收到或持续监控对方。

## 2. 三方分工与决定权

### 用户：提出想法，确认产品效果

- 说明哪里不对、希望变成什么；截图、口语和举例均有效。
- 对游戏整体规划、玩法方向及由此产生的产品取舍保留最终决定权；专业技术路线和实现选项全权委托 Codex 选择，不要求用户理解或逐项确认。
- 在 Unity 中按简短步骤目测、点击和验证体验；可以只回复“符合预期”或指出仍有问题。
- 决定何时统一检测、阶段收口，以及是否提交或推送。
- 不承担源码分析、测试命令编写或反复整理代理报告的责任。

### Codex：需求负责人、技术把关与独立审查

- 先确认用户真正要改变的行为，再形成明确、可验证的任务。
- 优先读源码、现有规则和关联记录，区分截图中可见事实、原因推测和已验证结论。
- 给 Cursor 可直接执行的指令，包括目标、允许改动、保护边界、验收条件与交付要求。
- 审查 Cursor 的方案、代码差异与证据，发现偏离时提出具体修正，不把技术争议转嫁给用户。
- 对用户目标内的专业技术路线和实现选项全权决策，承接 Cursor 的技术选择请求；只有涉及游戏整体规划或玩法取舍时，才用通俗语言征询用户意见。
- 默认不代替 Cursor 修改生产代码；用户另有明确授权时再调整角色，并区分自测与独立验收。

### Cursor：实现、自测与真实反馈

- 阅读任务及当前协作记录，以自己的身份同步和确认已读。
- 简短确认理解的范围；有技术异议先向 Codex 提出证据和替代方案，不能先做后报。包括使用 DeepSeek 在内的任何模型，遇到专业选项均交 Codex 裁决，不向用户弹出要求选择技术方向的确认框。
- 在已确认范围内开发并自测，不擅自增加玩法、调整参数、迁移存档或顺带重构。
- 如实报告改动、验证结果、未覆盖项和用户目测入口，不将“编译成功”写成“效果验收通过”。
- 不能代写 Codex 的独立验收结论，也不能以用户身份批准设计。

## 3. 日常闭环

1. **用户提出问题。** 发给 Codex：“这里不对”“我点完没反应”“希望这个页面更清楚”，附截图或操作说明即可。
2. **Codex 理解并落任务。** 先用简短文字复述目标，查相关资料，输出任务单。能从上下文查清的内容不反复询问；确实影响结果时才问关键问题。
3. **Cursor 确认边界。** 简单修复简短确认后直接按任务执行；有分歧时回给 Codex。Codex 与 Cursor 对该任务达成共识、且任务单标明“可以开发”后，才能开始该范围的实现。
4. **Cursor 开发与自测。** 遇到超范围依赖先报告；已明确的独立部分可以继续，不把局部分歧扩大成全项目停工。
5. **Codex 审查。** 对照任务看代码和证据，说明已满足什么、仍缺什么。偏离规范时退回具体问题；没有实质缺口时不新增无关要求。
6. **用户 Unity 目测。** Codex 给出打开位置、操作步骤和预期结果；用户无需阅读源码或技术报告。
7. **反馈并继续。** 不符合预期就沿用同一任务补充、修复；符合预期则记录目测结果，可继续下一项。日常完成不自动触发阶段收口。

默认仍由用户在两个聊天间转交文本或文件。双方应在项目内保存同一任务和反馈，减少重复粘贴；共享文件存在不等于对方已经阅读。

## 4. 任务单：Codex 每次交给 Cursor 的内容

任务单可存放于 `docs/dev-exchange/`，使用日期、主题和修订号命名；小修可先用一段完整文本下达，再补入阶段记录。无需为每次小修生成长篇 HTML。

```text
任务：日期 + 简短名称 / 修订号
用户目标：用户想看到或操作到的结果。
现状与复现：从哪个页面、什么前提、怎样操作、实际发生什么。
目标行为：修改后在相同场景应发生什么。
范围：要改的行为和允许涉及的模块；明确必须保持不变的行为。
实施状态：只分析 / 等双方确认 / 可以开发；写明已确认的子范围。
验收：可逐条判断的正确结果、必要边界和相关回归。
证据：需要真实执行的验证；模拟、截图和未测项分别说明。
目测：给用户的最短 Unity 操作步骤与预期结果。
交付：改动清单、自测结果、已知缺口；不自动收口或提交。
```

范围优先按行为约束，不把初步列出的文件路径当成绝对穷尽清单。发现必要的新文件或调用链时说明理由；若涉及新的产品行为、数据含义或持久化规则，须先与 Codex 对齐。

用户后续纠正优先于旧任务描述。Codex 更新同一任务版本，Cursor 确认新版本；不得一边按旧规范开发、一边声称执行了新规范。重大设计变化按现有项目要求回填设计依据和决策记录。

## 5. 哪些事情直接推进，哪些先讨论

- **日常小修：** 目标明确、影响可逆、保护边界清楚，按任务直接推进，不重复请用户批准每个实现细节。
- **设计或架构变更：** 涉及玩法、经济参数、容量口径、存档、跨模块重构等，Cursor 先给最小方案、影响和回退，Codex 审查后确认可实施的范围。
- **产品取舍：** 只有涉及游戏整体规划或玩法方向时，由 Codex 用通俗语言说明玩家将看到或体验到的差别，再征询用户意见。技术复杂、方案较多、涉及架构或存档，本身不构成要求用户选择技术路线的理由；Codex 应在既定产品目标内作出技术决定。既有操作授权、玩家数据保护和提交/推送规则仍然适用。
- **单纯报告与提案：** 文档中的“建议”“可执行指令”不自动成为开发授权，以最新用户指示及已确认任务状态为准。

达成共识要有明确范围和版本，不能仅凭“我让步了”或“意见都接受”认定验证完成。已经关闭的争议不因措辞反复开启；同一个证据缺口应给出可执行的补证条件，不无限追加要求。

### 5.1 专业选择请求：先交 Codex，用户不代选

本条为用户 2026-11-09 的明确委托，适用于 Cursor 使用的全部模型，包括 DeepSeek。数据库或数据结构、接口设计、算法、缓存、性能、测试工具、兼容策略、技术迁移与重构路线等专业选项，由 Codex 全权判断，不要求用户在技术弹框里选择。

1. Cursor 发现“有诸多选择，需要确认方向”时，先查已确认任务；已有决定则沿用，不重复询问。
2. 尚未决定的专业问题，应整理成给 Codex 的技术决策请求：当前目标、必须选择的原因、候选方案与影响、已有证据及推荐方案。不把长串术语和选项直接交给用户裁决。
3. 暂停依赖该决定的部分，继续不依赖它的已确认工作；不得以局部选择为由停掉全部任务。
4. 默认仍由用户转交这段请求；如果已经弹出确认框，用户可以只转发文字或截图，不必理解选项或代替 Codex 点选。
5. Codex 给出明确选择、简短理由、执行边界和验证要求，形成可直接回传 Cursor 的指令，不再把同一技术选择转回用户。
6. Cursor 按决定执行；若有新的不可行证据，再反馈 Codex。双方技术分歧继续由双方解决，不交用户做技术仲裁。
7. 如果技术方案实际改变游戏整体规划或玩法，Codex 先翻译成玩家能理解的问题，再请用户决定产品方向；方向明确后，剩余技术路线仍由 Codex 选择。

技术决策请求的简短格式：

```text
交 Codex 裁决，不要求用户选择技术方案。
当前任务与目标：
必须决定的问题与现有约束：
候选方案、影响与推荐：
证据及缺口：
等待期间可继续的工作：
```

Codex 回复应写成：“选择……；理由……；允许修改……；必须保持……；验证……；Cursor 可据此继续……”。决定记回同一任务版本，不另建相互矛盾的口径。

向用户征询玩法时，应问“你希望玩家能自由改航班，还是需要先经过审批？”这类体验问题；不要问“选状态机 A 还是事件模型 B？”。必要的操作权限或缺失信息仍可具体请求，但不能把它包装成要求用户选择专业技术路线。

### 5.2 选项卡片、操作请求和记录分工

- 技术路线、是否补某类测试、证据等级及验证先后顺序，由 Codex 决定。Cursor 不要求用户再确认本授权，不得以“用户不确认，下次仍会误弹框”作为继续执行的条件。
- 只有整体规划或玩法方向确需用户作产品选择时，才由 Codex 用通俗语言提供选项卡片；Cursor 将问题反馈 Codex，不自行把专业选择题发给用户。
- 提交/推送、阶段收口按用户主动指示执行，不在每次开发后例行弹框催问。保存关闭 Unity 属于具体操作请求：只有检测确实被编辑器占用阻断时，才说明原因请用户操作，不把它包装成“要不要做测试”的技术选择。工具自身要求的真实权限审批仍须遵守。
- `Place` 修复、缓存设计、机场身份迁移等不因玩家可能感知就自动变为玩法取舍。恢复既定行为或保持外部行为不变的技术实现由 Codex 决策；新增机场经营玩法、时刻重新分配、经济规则变化等实质产品变化，才按具体影响征询用户。
- 人读任务单、方案与裁决放 `docs/dev-exchange/`，开发阶段记录仍可放 `docs/handoff/`；机器任务状态走协作工具。正式状态以工具生成的 `CURRENT.md` 及对应记录为准，任务单关联机器任务编号，不手工维护第二套状态。
- 证据不齐时可以先交 Codex 审查，同时如实列缺口；不能将“可以审查”写成“已经验收”。用户未要求阶段收口时，不因补测或审查自动生成 DEL/REV。

## 6. Cursor 完成后怎样反馈

```text
任务及版本：
实际实现：改了什么，用户能看到什么变化。
改动范围：文件、核心行为及是否发现超范围依赖。
开发自测：实际入口、场景、结果与可复核输出位置。
未测或已知问题：特别说明模拟、真实 C#、Unity 测试各覆盖什么。
用户目测：页面入口、步骤、预期结果、是否需要重启或新局。
状态：已实现待 Codex 审查 / 需修正 / 待用户目测。
需要用户做什么：没有则写“无”。
```

交付先提供简洁结论与必要证据，不用长报告替代代码正确性。不凭测试脚本自行生成的“合法”标签证明真实申请链路合法。

## 7. Codex 如何监督不跑偏

Codex 审查四件事：是否实现用户目标、是否守住范围、是否保护相关旧行为、证据是否来自实际执行。

发现问题时写清“具体触发条件 → 实际结果 → 应有结果 → 必须修到什么程度”。问题应落到文件、函数、复现或数据，避免只说“不合理”“再完善”。同一反馈中区分必须修复、可后续改进与仅供参考，不把建议全部升级成阻断。

常规代码审查和针对性验证可以随任务进行，不等于阶段收口。正式独立验收必须使用对应 DEL 的固定快照和项目协作工具，不能把活动工作区的局部结果冒充整阶段通过。

不要为满足截图而伪造数据、隐藏异常、只改文案掩盖逻辑错误；不要因显示位移而悄悄改写玩家持仓。测试规模与改动风险相称，不为低影响文字微调增加无意义测试。

## 8. 用户目测与测试证据如何区分

以下结论分别记录，不能互相替代：

- **Cursor 开发自测：** 实现者验证过指定场景。
- **Codex 审查：** 已检查指定版本的代码、范围及证据，说明实际覆盖程度。
- **用户目测：** 用户确认页面、操作或体验符合预期。
- **正式独立验收：** 用户要求统一检测后，Codex 对 DEL 执行正式检测并形成 REV。

用户目测正确不自动证明隐藏账务、存档或容量守恒正确；机器回归通过也不自动证明视觉与交互符合用户心意。截图能证明可见状态，不能单独证明数据根因。未执行、环境阻断或没有样本都明确标注，不能记作通过。

## 9. Unity 操作与日常保护

用户拥有当前 Unity 编辑器和存档的控制权。测试优先使用隔离副本、独立场景或测试夹具，不覆盖玩家数据。不强杀 Unity、不删工程锁、不自动关闭用户编辑器。若指定检测入口因占用不能执行，先完成其余工作，再明确说明需要用户保存关闭哪个编辑器及原因。

不得每次修复都要求用户新建存档；确需新局、迁移或重启时说明原因、保护旧档和回退方式。界面小修不要顺带改变业务数值，容量和存档调整不要与视觉改动捆绑放行。

## 10. 阶段收口保持原约定

日常：Cursor 开发、自测、记录 → Codex 审查 → 用户目测 → 继续下一任务。不得自动运行 `stage-close`、生成 DEL、commit 或 push。

只有用户明确说“统一检测 / 阶段收口”时，Cursor 才汇总阶段任务与验收条件，执行 `stage-close` 生成 DEL 并预检；Codex 再执行 `stage-review`。失败则修复并生成新 DEL，历史记录不覆盖。预检是开发自测，不是独立验收。提交和推送由用户另外决定。

正式协作状态继续以 `docs/collaboration/CURRENT.md` 和工具记录为准，本文件不另建一套机器状态。

## 11. 用户以后怎样说

- 提问题：“这张截图里，我点了申请，但列表没变化。我想成功后立刻看到结果。”
- 看效果：“Cursor 做完了，请先替我检查，再告诉我在 Unity 里怎么试。”
- 继续修：“还是不对，数字变了但颜色没变，按原任务继续修。”
- 确认目测：“这个效果符合预期，继续下一项。”
- 集中验收：“这段时间的修改统一检测，阶段收口。”
- 转交专业弹框：“Cursor 又问技术方向了，这是弹框内容，请你直接选好并给它指令。”

这些是示例，不要求用户套模板。技术信息缺失由 Codex 和 Cursor 补查。

## 12. 发给 Cursor 的启用说明

> 请阅读 AGENTS.md 和 docs/collaboration/三方工作流程与操作方法_2026-11-09.md。从现在起，用户向 Codex 描述问题和期望，由 Codex 形成任务并监督范围，你负责实现与开发自测。收到任务后简短确认；专业技术选项交 Codex 全权选择，不向用户弹框要求选择技术方向；只有整体规划或玩法取舍由 Codex 用通俗语言征询用户。有技术异议先反馈，双方对该范围达成共识且任务标明可以开发后再实施。不得扩大范围或把待验证方案直接上线。完成后提供改动、自测、未测项和 Unity 目测步骤，交 Codex 审查，再由用户目测。日常不自动收口、生成 DEL、提交或推送。请先确认已读及是否有冲突，不要因此启动新的生产代码改动。

本流程依据用户 2026-11-09 的明确要求建立。最新用户明确指示优先于历史文档；发现冲突应指出并更新规范，不得以旧文档覆盖用户的新要求。
