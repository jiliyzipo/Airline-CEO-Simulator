# P31 · T04.8 现金桥对账（结构性缺陷 ②）· 开发记录（2026-10-27）

## 1. 背景：一条被「别当 oracle」掩盖的账目缺口

`docs/handoff/残余七项审计_2026-10-24.md` §8.5 从 60 组合矩阵里读出两个结构性问题，其中第 ② 条：

> `TotalNetProfit` 不含 IRROPS 现金冲击，所以「净利」和「期末 − 期初」对不上。
> 全服务/繁荣三档：期初 625/500/400、净利均 1248、期末 1853/1723/1616，
> `期末 − 期初` = 1228 / 1223 / 1216，比 1248 少 20 / 25 / 32，
> 恰好是 −25 万 IRROPS × 0.80 / 1.00 / 1.25。

当时的处理是一句免责声明：「矩阵是情景投影，不是台账」。这句话没说错，但它把**一个可以算清的差额**
变成了**一个不许追问的黑洞**。任何拿这张表做现金对账的人都会撞上「净利 ≠ 现金变化」，
而报告只说「别信它」。

T04 的验收标准第一条是「**关键账目能逐项解释**」。一张说不清差额的矩阵，恰好不满足这条。

## 2. 查实的现金流路径

逐行读 `AirlineYearSimulator.RunFiscalYear`，年度内动现金的地方只有四处：

| 位置 | 行 | 动作 | 是否进损益 |
|---|---|---|---|
| 月度经营 | `cash = pnl.CashEndWan` | `cashStart + net`，`net = revenue − totalCost` | ✅ 进（`NetProfitWan`） |
| IRROPS 冲击 | `cash += irropsDelta` | 第 6 个月一次性，按难度 0.80/1.00/1.25 缩放 | ❌ 不进 |
| 跑道告急贷款 | `cash += loanPrincipal` | 一次性全额放款 | ❌ 不进 |
| 等额本息月供 | `cash -= loanMonthlyPay` | 本金 + 利息 | ❌ 不进（**利息也不在 `net` 里**） |

第四行是最容易漏的一点：`SimulateMonth` 的 `net = revenue − totalCost` **不含利息**，
利息是在月度循环里事后 `cash -= loanMonthlyPay` 直接扣的。所以「净利」其实是**税前息前**口径，
只是旧代码没这么写。

## 3. 等式

设：`N` = 12 个月净利累加、`I` = 已付利息、`R` = 期末未偿本金。

还款总额 = `Σ loanMonthlyPay` = `I + (放款本金 − R)`
现金变动 = `N + IRROPS + 放款本金 − 还款总额`
　　　　 = `N + IRROPS + 放款本金 − I − 放款本金 + R`
　　　　 = `N + IRROPS − I + R`

即：

```
期末现金 = 期初现金 + 净利 + IRROPS 现金冲击 − 已付利息 + 期末未偿贷款本金
```

两个直觉解释：

- **未偿本金要加回**：放款是一次性全额进现金，只还了一部分，没还的那部分仍躺在账上 ——
  它是现金，不是利润。
- **利息单列**：月供里本金部分已在「未偿本金」项自然抵消，只有利息是净流出。

## 5. 验证

**单情景（最小航司，`dotnet run`）**

```
Opening cash : 500.0
Closing cash : 1707.9
Net profit   : 1232.9
Cash bridge  : 现金桥 500.0 期初 + 1232.9 净利 -25.0 IRROPS −0.0 利息 + 0.0 未偿本金
               = 1707.9，实际 1707.9，残差 0.00 → 对账通过
```

**60 组合（`dotnet run -- --stress`）**

```
现金桥对账  : 60/60 组合残差 ≤ 0.5 万（最大 0.03）
```

最大残差 0.03 万 = 300 元，来源是 `cash = pnl.CashEndWan` 每月 `Round2` 的累计（12 × 0.005 × 若干项），
不是漏记。有贷款的组合也全过，例如：

| 难度 | 航司 | 宏观 | 净利 | IRROPS | 利息 | 未偿本金 | 期末 | 残差 |
|---|---|---|---|---|---|---|---|---|
| 简单 | 低成本 | 滞胀 | −1122 | −20.0 | 26.0 | 161.4 | −381 | −0.02 |
| 简单 | 全服务 | 滞胀 | −500 | −20.0 | 6.7 | 412.8 | 511 | 0.00 |

第一行手算：期初 625 + (−1122) + (−20) − 26.0 + 161.4 = −381.6 ≈ −381 ✅

**矩阵数值零变化。** 全服务/繁荣仍是 1248，与 10-24 审计记录逐位一致 —— 本次是**纯加法**，
没有动任何系数、没有重录基线。

**编译**：`dotnet build tools/balance` 0 error；`node tools/semcheck/run.js`
`errors=0 (raw=0)` / `tests-asm: errors=0` / `enc: errors=0`。

## 8. 闸门：新增 `balance` profile

原来这套校验只在手动 `--stress` 里跑，`tools/collab/config.json` 没有对应 profile，
等于「改坏了也没人拦」。本次一并补上：

| 项 | 内容 |
|---|---|
| 新命令 | `dotnet run --project tools/balance -- --bridgecheck` |
| stdout | **只印一行**机器结果 JSON：`{"assertionsTotal":60,"assertionsFailed":0,"assertionsSkipped":0,"worstResidualWan":0.03,"toleranceWan":0.5}` |
| stderr | 人读摘要（`现金桥检查：60/60 对账通过`）+ 失败明细 |
| 退出码 | 只在「有组合对不上」时非零；**不因**破产/告急组合数量非零 |
| profile | `balance`，`resultKind: json` |
| 选择规则 | `stage.selectProfile`：`^tools/balance/` → `balance`，排在 `.cs → compile` **之前** |

为什么必须排在 `compile` 之前：`compile` 跑的是 `tools/semcheck`，它编译的是 Unity `Assets/Scripts`，
**根本不编译 `tools/balance`**。若让 `tools/balance/*.cs` 落到 `compile`，闸门就没碰到被改的代码 ——
「绿了但没验」比红灯更糟。

为什么 `--bridgecheck` 不复用 `--stress` 的退出码：`--stress` 有 15 个告急组合是**预期设计**，
它必须返回 1；现金桥对账必须返回 0。两件事混在一个退出码里，就会让「预期内的红」掩盖「意外的红」。

验证：

```
$ dotnet run --project tools/balance --no-build -- --bridgecheck
现金桥检查：60/60 对账通过（容差 0.5 万，最大残差 0.03 万）
{"assertionsTotal":60,"assertionsFailed":0,"assertionsSkipped":0,"worstResidualWan":0.03,"toleranceWan":0.5}
exit=0
```

`node tools/collab/tests/run-all.mjs` → **collab 179/179**，`stage.test.mjs` T11 增两条断言
（`tools/balance/Sim/CashBridge.cs` 与 `tools/balance/README.md` 都必须选到 `balance`）。
