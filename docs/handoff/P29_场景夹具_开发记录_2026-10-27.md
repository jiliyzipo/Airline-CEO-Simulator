## 3. 刻意不做的事

- **不写存档**。夹具只改 Play 模式的内存态，不碰 `PlayerPrefs`，退出 Play 即恢复。
  这样不存在「改坏了怎么回滚」，也不需要动槽位快照。
- **不做「撤销」**。逆向恢复要还原月预测、机组缓存、地面判定等一整套派生量，
  做不干净反而制造假象；要恢复就重进 Play。
- **已经处于目标状态时返回 false 并说明原因**，不假装「又生效了一次」。
  手测记录里最怕的就是这种假成功。
- **不改产品玩法数值**。夹具只推动状态，不动难度、票价、成本。

## 6. AI 触发桥（让夹具能在后台自测）

### 6.1 为什么需要

`tools/regression/RunUnityTests.ps1` 有两道硬闸：只要有任何 Unity 进程存在就 `throw`，
且只认 `companyName: AirlineCEORegression` 的隔离导出（`DevelopmentPlaySmoke` 里也有同一道闸）。
这两道闸是**对的** —— 它们保证测试不会碰玩家的存档与 PlayerPrefs。
但代价是：Unity 代码改完后，Cursor 侧在用户关掉编辑器之前**完全无法自测**，
只能"改完等你点一下"。

桥走的是第三条路：**在当前工程、当前代码上**，只做用户本来会手动点的那件事。

### 6.2 协议

请求方 `tools/regression/ai-run.mjs`：

```
node tools/regression/ai-run.mjs --suite scenario-fixture [--timeout 180]
```

1. 写 `out/ai-trigger/<id>.json`（`{"id","suite","requestedAt"}`）；
2. 编辑器侧 `RegressionTriggerBridge`（`EditorApplication.update` 每秒轮询）取走并执行；
3. 结果写 `out/ai-result/<id>.json` + 同名 `.log`（本次 Console 捕获，最多 400 行），
   另有稳定的 `latest.json`；
4. 触发文件移入 `out/ai-trigger/done/<id>.<status>.json`，不会被重复执行。

`out/` 已在 `.gitignore` 里，因此请求与结果都不会污染工作区。

### 6.3 安全边界（硬性）

| 边界 | 实现 |
| --- | --- |
| 不能变成"编辑器里执行任意代码"的后门 | 只认 `RegressionTriggerBridge.Suites` 白名单；未知 suite 回 `refused` |
| 不在游玩途中跑 | `isPlaying \|\| isPlayingOrWillChangePlaymode` → `refused`，不动实时状态 |
| 不在编译/导入半途跑 | `isCompiling \|\| isUpdating` → 触发文件留在原地，下一轮再试 |
| 不写存档 | 桥只调用被调方的静态方法，自身不碰 PlayerPrefs 与存档槽位 |
| 可一键停用 | `out/ai-trigger/OFF` 文件；或菜单 `AirlineCEO/AI 触发桥/启用或停用` |

### 6.6 已知副作用（如实写明）

回归会在**当前打开的场景**里临时创建 GameObject 并销毁。这不损坏数据，
但可能把场景标记为已修改；结果 JSON 里有 `scenePath` / `sceneDirty` 供核对。
手上有未保存的场景改动时，建议先保存再让自动化跑，免得分不清哪个改动是自己的。

## 7. 一次真实的预检失败（记下来，别重犯）

第一次 `stage-close` **预检未通过**（`DEL-20261027024555-4ff815`），
报告只有一句 `machine result reports 2 failed assertion(s)`。快照内 `semcheck_report.txt` 给的真相是：

```
Assets/Scripts/Editor/AccountingScenarioRegression.cs(4,18): CS0234
命名空间"AirlineCEO"中不存在类型或命名空间名"Data"
```

### 原因

`semcheck.csproj` 的编译输入是：

```xml
<Compile Include="../../Unity Project/Assets/Scripts/**/*.cs" />
<Compile Include="../../Unity Project/Assets/Tests/**/*.cs" />   <!-- semcheck_tests -->
```

也就是说它**要整棵 `Assets/Scripts`**。而我在任务定义里把 `snapshotRoots` 写成了
`Assets/Scripts/Editor` + `Assets/Tests/EditMode` —— 快照只导了 `Editor` 子目录，
`Data` / `Logic` / `Systems` / `UI` 全不在里面，于是快照内编译必然全红。

**本机跑 `semcheck` 是绿的，因为工作区是完整的。** 这类「本机绿、快照红」的失败，
只有预检能抓到，正好验证了预检存在的价值。

### 修法

`snapshotRoots` 改为编译真正需要的四个根：

```
Unity Project/Assets/Scripts   Unity Project/Assets/Tests   tools/semcheck   tools/regression
```

这不与 S17 冲突：S17 之后，已交付任务的 freshness 走 `scopePolicy='changed-files'`
（按 `files.workspaceChanges` 比对），**不再拿 snapshotRoots 当比较基线**。
所以根的宽窄只影响「快照装不装得下编译输入」，不再让任务永久 stale。

重跑后 `DEL-20261027024816-5a1cf9` 预检通过。

### 教训

任务定义里的 `snapshotRoots` 不能按「我改了哪些目录」写，要按「验证需要读哪些目录」写。
compile profile 尤其如此：它会在快照里重新编译，缺一个根就整片 CS0234。
