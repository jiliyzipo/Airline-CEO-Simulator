## 0. 一句话结论

本作**物理层早已等价实现**了资料里的核心主张（一槽 = 一对、缺一端飞不了、到达 = 离场 + 轮挡）；在途实现已把「到港时刻」落成 `SlotHolding.arrTime` 字段并把 `kind`（DEP/ARR）透到了申请单与排班闸门。
**真正没做的是下面这几件事**（完整清单与修法见 §4 的 G1–G7，这里只列前三件真正会咬人的）：

1. **到港端的容量从未被校验** —— `arrTime` 只被记下来，没有任何一处拿它去问「那一刻的池子还有没有余量」。所以资料里最核心的那个场景（「PEK 08:00 有，但 SZX 11:15 已满」）**游戏现在判不出来**。
2. **二级市场的单边交易只做了一半** —— `SlotMarketListing.kind` 已加、买入侧已通（`Roll` 会摇出 ARR 挂牌、`Buy` 会按 kind 落账），但**卖出侧**（`ListOwn` 不写 kind、`HoldingIndexOf` / `IsListed` 不按 kind 定位）仍是单向的。
3. **池的消耗口径自相矛盾** —— 容量接口按「每端各 = 对数」设计（`SlotCapacity(kind)`），但余量接口 `SlotsAvailable(kind)` 是 `_ = kind`、用「对数 − 全部持仓」。同一物理结果（一次停留），记成一条成对持仓消耗 1，记成 ARR+DEP 两条持仓消耗 2。这会让「分开买」比「一起买」贵一倍。

另有四件次要但必须一起排期的：**G4** 申请单尚未按方向做单号/原子性、**G5** 界面没有任何到港维度（用户第 2 条的可视部分）、**G6** 「有去无回」既无表达也无出口、**G7** 80% 使用率台账只记离港一侧。

### 3.1 什么场景走哪条（判据落到函数）

| 场景 | 判据 | 走哪条 |
|---|---|---|
| 两端都缺、池有余量、不急 | `EndStatusKey == "missing"` 且 `CanApplyEnd` 为真 | ① 成对提交，7/18 天 |
| 该刻已有空闲持仓 | `EndStatusKey == "free"` → `ReserveSlot` 绑定 | 直接绑，不办手续 |
| 本线在该站已有槽，仅时刻滑点 15~240 分 | `TryTimeChange` 且 `poolRoom > 0`（`SlotChangeWindowMinutes=240`） | ③ 改时，7 天 |
| 池已满但仍要那一刻 | `EndBlocked` | ② 二级市场（唯一能突破池容量的渠道） |
| **一端满、另一端空** | 离港 `EndBlocked`、到港 `EndReady/EndApply`（或反之） | **先买瓶颈端再申请另一端**（拆单边后最重要的新策略，现有实现判不出来，见 G2） |
| 槽闲置但不想失祖父权 | `leasedUntilTurn == -1` 且未绑定 | ④ 租出 |
| 两端不均（一端祖父掉了） | `SlotUsageLogic.Evaluate` 逐系列使用率 | 先改时拉齐，再考虑放弃 |

### 3.2 拆单边后新增的铁律

**「先探瓶颈端，再付出另一端」**。成对持仓时代这条自动成立；一旦允许单边，先申请宽裕端再发现瓶颈端批不下来，就是一张半废票，沉没的是 7~18 天工期。
所以 §4 的 G4 规定：**协调池默认成对原子提交**（一端不批则两端都不批），单边只允许玩家在二级市场**主动**购买。

## 4. 这次要改什么（缺口清单 G1–G7）

> 本节按磁盘现状写。每条给：症状 → 根因（文件:行）→ 精确修法 → 新增回归。

### G1【P0·必须】池消耗口径自相矛盾，分开买比一起买贵一倍

**症状**
同一个物理结果（一次停留），两种记法消耗的池容量不同：

| 记法 | 落账 | 消耗池 |
|---|---|---|
| 成对买：一张申请单带 `arrClock` | 1 条 `DEP` 持仓（`arrTime` 有值） | 1 |
| 分开买：一条 `ARR` + 一条 `DEP` | 2 条持仓 | 2 |

玩家按用户第 2 条「单独购买到港」，反而被多扣一倍容量。

**根因**
`Logic/RoutePermitLogic.cs`：

```csharp
public static int SlotsAvailable(GameState gs, string airport, int band, string kind)
{
    _ = kind;
    int left = SlotPoolCapacity(airport, band) - SlotsHeld(gs, airport, band);
    left -= IndustryAirlineLogic.IndustryHeld(gs, airport, band);
    ...
}
```

而同一文件的 `SlotPoolCapacity(airport, band, kind)` 与 `Data/AirportCatalog.cs · SlotCapacity(code, band, kind)` 的注释明确写着「**两个池各取同一个数**（= 原对数），一个停站各取一条，能飞多少班与拆分前一致」。同一个类里两处注释互相矛盾。

`SlotsAvailableAt(kind)` 与 `IndustryHeld(kind)` 同样是 `_ = kind`。

**修法（推荐「同值双池」落地，不需要新增 `pairId`）**

1. `SlotPoolCapacity(a,b,kind)` 保持现状（= 对数）。✔ 不改
2. 新增 **池消耗计数**（不是展示计数）：

```csharp
/// 该机场该时段在 kind 这个池里的**消耗条数**。
/// 规则：一条 DEP 持仓（无论有没有 arrTime）同时消耗 DEP 与 ARR 各 1（它就是一对）；
///       一条 ARR-only 持仓只消耗 ARR 1。
/// 这样「成对买」与「分开买」对池的消耗完全相同 —— 这是 G1 的判据。
public static int PoolUse(GameState gs, string airport, int band, string kind)
```

3. `SlotsAvailable(a,b,kind) = max(0, SlotPoolCapacity(a,b,kind) − PoolUse(a,b,kind) − IndustryHeld(a,b,kind))`
4. `SlotsAvailableAt(clock, kind)` 同样改用逐刻的 `PoolUseAt(clock, kind)`
5. `IndustryHeld(a,b,kind)` 去掉 `_ = kind`，哈希键加方向后缀（`"occ:" + kind`）。否则两个方向的 AI 占用会拿到同一个随机数，玩家永远碰不到「一端满一端空」——而那是 §3.1 最后一行要教的策略。
6. `SlotsHeld` / `SlotsHeldOfKind` / `SlotsHeldAt` 降级为**仅展示**，函数注释里写明「判余量请用 `PoolUse*`」，防止下一个人再踩。

**守恒自检**（写进回归）：`PoolUse(kind=DEP) + PoolUse(kind=ARR)`，在「全部成对持有」的场景下应等于 `2 × 改造前的持仓数`；在「一半成对一半拆单」的场景下应等于 `2 × 停站数`。

### G2【P0·必须】到港端容量从未被校验，资料里最核心的场景判不出来

**症状**
资料 M6/M11 的整套价值在于「PEK 08:00 有槽，但 SZX 11:15 已满 → 提示改点或买对端」。
当前实现：`AcquireSlotsAt` 只对**离港**那一刻调 `SlotsAvailableAt(gs, airport, clock, slotKind)`，**从头到尾没有对 `arrClock` 做过一次容量判定**。于是 SZX 11:15 那一格早就被占满，游戏照样批。

**根因（两处）**

1. `Systems/StrategyManager.cs · AcquireSlotsAt(..., kind, arrClock)`：`arrClock` 只用来到账时写进 `SlotHolding.arrTime`，没有参与可行性判定。
2. `Logic/RoutePermitLogic.cs`：
   - `EndStatusKey(gs, route, need)` / `CanApplyEnd(gs, route, need)` 调的是 `FreeSlotsAt(gs, need.airport, TimeOf(need))`（**3 参数版**，默认 `DEP` 且不比对到港），而 `FreeSlotsAt(..., kind, arrClock)` 的 5 参数版**已经会校验配对**了。
   - 结果：`HasBoundSlot` 这一路会校验到港，`FreeSlotsAt` 这一路不会 —— 两条路口径不一致。

**修法**

1. `RoutePermitLogic` 新增成对判据（一次性收敛，避免第四个调用点再漏）：

```csharp
/// 一次停留**两端都可办**：离港端 + 到港端各自过一遍。
/// 任一端的池余量为 0 或该刻无容量 → 返回 false，并通过 out 参数说明是哪一端。
public static bool CanApplyStop(GameState gs, RouteData route, SlotNeed need,
                                out string blockedEnd, out string blockedClock)
```

2. `EndStatusKey` / `CanApplyEnd` / `SlotCandidateLogic.EndStateOf` 全部改走成对判据，`Blocked` 档要带上「离港端 / 到港端」标签（直接喂给 G5 的红字文案）。
3. `StrategyManager.AcquireSlotsAt` 的成对路径（`arrClock` 非空）在落账前**必须**再判一次到港：`SlotsAvailableAt(gs, airport, arrClock, SlotHolding.SlotKindArrival)`。不足则整单失败、一条不落。
4. `CanScheduleEnd` 的 `FreeSlotsAt` 调用改成 5 参数版（传 `need.kind`、`need.arrTime`）。
5. 驳回文案要按资料 M11 的两条出路写：
   > ❌ 到港端缺口：`SZX` `11:15` 已满（池 {used}/{cap}，我司 {mine} · 他航 {other}）。
   > ① 把起飞改到 `09:00`（到达 `12:15`，该刻余 {room} 条）；
   > ② 去时刻二级市场买 `SZX 11:15` 的到港时刻。

**判据来源**：`SlotsAvailableAt(airport, arrClock, SlotKindArrival)`；到达时刻先过 `ScheduleSlots.NearestSeries` 吸附（`TimeOf` 已有先例，需新增 `ArrTimeOf(need)`）。

| **`ListOwn` 写挂牌** | ❌ **不写 `kind`** —— 玩家把一条 ARR-only 持仓挂牌，会变成一条「离港」挂牌，`clock` 却是到港钟点。买家买到的是一条到港时刻的**离港**槽 |

| **`IsListed(mkt, airport, clock)`** | ❌ 不按 kind。同一刻的 ARR 与 DEP 会被判成「已在挂牌」 |
| **文案** | ❌ 单边挂牌与单边成交的文案不区分方向 |

**修法**

1. `ListOwn` 落账时写 `kind = SlotHolding.KindOf(h)`；`clock` 取 `h.slotTime`（对 ARR 持仓它就是到港钟点）。
2. `HoldingIndexOf(gs, airport, clock)` → 加 `kind` 参数，只在同类持仓里找。三处调用（`PruneExpired`、`AcceptOffer`、`HoldingIndexOf(listing)`）全部透传 `listing.kind`。
3. `IsListed` 加 `kind`。
4. 文案：`SlotHolding.IsArrivalOnly` 为真时，所有「时刻槽」字样改成「到港时刻」。

**界面必须给的警告**（否则玩家买了用不上会当 bug 报）：

### G4【P1】协调池成对申请的原子性与池检查顺序

**现状**：一张单两腿（`slotClock` + `slotArrClock`），但两腿的余量检查只做了离港腿（G2）。此外 `QueueApplySlots` 的重复单判据 `HasOpenApplySlot(gs, apt, clk, routeId)` 不含 kind/arrClock，同一站的 ARR 与 DEP 两张单可能被判成重复。

**修法**

1. 单号与重复判据都加方向段：
   `m_apply_slot_{route}_{apt}_{arrClock}_{clock}_{kind}_{y}q{q}`
2. `QueueApplySlots` 的闸门改成：
   ```csharp
   if (RoutePermitLogic.SlotPoolFull(gs, apt, depBand, SlotHolding.SlotKindDeparture)
    && RoutePermitLogic.SlotPoolFull(gs, apt, arrBand, SlotHolding.SlotKindArrival)
    && RoutePermitLogic.FreeSlotsAt(gs, apt, clk, kind, arrClk) <= 0)
   ```
   注意：`arrBand` 要用**到达钟点**所在时段（`ScheduleSlots.BandOfClock(arrClk)`），不能用离港的 `b`。跨波落地（22:50 起飞 / 01:20 落地）时两者不同段。
3. 成对落账的原子性：`arrClock` 非空时，两端任一端不足 → **整单失败**，`assigned` 返回空表。
4. **「单独申请到港」目前没有入口**：`SlotNeed.kind` 字段已存在、`QueueApplySlots(kind:"ARR")` 已支持，但 `NeedsFromCalls` 永远不产 `kind = ARR` 的需求，所以整条链路走不到。若要真让玩家单独申请到港时刻（用户第 2 条后半句），需要一个**产出 ARR-only 需求的入口**，现实依据是 only-landing 时刻（红眼回程、宵禁前的早到波）。最小做法：在 `NeedsFromCalls` 里对「到达段比离港段更紧」的停留额外产一条 `kind = ARR` 需求，或在时刻页给一个「只申请到港」的显式按钮 → `QueueApplySlots(..., kind: ARR)`。**此项需用户裁决**（见 §6.8）。

### G6【P2】「有去无回」的表达与出口

拆出单边之后这个状态第一次变得可能：**某次停留的 DEP 已绑班次、ARR 却没有**（或反之）。必须先有 guard，再谈交互。

| 层 | 措施 | 落点 |
|---|---|---|
| **L1 前置闸门（最重要）** | 起飞前必须两端齐 | `CanScheduleEnd` → `HasBoundSlot`（已校验 `arrTime`）**+** `FreeSlotsAt` 5 参数版。修好 G2 第 4 条即自动成立。效果：**飞机永远不会带着缺半边的状态起飞** |
| **L2 卖/收 guard** | 不许制造孤儿 | `EvaluateSale` / `ListOwn` / `ReleaseIdleHoldings` / `ApplyDueReleases` 统一加：若对端同 `usedByRouteId` + `usedByFlightNo` 仍在 `inUse`，本侧不可卖、不可回收。文案：「该到港时刻正服务于 {航线} {航班号}，需先停飞或改时」 |
| **L3 事后出口** | 已经单边了怎么办 | ① **补另一端**：运营部开单边申请单，文案写明「补齐后可飞」；② **弃槽认赔**：新增 `ReleaseHolding(index, reason, out float lostWan)`，复用 `ReleaseIdleHoldings` 的 lostWan 记账；③ **调机回场**：生成提案式「不载客调机」，不占商务槽；④ **单边挂牌**：把孤儿侧挂到二级市场（G3 落地后自动可用） |

**明确不做**：飞行中「盘旋等待」的实时航路（§5.3），所以 L3-③ 只能是提案式，不是空中状态机。

**没有 `pairId` 怎么找对端**：用 `(airport, usedByRouteId, usedByFlightNo)` 三元组 + `inUse` 即可判定「本站在本班是否已有另一端在飞」，不必新增字段。若将来要支持「一停站多对」，再考虑加 `pairId`。

### G7【P2】使用率台账没有方向

**现状**：`Logic/SlotUsageLogic.cs` 全文 `kind` 零命中、`arrTime` 零命中。系列恒按**离港**时刻记（`SeriesTimeOf(FormatClock(Mod24(c.dep)))`）。

**影响**：一旦出现 ARR-only 持仓，它既不进 `due` 也不进 `operated` → 永远没有系列 → 换季被 `ReleaseIdleHoldings` 当闲置收回（`expiresTurn`）。反过来，成对持仓的到港那一半也不单独考核。

**修法**

1. `SlotSeries` 加 `string kind`；`NoteDueForFlight` / `NoteOperatedForLeg` 每次停留记**两条**（`c.arr` → ARR 系列、`c.dep` → DEP 系列）。
2. **不改 80% 的结论**：一次停留的两条腿永远同进同出，两边的 `operated/due` 恒等，使用率数值与改造前**逐位相同**。这一点必须有回归钉住，否则下一个人会以为「分母翻倍 → 门槛翻倍」。
3. 旧档迁移：已有系列补 `kind = DEP`（`SlotUsageLogic.MigrateSlotTimes` 已有幂等先例，照抄）。

## 5. 不做什么

| 编号 | 不做 | 理由 |
|---|---|---|
| 5.1 | **时区 / 时差模型**（M12） | 全仓无时区概念，`arrTime` 本就是落地**当地**钟点，玩家填 11:15 就是 11:15。真引入要改 `LiveClockSimulator` / `ScheduleSlots` / 全部时刻比较，还要给 61 场补时区字段 —— 收益是一个肉眼看不见的数值。**只有做跨 8 小时以上洲际线时才值得重开** |
| 5.2 | **ARR / DEP 分端容量数据** | 公开资料只给「每小时架次」，不分到发。硬拆只能编造，会破坏 61 场对照表的可核对性。用「同值双池」并在表头标注为**已知简化**（`AirportCatalog.SlotCapacity(kind)` 的注释已经这么写了） |
| 5.3 | **飞行中盘旋 / 实时航路** | 本作是班次级仿真，没有空中状态机。M2 的「盘旋」只能表达为「排不出班」，不是真在飞 |
| 5.4 | **单边租出** | 租出的商业逻辑是「把这条**服务**让给你飞一季」，现实租赁几乎总是整对。拆单边会让承租方拿到一半，还得再谈一次，收益 < 成本 |
| 5.5 | **新增 `pairId` 字段** | G6 的对端识别用 `(airport, usedByRouteId, usedByFlightNo)` 就够。加字段会牵动存档迁移与所有夹具，收益为零 |
| 5.6 | **重命名 `slotTime`** | 16 个文件出现该字段，重命名只制造无谓 diff。改注释即可 |
| 5.7 | **两张单的跨邮件成对状态机** | 一张单两腿（现状）更稳；两张单会让「原子成对」变成一个跨邮件状态机 |

### 8.7 浮窗「容量 / 已占 / 可申请」自相矛盾（2026-11-07 · 用户报障）

**用户原话**：「容量1条，已占1条，可申请0条。为什么可申请是1条呢？所有的时刻都是这样的错误。」

**用户裁决**（同日追问后）：浮窗只如实报三个数 —— 容量、已占、可申请；等让位、走二级市场、
还是改刻，由战略部/运营部算清楚再报 CEO 决策，**不能靠表格含糊过去**。

根因是两套口径摆在同一行：

| 数 | 旧算法 | 结果 |
|---|---|---|
| 已占 | 逐刻把「我司 + 他航」铺满 → `list.Count` | 容量 1 · 他航 1 条 → 已占 1 |
| 可申请 | `QuarterCapacity − 我司该刻持仓`（**不扣他航**） | 我司 0 条 → 可申请 1（打架） |

「他航让位」是 2026-11-05 为保住枢纽可申请性刻意做的；代价是表上说满、闸门却放行。

修法（表与玩法同源）：

| 项 | 落点 | 说明 |
|---|---|---|
| 逐刻他航占用 | `IndustryAirlineLogic.IndustryClockCounts / IndustryAtClock` | 与卡片**同一份铺排**（我司先落位，他航只铺剩余容量） |
| 闸门 | `RoutePermitLogic.SlotsAvailableAt` | `容量 − 我司 − 他航`，并分池（DEP/ARR） |
| 卡片 | `ChipsOf` | `可申请 = 容量 − 已占`（`held` 含他航）；色块自动转灰 |
| 我司落位 | `DepLayout` / `OursLayout` / `RoutePermitLogic.PoolClocksAt` | 我司按**真实持仓时刻**落位（旧版按序号铺排，会把 12:00 画到 06:00），且逐条落位保证 Σ 逐刻 ≡ 池占用（R48 恒等式不破） |
| 驳回文案 | `SlotPoolLineAt` | 「该刻余」与「已持」同源，不再出现「余 0（已持 0 条）」 |
| 浮窗到港行 | `StrategySubpagePanel.ShowSlotTip` | 他航占用时写「他航已占 / 他航已占满」，与离港行同一读法 |

### 8.8 全集回归结果与「四端凑不齐」死结（2026-11-07）

跑批（隔离快照 `out/snap-t057..t060`，`companyName=AirlineCEORegression`）：

| 套件 | 结果 | 红项 |
|---|---|---|

本轮同时补掉一处**段余与刻余自相矛盾**（用户报障「所有的时刻都是这样」的第二层根因）：

- 旧 `RoutePermitLogic.SlotsAvailable(band)` = `池容量 − 我司 − 他航`，三个**聚合数**相减；
  而他航占用是铺在逐刻容量上的（容量 2 的刻可能被叠两条），于是出现
  「本段余 0 条」而某刻「容量 1 · 已占 0 · 可申请 1 条」。
- 改法：段余 = **Σ 逐刻余量**（同一份铺排），段与刻由构造保证一致；
  `CanApplyEnd` 也因此不再被一个假的「段满」挡死。

**红项共同根因（不是夹具坏，是模型后果）**：
他航逐刻占用 85–92% 之后，一条两机场往返要**四个端同时有空刻**（本场端离港 + 对场端到港 + 回程对场端离港 + 本场端到港）。
每段只剩 1–3 个空刻，四端同时命中的概率趋近 0：

- `Stopover_...` 直接报「候选去程时刻里没有一组**四端**都能办下槽的」；
- `SlotCandidateTests` 报「晚班 20 刻里 0 刻两端齐备、其余刻最多 0 条备选」——
  `SlotCandidateLogic.Options` 要求四端都 `ready/apply/change`，于是整段一条备选都生成不出来，
  运营部只能发「受阻汇报件」；
- `Application_SaveLoad...`/`StrategyManager_WritesState` 是夹具钉死 PEK 18:00 / 某段某刻，
  该刻被他航占满（段内还有 3 条，但那 3 条不在 18:00）。

### 8.13 机场时刻页 40 秒卡顿：逐刻重算整段铺排（2026-11-07）

用户实机复测：点「航线—航权与时刻槽—机场时刻」卡 **40 秒**。

**根因（数量级错误，不是某个慢函数）**：`IndustryAirlineLogic.ChipsOf` 把整段统计写在**逐刻循环内部**：

- `RoutePermitLogic.SlotsAvailable(gs, airport, band)`（离港）与 `SlotsAvailable(..., ARR)` 各调一次 ——
  而它们内部都要跑一次完整的他航铺排（`IndustryClockCounts → DepLayout / ArrLayout`）；
- `SlotsAvailableAt` 逐刻调用时，`IndustryAtClock` 又把**整段**铺排重算一遍只为取一个下标。

一段 13 个刻 → 26 次整段铺排；乘 80 个协调机场 × 4 段 = 320 段 → 上万次铺排，
每次还要 13 遍 `DemandWeight`（每遍重扫 24 小时容量表）。40 秒由此而来。

**修法（判据一字未改，纯去重）**：

1. `RoutePermitLogic` 新增两个重载，允许调用方**传入已算好的他航逐刻占用**
   （`SlotsAvailable(..., int[] industryCounts)` / `SlotsAvailableAt(..., int industryAtClock)`）；
   旧签名保留，内部转调新签名 —— 公式仍只有一份，不会漂移。
2. `ChipsOf` 的段余 / 到港段余提到循环外，并直接复用它已经铺好的 `perQ`（离港）与
   `arrIndustry`（到港）。
3. `DemandWeight` 拆出 `PeakHourCapacity(airport)` + `WeightAt(...)`，`FillWave` /
   `FillWaveCounts` 每段只算一次峰值（原来每刻一次）。
4. `PickAirline` 的 `AirportRegions.CountryOf(airport)` 从航司循环内提到循环外。
5. `SlotsTableText` 的段余改取闸门口径（`SlotsAvailable` = 逐刻余量之和），不再用聚合相减的 `OpenSlots`。

**护栏**：PlayMode 新增 `SlotsTable_ComputesWithinBudget`（整表预算 3 s，只拦数量级退化，
并 `Debug.Log` 实测毫秒数），注释里写明「`SlotsAvailable` / `IndustryClockCounts` 不许进逐刻循环」。

**当时未跑实测**（Unity 开着、项目被占用）：文字表约 12 万字符，TMP 生成网格也可能占可观时间 ——
那部分属于版式问题，随新 UI 的分页 / 折叠一并消解。第二轮补测见 8.14。

### 8.14 机场时刻页第二轮：40 s → 4 s，再把重复计算与分配清掉（2026-11-07）

用户实机复测（第一轮修复后）：进入该页 **4 秒**（原来 40 秒）。方向对了但还慢。

**第二轮查到的三处**：

1. **排版被算了两遍**：`ChipsOf` 已经把本段离港 / 到港铺排算完并得到 `bandFree` / `bandFreeArr`，
   但纯文字表为了写「离港余 / 到港余」又各调了一次 `SlotsAvailable` —— 每个机场每段白跑两遍
   完整铺排（80 × 4 × 2 = 640 次）。改为 `ChipsOf(..., out int bandFreeDep, out int bandFreeArr)`
   直接带回，调用方零额外成本。
2. **`PickAirline` 每次填一条槽都重算 38 家航司的权重**：候选集与权重只取决于机场
   （`Participates` / 枢纽加成 / 本国加成 / `Unit(code, airport, "w")` 抖动都与 band、k 无关），
   而一段要填几十条槽 → 每段几千次重算，× 320 个机场×段。改为按机场**永久缓存**
   `AirlineWeightSet{cands, weights, total}`，浮点求和顺序不变，结果逐位一致。
3. **热路径上的分配**（三处，全部改成零分配、输出不变）：
   - `Unit(params string[])`：原来每次 1 个数组 + 1 个 StringBuilder + 1 个 string。
     改为增量 FNV（喂 `'|'` 与各段字符），与 `Hash(joined)` 逐位等价；
     另加 2 参 / 3 参重载，热路径不再分配数组。
   - `ScheduleSlots.FormatClock`：原来每次插值格式化，改为 1440 项常量表查表。
   - `ScheduleSlots.ParseClock`：原来 `int.TryParse(Substring(...))` 每次两个子串，
     改为原地解析（保留 TryParse 的口径：前导空白、正负号、尾部杂质即失败）。
   - `BandGrid` / `BandGridLabels`：原来每次都遍历 96 个刻度重新拼，改为按 band 缓存后返回副本。

**自测**：`node tools/semcheck/run.js` → `errors=0` / `tests-asm: errors=0` / `enc: errors=0`。
**实测量化**（隔离导出 `out/b17-perf2`，PlayMode `SlotsTable_ComputesWithinBudget` 打出两条）：

| --- | --- | --- |

| 从建面板到文字表排进 TMP（含 TMP 排版） | 用户实机约 4 s | **219 ms** |
