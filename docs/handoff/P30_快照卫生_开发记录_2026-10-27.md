# P30 · 交付快照卫生（42 GB 缓存）· 开发记录（2026-10-27）

## 1. 发现

统计 `out/collab` 时发现 **58 个交付快照共占 44,261 MB**，单个最大 1923 MB。逐层拆解：

```
Unity Project\Library     1874.8 MB   ← 97.6%
Unity Project\Assets        32.3 MB
Unity Project\Logs          13.5 MB
tools                         1.1 MB
```

58 个目录中 **23 个带 `Library`**，合计 **42.1 GB**。

## 2. 根因

不是快照复制错了，而是**预检在快照内跑 Unity**：

```json
recommendedProfiles: ["unity-playmode"]
selfTest: "stage-close preflight: unity-playmode"
```

`runProfileInSnapshot` 以快照目录为 cwd 启动 Unity，Unity 就在那里生成 1.9 GB 的 `Library`。
而没有任何代码在跑完后清理它。`exportStableSnapshot` 只复制 `IMPLEMENTATION_ROOTS`
（`Assets` / `Packages` / `ProjectSettings` / `tools/*`），`Library` 从来不在其中——
核对交付 manifest：**1283 条目，Library 条目 0**。

也就是说这 42 GB 是 **manifest 之外的纯遗留物**：`ARTIFACT_DIR_NAMES` 把它当构建产物忽略，
`collectEntries` 不列它，`verifySnapshotIntegrity` 也不过问，因此它一直无人回收。

## 3. 修复

新增 `tools/collab/lib/snapshot-hygiene.mjs`，导出 `pruneSnapshotArtifacts(snapAbs, { keep, protect })`。

规则刻意收窄到四条：

| 规则 | 理由 |
| --- | --- |
| 只看**名字**属于 `SNAPSHOT_ARTIFACT_DIRS` 的目录 | 与 `fingerprint.EXCLUDE_DIR_NAMES` / `ARTIFACT_DIR_NAMES` 同源，不会误伤源码目录 |
| **manifest 列出的文件永不删除**，即使它落在产物目录里 | 这是"绝不删证据"的硬保证 |
| 已声明的 run 输出（`resultFile`、`runOutputRels`）保留 | 见下 |
| 其余一律删除，空目录一并移除 | 全部可再生 |

第三条是关键：`unity-editmode` / `unity-playmode` 的 `resultFile` 是
`Unity Project/Logs/Tasks20261017_{runToken}.xml` —— **NUnit 结果本身就放在 `Logs/` 里**。
若直接整目录 `rm -rf Logs`，就会把检测正要读的证据一起删掉。

`runProfileInSnapshot` 在**完整性校验之后**调用它（先算出判决，再清场），
并把结果作为 `artifacts` 字段返回。

## 4. 一次性清理

用同一个模块跑一遍历史快照（`keep` 取各自 manifest）：

```
snapshots touched: 29 | files removed: 813795 | freed GB: 42.25
```

耗时约 12 分钟 —— `Library` 里是几十万个小文件，Windows 删起来慢。

## 5. 清理后校验：证据没有受损

对全部 57 个仍在盘上的快照重跑 `verifySnapshotIntegrity`：

```
integrity ok: 55 | failed: 2
```

那 2 个失败**与本次清理无关，是既有问题**，且失败点不同：

| 交付 | 任务 | 报错 |
| --- | --- | --- |
| `DEL-20261017150657-dd9483` | C-DEMO | 快照含未列文件：`docs/collaboration/CURRENT.md`、`events/*.json` 等 |
| `DEL-20261022131900-282815` | S07-Balance | 快照含未列文件：4 个 `QuarterlyOneOff*.meta` |

两者的报错都是 **"contains unlisted files"（多出文件）**，而不是 **"file missing"** 或 **"tampered"**。
删除动作只会减少文件，不可能制造"多出文件"，所以这两条早于本次清理存在。

更重要的是：完整性校验是**分步**的 —— 第 1 步逐条核对「manifest 每个文件存在且 hash 相符」，
第 2 步才查「有没有多余文件」。这两条异常是在第 2 步抛出的，说明**第 1 步对全部 57 个快照都通过了**。
这就是「清理没有删掉任何被 manifest 引用的字节」的直接证据。

## 6. 回归

`tools/collab/tests/collab.test.mjs` 新增 2 条：

- **pruning drops regenerable snapshot debris but never evidence**：构造
  `Library`（含嵌套子目录）、`Temp`、`obj`、`bin`，加一个 manifest 文件和一个位于
  `Logs/` 内的结果文件；断言前两者存活、`Logs/Editor.log` 被删、`Library` 目录本身被移除、
  释放字节数精确等于构造值、`keptFiles=1`（只统计产物目录内被保留的文件）。
- **pruning a snapshot that has no artifacts is a no-op**：无产物时 `freedBytes=0` 且源文件逐字节不变。

`node tools/collab/tests/run-all.mjs`：**174 项通过，失败 0、跳过 0**。

## 7. 尚未做的事（如实声明）

- **没有真的跑一次 `unity-*` 预检**来验证"跑完自动瘦身"这条路径。理由：`stage-close` 的
  unity 预检要求关闭编辑器并持有 45 分钟的 Unity 租约，而当时用户正在用 Unity；
  且 S19 刚交付、不适合再叠一次重预检。目前该路径的正确性依据是：单元测试覆盖
  `pruneSnapshotArtifacts` 的语义 + `runProfileInSnapshot` 只是在校验之后多调一次。

# 附录 · 第二部分：`DEL-20261027031726-30842b` 被检测退回的缺陷

## 8. 发生了什么

第一版交付（`DEL-20261027031726-30842b`，profile `collab`）送给 Codex 后**未执行**，原因：

> AC2 要求本次 Unity EditMode 结果，但 profile 是 `collab`，快照也不含 Unity 工程，
> 无法如实签署 `AC2=passed`。

这是**准确的拒绝**。交付里躺着一条检测者根本不可能证明的验收条款 —— 与 S18 修的
rescope 分歧属于同一类问题：内部口径不一致，产出一个无法收口的交付。

## 9. 根因：复用任务时不校验验收条款的出处

`cmdStageClose` 只有在**新建**任务时才生成 AC：

```js
if (!task) { /* 生成 definition，AC 来自 acceptanceCriteriaFor(pick.profile, taskId) */ }
else if (!task.acceptanceCriteria?.length) { fail(...) }
```

而带 `--task` 指向已存在任务时，`task = existing`，AC 原样沿用。

时间线正好踩中：

| 时刻 | 动作 | profile | 结果 |
| --- | --- | --- | --- |
| 第一次 | `stage-close --task S20-...` | `unity-editmode`（自动选） | **已被写入任务定义**，但 Unity 占用 → exit 4 |
| 第二次 | `stage-close --profile collab --roots ...` | `collab` | 复用上一轮的任务，AC2 仍是 EditMode 条款 |

第一次失败发生在 `writeDefinition` / `cmdTaskAdd` **之后**、Unity 占用检查之前，
所以任务已经落盘。重试换了 profile，任务却带着旧合同。

## 10. 修复：fail-closed + 显式 `--refresh-ac`

新增 `criteriaProfile(cfg, acceptanceCriteria, taskId)`：把任务的 AC 文本**逐条**与各
profile 的模板做全等比对，反推出它由哪个 profile 生成。

- 比对不上任何模板 → 视为人工撰写，**不干预**（不误判）；
- 比对得上且 ≠ 本次所选 profile → **拒绝交付**，exit 2，并给出两条出路：

```
task S20-SnapshotHygiene has acceptance criteria generated for profile unity-editmode,
but this close runs collab; the reviewer could not sign unity-editmode's clauses
{"criteriaProfile":"unity-editmode","profile":"collab",
 "hint":"pass --refresh-ac to regenerate the acceptance criteria for collab (records a new task revision), or re-run with --profile unity-editmode"}
```

- 显式 `--refresh-ac` → 按实际 profile 重新派生 AC，**任务 revision +1**，并写一条
  `stage-refresh-ac` 事件，`data.previous` 完整保留旧条款。旧合同进事件日志，不是被静默抹掉。

## 11. 重交付

```
DEL-20261027034213-898afe ｜ profile collab ｜ 预检通过 ｜ 改动 8 个文件
```

- 任务 AC 已变为 collab 模板（AC2 = 协作工具回归套件全部通过），`revision` 1 → 3；
- `stage-refresh-ac` 事件：`unity-editmode -> collab`，`data.previous` 保留原 AC；
- 旧交付在共享台账（`state.json.deliveryStatus`）标记
  `superseded by DEL-20261027034213-898afe`；
- 交接命令**不再需要 `--coverage`** —— 条款已与模板逐字一致，回到机器可判定。
  这一点本身就是修复生效的旁证：上一版被迫人工补证，正是因为条款被换过。

## 12. 回归

- `stage.test.mjs` 新增 **T09 / T10**（fixture 内加第二个 profile）：
  - T09：不同 profile 关闭同一任务必须 exit 2，且**一份交付都不许落盘**，任务 AC 不被改动；
  - T10：`--refresh-ac` 后 AC 切换、revision +1、`stage-refresh-ac` 事件含 from/to/previous。
- `collab.test.mjs` 新增 2 条（见 §6）。
- `node tools/collab/tests/run-all.mjs`：**176 项通过，失败 0、跳过 0**，8 个子套件全绿。

## 13. 仍然没做的

- `--refresh-ac` 走的是"同一任务换合同"，**没有**强制要求该任务此前无检测记录。
  理论上一个已被检测拒绝的任务可以改条款后重交付 —— 这是有意留的口子（修缺陷本来就该
  能改条款），但代价是：改条款这件事只留在 `stage-refresh-ac` 事件里，检测者需要主动去看。
  更严的做法是要求改动前该任务 `reviewStatus != passed`，本次未加。

# 附录 · 第三部分：`settled` 与 gate 对 `archived` 判定不一致

## 14. 怎么发现的

前两笔检测通过后，我按流程查依赖链，发现 `S18 → blocked by S17-ScopeBaseline`、
`S19 → blocked by S18`。于是对 S17 跑 `task-rescope`：

```
改动文件 17 个：未变 9、已再次改动 8、其中已被后续通过交付接手 8
结论：变动部分的当前字节已由后续通过交付（DEL-20261027034213-898afe）承担，按改动文件收敛并归档。
```

S17 被正确归档为 `freshness=archived` —— 这是 S18 修好的接管逻辑在生效。**但 gate 依然报 BLOCKED**：

```
S17-ScopeBaseline | BLOCKED | freshness=archived ; blocked by: S16-CollabFidelity
S18-ScopeVerdictFix | BLOCKED | freshness=archived ; blocked by: S17-ScopeBaseline
```

也就是说：归档这件"已经做对了"的事，**完全不能解锁任何下游**。再往上游倒，S16 也是同样情形。

## 15. 根因：同一个问题有两个定义

两处代码在回答同一个问题——"这个任务的检测结论还算不算数"——但答案不同：

| 位置 | 判据 | 归档的任务 |
| --- | --- | --- |
| `state.mjs` 的 `settled()` | `passed && (current \|\| archived)` | **算完成**，从 NEXT_CURSOR / NEXT_CODEX 移除 |
| `taskbook.mjs` 的 `computeTaskGate` | `passed && current` | **算失败**，于是 dependencies 检查判下游阻塞 |

后果是一个自相矛盾的状态：看板上这个任务已经"结束"、不再出现在待办里，而 gate 说它没过，
于是它的依赖者永远卡住。链路 S16 → S17 → S18 → S19 四个任务**每一环都有通过且独立的检测**，
却全部无法通过 gate。

这和 S18 修的 rescope 分歧是同一个病：同一事实在两处各算一次，然后不一致。

## 16. 修复：一个谓词，两个调用方

`basis.mjs`（无本地依赖，不会造成循环）新增：

```js
export function freshnessSettles(freshness) {
  return freshness === 'current' || freshness === 'archived';
}
```

- `state.mjs` 的 `settled()` 改为调用它；
- `taskbook.computeTaskGate` 的 `current-passed-review` 改为调用它。

为什么 `archived` 该算通过：归档的语义是"这个任务自己改过的字节**还在**，或者已被后续
**通过检测**的交付接手"。两种情况都意味着它对那批字节的检测结论仍然是诚实的陈述。
而 `stale` 是"有字节变了且没有被任何通过的交付接手"——那才是真的要重验。所以：

- `current` → 通过
- `archived` → 通过（字节有人负责）
- `stale` / `unknown` → 不通过（fail-closed 保持不变）

修复后立刻验：

```
S16-CollabFidelity   | gate: OK
S17-ScopeBaseline    | gate: OK
S18-ScopeVerdictFix  | gate: OK
S19-ScenarioFixture  | gate: OK
S20-SnapshotHygiene  | gate: BLOCKED | latest review ... passed; freshness=stale
```

S20 仍然 BLOCKED，但这次是**真的** stale——原因见 §17，与本节无关。
