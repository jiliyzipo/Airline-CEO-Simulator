## 1. 缺陷（S17 交付内自相矛盾）

`DEL-20261027014232-7be62b` 的 `task-rescope` 只看原始漂移：

```js
next.freshness = drift.drifted.length ? 'stale' : 'archived';
```

而 `refreshFreshness` 会走「后续通过交付接手」判定。S17 通过后，S16 的改动文件
有 4 个被 S17 改过，其中 2 个当前字节与 S17 快照一致。于是：

- `task-rescope --task S16-CollabFidelity` 打印「这些文件被后续改动过，任务仍需要按当前代码复验（不归档）」；
- 紧接着的一次 `sync` 把同一个任务写成 `archived`。

命令说要复验、状态说已归档。这正是 S17 想消灭的那类「读到的结论和实际要做的活不一致」。

## 2. 原因

判定逻辑有两份实现：

| 位置 | 是否含接手规则 |
| --- | --- |
| `refreshFreshness`（state.mjs） | 含 |
| `cmdTaskRescope`（commands.mjs） | 不含 |

`--dry-run` 是只读预览，却复用了缺少接手规则的那一份，因此预览本身就不可信。

## 3. 修复

`basis.mjs` 新增 `rescopeVerdict(repoRoot, delivery, { deliveries, latestReviewFor })`，
把「漂移 + 接手 + 结论 + scopeDrift」合成单一出口：

```js
{
  drift, basis, intact, covered, uncovered, uncoveredCount,
  owners,        // 接手方交付 id
  freshness,     // 'stale' | 'archived'
  scopeDrift,    // 落盘用
}
```

`refreshFreshness` 与 `cmdTaskRescope` 现在都调用它。命令的
`--dry-run` 输出 `freshness / covered / uncovered`，并据此决定打印
「已归档」还是「仍有 N 个文件无人复验」，与随后 `sync` 写入的状态必然一致。

`rescope` 记录里额外保存 `coveredBy` 与 `uncovered`，便于事后追责到具体交付。
