## 2. 单项占比：73% 的机器时间花在 2 个用例上

把一次完整交付闭环里的**机器时间**（不含人写代码、不含等待授权）相加：

```
Explicit 2 项      510.1 s   ████████████████████████████████████  73%
PlayMode 173 项     67.5 s   █████                                  10%
semcheck            23.2 s   ██                                      3%
Unity 启动×2        90.0 s   ██████                                  13%
EditMode + 其余      4.6 s   ▏                                       1%
─────────────────────────────────
合计              ~695.4 s ≈ 11.6 分钟
```

**这两个 Explicit 用例是 `T057OneXPlayModeTests`**（`Tests/PlayMode/T057OneXPlayModeTests.cs:105,136`）。

它们慢不是缺陷，是设计：用例验证 1× 速度下「现实 1 分钟 = 游戏 1 分钟」，因此必须**真的等满现实时间**。文件头注释写得很清楚："运行时长约 8 分钟，故标 `Explicit`"。任何加速手段都会让断言失去意义。

但有两点值得记录：

1. 它们**按设计不进默认套件**。S47 之所以跑它们，是因为"无剩余未执行项"这条汇报口径。S47 改的是 `DeptReportLogic`（纯文本投影），与 `TimeManager` / `GameSpeed` / 时钟停表毫无交集。
2. 按 Batch 逐个算：12 批 × 8.5 分钟 ≈ **1.7 小时纯等待**，换来的结论在未触碰时间系统时恒为"通过"。

## 3. 增量编译：缺口已补，结论比预期更不利于路线 B

2026-11-01 用探针实测（`.collab-local/measure/probe.mjs`：向目标文件尾部追加一行注释、按字节还原，实测后 SHA256 与实现指纹均未变）：

| 改的文件 | 所在层 | 样本（`compile time`） | 中位数 | 极差 |
|---|---|---|---:|---:|
| `GameplayEnums.cs`（19 行） | Logic | 2,914 / 3,508 / 3,589 ms | **3,508 ms**（n=3） | 675 ms |
| `MapPlaceNameLayer.cs`（16 行） | UI | 2,552 / 7,015 ms | 4,784 ms（n=2） | **4,463 ms** |

合计 n=5，全部是**同一个程序集** `AirlineCEO.Runtime`、同样只加一行注释。

两个观察：

1. **Logic 侧相当稳**：三次落在 2.9–3.6 s，极差 675 ms（约 19%）。这个精度足以支撑比较。
2. **UI 侧出现一个 7,015 ms 的离群值**：同文件另一次只要 2,552 ms，与 Logic 的量级一致。属离群而非层差异（理由见 §3.1）。

**因此可用的基线是 2.5–3.6 s 这个区间，不是某个单点。**

### 3.1 层间差异根本不成立：Logic 与 UI 在同一个程序集里

`Unity Project/Assets/Scripts/` 下只有一个 `AirlineCEO.Runtime.asmdef`，`Logic/` 与 `UI/` 都在同一个程序集 `AirlineCEO.Runtime` 内（`Assets/Tests` 与 `Assets/Scripts/Editor` 各自独立）。改任一层的任一行，Unity 重编译的都是**同一个程序集**，输入完全相同。

既然输入相同，"UI 要 7 秒、Logic 只要 3.5 秒"在原理上就不该存在 —— 它只能是噪声。第二次 UI 采样（2,552 ms）反过来落到了 Logic 的水平，正好印证这一点。

**因此：任何"某层更贵"的结论都是把噪声当信号。**

### 3.2 按最有利的假设换算，B 的收益落在噪声区间内

假设编译耗时与重编译行数严格成正比（这是对 B **最有利**的假设），用 Codex 报告的行数：

| 场景 | 实测基线 | 行数削减 | 按比例可得收益 |
|---|---:|---:|---:|
| 改 Logic | 3.51 s（中位） | −4.40% | **≈ 0.15 s** |
| 改 UI | 4.78 s（中位） | −52.77% | **≈ 2.52 s** |

即使按最有利假设取上界，改 UI 也只省 2.5 秒。而：

- 改 Logic 能省的 0.15 s，**比 Logic 侧自身的极差（0.68 s）还小 4 倍** —— 拆完也测不出来；
- 改 UI 能省的 2.5 s，落在 UI 侧 4.5 s 的波动之内 —— 同样测不出来；
- 冷启动编译 30 秒，是增量编译的 9–11 倍，B 对它毫无影响；
- 一次交付闭环的机器时间 ~695 秒里，Explicit 两项占 510 秒。

**结论：在现测精度下，路线 B 的收益无法与本机噪声区分。**这不是说 B 一定无效，而是说"省下来多少"在本机不可测 —— 要继续推进 B，需要先有稳定的测量方法（更多重复、控制杀毒与索引干扰），而不是再拆一层。

补测记录：后续 7 轮自动化采样中 5 轮被判为超时，但事后查 `Editor.log` 发现其中 2 轮**实际已经编译**（3,589 ms / 2,914 ms）—— 是轮询脚本漏读，不是 Unity 没干活。已修脚本（增 `CompileScripts:` 兜底）并按日志回填。另外 Unity 转入后台确实会停止重编译，所以**每次测量都要求焦点在 Unity 上**，这本身是可重复性的一个障碍。

### 3.3 顺手发现：这部分固定开销占比很大

冷启动 `CompileScripts` 30,030 ms 对应完整的 ~121.5k 行；增量 3.5–7.0 s 对应的也是同一程序集。若纯按行数线性推算，增量编译本应接近冷启动的量级，实际只有 1/4 到 1/8。差额是 Roslyn 进程复用、Unity 增量管道等固定开销 —— 也就是说**减少行数能省的绝对秒数，远小于行数比例**。这与 3.2 的结论方向一致。

## 5. 一句话结论

**被证实的"慢"只有两项：冷启动 30 秒编译、8.5 分钟显式测试。前者是程序集级、后者是物理时间，`25→12` 对两者都无影响。**

增量编译已实测（n=5）：基线 2.5–3.6 s。Logic 三次极差 0.68 s，UI 出现一个 7,015 ms 离群值。Logic 与 UI 同在单程序集 `AirlineCEO.Runtime` 内，编译输入完全相同，层间差异在原理上不存在。

按对路线 B 最有利的线性假设换算，拆分能省的绝对时间（0.15 s / 2.52 s）**都小于各自侧面的测量波动**（0.68 s / 4.5 s）。**B 的收益在本机不可证伪，也不可测量**。

要继续推进 B，先要有可重复的测量方法（更多重复、受控环境），而不是先拆程序集 —— 否则拆完之后没人能说出到底快了多少。
