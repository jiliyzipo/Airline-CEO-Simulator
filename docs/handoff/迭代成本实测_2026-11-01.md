## 2. 单项占比：73% 的机器时间花在 2 个用例上

把一次完整交付闭环里的**机器时间**（不含人写代码、不含等待授权）相加：

```
Explicit 2 项      510.1 s   ████████████████████████████████████  73%
PlayMode 173 项     67.5 s   █████                                  10%
semcheck            23.2 s   ██                                      3%
Unity 启动×2        90.0 s   ██████                                  13%
EditMode + 其余      4.6 s   ▏                                       1%
─────────────────────────────────
```

**这两个 Explicit 用例是 `T057OneXPlayModeTests`**（`Tests/PlayMode/T057OneXPlayModeTests.cs:105,136`）。

它们慢不是缺陷，是设计：用例验证 1× 速度下「现实 1 分钟 = 游戏 1 分钟」，因此必须**真的等满现实时间**。文件头注释写得很清楚："运行时长约 8 分钟，故标 `Explicit`"。任何加速手段都会让断言失去意义。

1. 它们**按设计不进默认套件**。S47 之所以跑它们，是因为"无剩余未执行项"这条汇报口径。S47 改的是 `DeptReportLogic`（纯文本投影），与 `TimeManager` / `GameSpeed` / 时钟停表毫无交集。

## 3. 增量编译：缺口已补，结论比预期更不利于路线 B

2026-11-01 用探针实测（`.collab-local/measure/probe.mjs`：向目标文件尾部追加一行注释、按字节还原，实测后 SHA256 与实现指纹均未变）：

| 改的文件 | 所在层 | 样本（`compile time`） | 中位数 | 极差 |
|---|---|---|---:|---:|
| `GameplayEnums.cs`（19 行） | Logic | 2,897 / 2,914 / 3,508 / 3,589 / 3,669 ms | **3,508 ms**（n=5） | 772 ms |
| `MapPlaceNameLayer.cs`（16 行） | UI | 2,552 / 2,615 / 4,143 / 7,015 ms | **3,379 ms**（n=4） | 4,463 ms |

合计 **n=9**，全部是**同一个程序集** `AirlineCEO.Runtime`、同样只加一行注释。

三个观察：

1. **两层的中位数几乎相同**：3,508 vs 3,379 ms，差 4%。这与"两者编译输入完全相同"完全一致 —— **层间差异不存在**。
2. **Logic 侧很稳**（n=5，极差 772 ms / 22%），足以支撑 0.1 秒级的判断。
3. **UI 侧有一个 7,015 ms 离群值**，其余三次都在 2.5–4.1 s。它是单次异常（可能是资产导入或杀毒扫描叠加），不是层的属性。

**基线：约 3.4 s（n=9 中位 3,508 ms），正常波动范围 2.6–4.1 s。**

### 3.1 层间差异根本不成立：Logic 与 UI 在同一个程序集里

`Unity Project/Assets/Scripts/` 下只有一个 `AirlineCEO.Runtime.asmdef`，`Logic/` 与 `UI/` 都在同一个程序集 `AirlineCEO.Runtime` 内（`Assets/Tests` 与 `Assets/Scripts/Editor` 各自独立）。改任一层的任一行，Unity 重编译的都是**同一个程序集**，输入完全相同。

既然输入相同，"UI 要 7 秒、Logic 只要 3.5 秒"在原理上就不该存在 —— 它只能是噪声。第二次 UI 采样（2,552 ms）反过来落到了 Logic 的水平，正好印证这一点。

**因此：任何"某层更贵"的结论都是把噪声当信号。**

### 3.2 按最有利的假设换算，B 的收益落在噪声区间内

假设编译耗时与重编译行数严格成正比（这是对 B **最有利**的假设），用 Codex 报告的行数：

| 场景 | 实测基线 | 行数削减 | 按比例可得收益 | 该层极差 |
|---|---:|---:|---:|---:|
| 改 Logic | 3.51 s（n=5 中位） | −4.40% | **≈ 0.15 s** | 0.77 s |
| 改 UI | 3.38 s（n=4 中位） | −52.77% | **≈ 1.78 s** | 4.46 s |

即使按最有利假设取上界，改 UI 也只省 1.8 秒。而：

- 改 Logic 能省的 0.15 s，**只有该层自身极差（0.77 s）的 1/5** —— 拆完也测不出来；
- 改 UI 能省的 1.8 s，落在该层 4.5 s 的波动之内 —— 同样测不出来；
- 冷启动编译 30 秒，是增量编译的 **9 倍**，B 对它毫无影响；
- 一次交付闭环的机器时间 ~695 秒里，Explicit 两项占 510 秒。

**结论：在现测精度下，路线 B 的收益无法与本机噪声区分。**这不是说 B 一定无效，而是说"省下来多少"在本机不可测 —— 要继续推进 B，需要先有稳定的测量方法（更多重复、控制杀毒与索引干扰），而不是再拆一层。

补测记录：后续 7 轮自动化采样中 5 轮被判为超时，但事后查 `Editor.log` 发现其中 2 轮**实际已经编译**（3,589 ms / 2,914 ms）—— 是轮询脚本漏读，不是 Unity 没干活。已修脚本（增 `CompileScripts:` 兜底）并按日志回填。另外 Unity 转入后台确实会停止重编译，所以**每次测量都要求焦点在 Unity 上**，这本身是可重复性的一个障碍。

### 3.3 顺手发现：这部分固定开销占比很大

冷启动 `CompileScripts` 30,030 ms 对应完整的 ~121.5k 行；增量 3.5–7.0 s 对应的也是同一程序集。若纯按行数线性推算，增量编译本应接近冷启动的量级，实际只有 1/4 到 1/8。差额是 Roslyn 进程复用、Unity 增量管道等固定开销 —— 也就是说**减少行数能省的绝对秒数，远小于行数比例**。这与 3.2 的结论方向一致。

## 5. 测量方法本身的可靠性

用户裁决"先建可重复的测量方法，再决定要不要拆"。方法已固化为脚本，但有一个必须写明的限制。

### 5.1 方法

`.collab-local/measure/probe.mjs`（单次）与 `run-series.mjs`（连跑）：

1. 向目标 `.cs` 尾部追加一行注释 `// collab-compile-probe <token>`（语义为零）；
2. 记下 `Editor.log` 的字节偏移；
3. 等 Unity 重编译；
4. 只读偏移之后的新增内容，提取 `compile time=N ms`；
5. **按原字节还原**并校验 SHA256 —— 指纹是按内容哈希算的，字节还原即指纹还原，不会弄脏任何待验交付。

已实测验证：还原后 SHA256 与实测前完全一致，工作区 `git status` 无残留。

### 5.2 限制：Unity 在后台不编译，自动化成功率约 1/3

实测 10 轮自动化采样，仅 3–4 轮在脚本超时前捕获到编译。原因：Unity 编辑器转入后台后不再抽取编译队列。

已尝试无效的做法：`AppActivate` 把窗口提到前台（只提窗口、不发送输入）。提出去后仍不稳定，说明编辑器还要求真实交互事件才排空队列。

**因此每轮有效测量目前仍需人工点一下 Unity 窗口。**这不妨碍数据有效性（所有样本都来自 `Editor.log` 里真实的编译记录），但妨碍"无人值守跑 20 次取中位数"。

### 5.3 一个已修的读数缺陷（值得记录）

轮询脚本最初只认 `Scripting: domain reloads=…, compile time=…` 这一种行。某些构建只写 `CompileScripts: N ms` 而没有配对行，导致 **2 轮真实编译被误判为超时丢弃**。已增加 `CompileScripts:` 兜底，并按日志回填那 2 条样本。

教训：这正说明"单次采样"不可信 —— 一次误判就能让结论反转。

### 5.4 现有数据是否足够

够。n=9，两层中位数相差 4%，各自极差已知。要比较的两个量（B 的收益 0.15 s / 1.78 s）都显著小于同层极差（0.77 s / 4.46 s）—— 这个判断不需要更高精度，因为**差距本身小于噪声**，再多测也只会把噪声估计得更准。

要真的验证 B 的效果，测法得换：在拆分前后各测同一批文件、用配对比较消掉环境漂移，而不是继续加大样本量。

## 6. 收口流程的成本与已做的削减（2026-11-01 下午）

### 7.1 一次收口原本花在哪里

| 环节 | 耗时 | 说明 |
|---|---:|---|
| 快照导出 | ~5 s | 35 MiB / 1,378 文件 |
| **预检（跑 profile）** | **~130 s** | `collab` 套件；`unity-*` 要冷导入，100–450 s |
| 合计（`stage-close` 实测） | **137.8 s** | 预检占 95% |

而 `stage-review` 随后**又跑一遍同款套件**（89.5–199.4 s）。

### 7.2 预检的实际拦截率

73 次交接记录：**通过 66 / 失败 7（9.6%）**。

但 `DEL-20261101013704-042046` 是**预检通过、复验失败**（D35）——两者环境不同，预检通过的字节复验仍可能拒收。也就是说预检给出的信号比复验弱，却要付出同等甚至更高的机器时间。

**处置：预检默认关闭**（`--preflight` 显式开启）。实测 `stage-close` 从 **137.8 s → 14.4 s**（含导出），降幅 89%。交付快照、交接单、自测声明均照旧生成，只是不再在快照内重跑一遍。

### 7.3 冷导入：为什么 42% 的交付特别慢

`unity-editmode` 占 39/92 个交付。快照不带 `Library`（工作区那份 2,078 MiB / 46,574 文件），所以预检和复验**各自从零冷导入**，单次 85.9–451.7 s。改一行游戏代码 ≈ 2 × 冷导入 = 3–15 分钟纯等待。

### 7.4 预热可行性调查（未做实现，仅测数）

| 方案 | 实测 | 结论 |
|---|---:|---|
| `Copy-Item` 整树 | **204.5 s** | 比冷导入还慢，否决 |
| `robocopy /MT:32` | **32.6 s** | 比冷导入下界快 67 s，有希望 |
| Library 是否写死项目绝对路径 | 抽 13 个文件，**0 命中** | 大概率可搬迁 |

**未验证的关键一环**：把 Library 搬到快照路径后，Unity 是否真的跳过重导入。Library 内的 `ArtifactDB`/`SourceAssetDB` 可能仍按 GUID 重新校验；若 Unity 判定不一致，就会「32.6 s 预热 + 完整冷导入」，比现在更慢。

这一步需要一次真实的 `unity-*` 复验来验证，而它要求 Unity 未被占用。**结论：方案有希望，但仍未证明，不能据此宣布提速。**

## 7. 一句话结论

**被证实的"慢"只有两项：冷启动 30 秒编译、8.5 分钟显式测试。前者是程序集级、后者是物理时间，`25→12` 对两者都无影响。**

**收口本身不慢，慢的是预检。** 预检默认关闭后 `stage-close` 从 137.8 s 降到 14.4 s（89%），交付与快照照旧完整。冷导入（`unity-*` 每次 100–450 s）是下一个大头，`robocopy` 预热测出 32.6 s、Library 未写死绝对路径，但 Unity 是否接受尚未验证。

增量编译已实测 **n=9**：基线约 **3.4 s**，正常波动 2.6–4.1 s。**Logic（中位 3,508 ms）与 UI（中位 3,379 ms）相差 4%** —— 两者同在单程序集 `AirlineCEO.Runtime` 内、编译输入完全相同，层间差异确认不存在。

按对路线 B 最有利的线性假设换算，拆分能省的绝对时间（改 Logic 0.15 s / 改 UI 1.78 s）**都远小于各自侧面的测量波动**（0.77 s / 4.46 s）。**B 的收益在本机既不可证伪，也不可测量。**

测量方法已固化（§5），但受限于"Unity 后台不编译"，无人值守连跑尚不可行。要真正验证 B，测法得换成拆分前后的**配对比较**，而不是继续加大样本量。

## 8. S50+ partial 拆分：已评估，决定搁置（2026-11-01）

结论：**partial 拆分只换可读性，不换速度。可读性不是当前痛点，故不做。**

触发问题：拆分（把大文件按 `partial class` 拆成多个文件）对任务处理速度和 Unity 导入速度有没有影响。

### 8.1 四条结论

| 维度 | 影响 | 依据 |
|---|---|---|
| 运行时（任务处理） | **零** | `partial` 是纯编译期特性，Roslyn 合并后生成的 IL 与单文件逐字节相同。这是语言语义，不是估算。 |
| 编译时间 | **零收益** | Unity 按**程序集**编译，不按文件。改 `InboxManager.cs` 一行即全量重编 `AirlineCEO.Runtime`，拆成几个文件都一样。拆分不减少总行数，只移动行。基线见 §3（中位 3.4 s，n=9）。 |
| Unity 导入 | **几十毫秒级** | 按 19 个候选各拆 3 份估算，新增约 36 个 `.cs` + 36 个 `.meta`，资产数 1,260 → 约 1,332（+5.7%）。但导入按 mtime/哈希增量，新增文件只导一次，摊到 8,587 ms 冷导入（§1）上落在噪声内。交付快照 1,379 文件 → +36（+2.6%），导出 5 s 里约 0.1 s。 |
| 开发任务速度 | **接近零** | 改代码的模式是 `Grep` 定位 → 读片段 → 改，不会整读 6,000 行文件。拆成 3 个 2,000 行文件后，工具调用次数基本不变。唯一确定增加的是**一次性成本**（移动代码 + 验证不破坏编译与测试）。 |

### 8.2 规模基线（2026-11-01 实测）

| 项 | 数值 |
|---|---|
| `Unity Project/Assets` 下 `.cs` 文件 | 439 个 |
| 总行数 | 117,323 |
| `Assets` 下资产总数 | 1,260 |
| ≥1000 行文件 | 19 个 / 35,778 行（占全部 30.5%） |
| 其中 `partial` 可拆 | **18 个 / 30,634 行（26.1%）** |
| 已存在 `partial class` 的文件 | 7 个（有先例，非新机制） |

最大的三个：`InboxManager.cs` 6,133 行（`public static class`，可拆）、`LogicSelfTests.cs` 5,144 行（**不可拆**，见 8.3）、`CapacityDirectiveLogic.cs` 2,263 行。

### 8.3 方法级发现：`LogicSelfTests.cs` 不能靠 partial 拆

原本按行数把它算作第二大可拆候选，查结构后发现**它不可拆**：

- 它是 `public static class LogicSelfTests`，类体内只有 **一个 `Run()` 方法**，从第 22 行写到第 5,144 行。
- 缩进统计印证：4 空格缩进仅 7 行（就是成员声明），12 空格缩进 893 行（`Run()` 内部的嵌套块）。

`partial` 拆的是**类**，而这里只有一个方法，没有可拆的类成员边界。要拆只能从 `Run()` 里**抽取方法**，那是改变结构的重构，风险与成本比 partial 高一个量级，且会触碰每次改测试都要进入的巨型方法。

**所以这里的病灶不是「文件太大」，而是「方法太大」。** 将来若那里成为痛点，要处理的是抽取方法，不是拆分文件；且必须单独评估，不能并入 partial 批次。

### 8.4 与路线 B 的关系

路线 B（程序集拆分）已因收益不可测而搁置（§3、§5）。S50+ 的 partial 拆分与 B 是**不同的事**：B 试图减少**编译输入**，partial 不改变编译输入、只改善人眼可读性。所以 §3 的实测结论既不支持也不反对 partial —— partial 从一开始就没有速度收益可谈。

### 8.5 搁置条件

不做的前提是「可读性不是当前痛点」。若将来出现以下情况，应重新评估：

- 某个文件大到难以定位改动点（Grep 命中过多、单次读取超出上下文）；
- 多人/多模型协作时，同一文件频繁冲突；
- 某个类被拆开修改（例如 Inbox 拆子模块）时，可顺带按 `partial` 分文件，边际成本最低。

测试基础设施同类处置见 S49：夹具自动清理功能已冻结现状、不再增加功能（套件本身仍承载每份交付的机器检测，不能停）。
