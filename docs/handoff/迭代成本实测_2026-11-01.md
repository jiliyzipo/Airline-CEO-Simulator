## 2. 单项占比：73% 的机器时间花在 2 个用例上

把一次完整交付闭环里的**机器时间**（不含人写代码、不含等待授权）相加：

```
Explicit 2 项      510.1 s   ████████████████████████████████████  73%
PlayMode 173 项     67.5 s   █████                                  10%
semcheck            23.2 s   ██                                      3%
Unity 启动×2        90.0 s   ██████                                  13%
EditMode + 其余      4.6 s   ▏                                       1%
─────────────────────────────────
合计              ~695.4 s ≈ 11.6 分钟
```

**这两个 Explicit 用例是 `T057OneXPlayModeTests`**（`Tests/PlayMode/T057OneXPlayModeTests.cs:105,136`）。

它们慢不是缺陷，是设计：用例验证 1× 速度下「现实 1 分钟 = 游戏 1 分钟」，因此必须**真的等满现实时间**。文件头注释写得很清楚："运行时长约 8 分钟，故标 `Explicit`"。任何加速手段都会让断言失去意义。

但有两点值得记录：

1. 它们**按设计不进默认套件**。S47 之所以跑它们，是因为"无剩余未执行项"这条汇报口径。S47 改的是 `DeptReportLogic`（纯文本投影），与 `TimeManager` / `GameSpeed` / 时钟停表毫无交集。
2. 按 Batch 逐个算：12 批 × 8.5 分钟 ≈ **1.7 小时纯等待**，换来的结论在未触碰时间系统时恒为"通过"。

## 3. 关键缺口：唯一真正决定 B 成败的数字，没有样本

用户关心的"改一个文件后要等多久"，需要的是**增量（暖）编译**时长。当前日志里**一个样本都没有**——两次会话都太短，没留下编辑后的重编译记录。

这个缺口直接决定程序集拆分（路线 B）值不值得做：

- Codex 报告算出 B 在理想 DAG 下能把"改 Logic"的重编译行数从 121,528 降到 116,185（−4.40%），"改 UI"降到 57,397（−52.77%）。
- 但**行数比例不等于秒数比例**。30 秒冷编译里有多少是 Roslyn 起停与 Unity 管线固定开销、多少与代码量成正比，没人量过。若固定开销占大头，52.77% 的行数削减可能只换来 20% 的时间削减。
- Codex 自己也在 §2.6 末尾承认了这点。

**所以：在拿到增量编译样本之前，任何关于 B 收益的结论都只是结构推算。**

## 5. 一句话结论

**目前唯一被证实的"慢"是冷启动 30 秒编译 + 8.5 分钟显式测试；前者是程序集级、后者是物理时间。**
`25→12` 这个指标对这两项都无影响。在拿到增量编译样本之前，路线 A 与路线 B 的收益都还是推算，不是实测。
