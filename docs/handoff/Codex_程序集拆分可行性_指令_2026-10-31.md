## 1. 要回答的决策问题

用户当前面临的岔路：

- **路线 A**：继续按 `Codex_Phase2_指令_2026-10-31.md` §2 的分批顺序，做 13 个文件的
  `partial` 拆分。已完成 S46（流程演练）与 S47（`DeptReportLogic.cs`，方案已确认）。
  剩余约 11–12 批。
- **路线 B**：把 `AirlineCEO.Runtime` 一个程序集拆成 `Data ← Logic ← Systems ← UI`
  四层。estimated 1–2 批。

两条路线**解决的不是同一个问题**：

- A 让单个文件变小 → 降低单次编辑的上下文体积 → **导入/编译时间零收益**（已实测确认：
  编译单位是程序集，拆 partial 不改变重编译总量）。
- B 让编译单位变多 → 改一层只重编该层及下游 → **才可能影响导入/编译时间**，但收益
  取决于编辑落在哪一层（见 §2.6）。

**你要回答的是**：B 是否真的可行？若可行，它的实际收益与风险是什么？A 已经付出的
部分沉没成本是否影响结论？用一张决策矩阵收口，给出有条件的推荐。

## 2. 必须回答的六项探测

逐项给结论 + 证据（文件路径:行号 / 统计数字 / 复现命令）。**不接受"看起来没问题"。**

### 2.1 依赖方向是否单向

- 扫 `Unity Project/Assets/Scripts/{Data,Logic,Systems,UI,AI,Testing}/` 的跨目录类型引用
  （`using`、全限定名、字段/参数/返回类型、泛型参数、特性）。
- 输出一张 **7×7 目录级邻接矩阵**（行=引用方，列=被引用方，格子=命中次数）。
- 特别确认：`Data` 是否引用 `Logic`/`Systems`/`UI`？若有，逐条列出**具体成员**，
  并判断能否靠把该成员下沉到 `Data` 解决，还是需要反向依赖。

### 2.2 是否有循环依赖

- 在 2.1 的目录级图上找**强连通分量**。若有环，列出**环上的具体类型与成员**，
  并指出拆哪一刀会直接编译失败。
- 若目录级无环，再做**类型级**抽查：是否存在 `Data` 内部的类型反向引用 `UI` 类型
  （即使目录级看起来干净，单点反向依赖也会让 `Data` 必须引用 `UI` 程序集）。

### 2.3 MonoBehaviour 的 `m_Script` 与序列化（**最高风险，必须给明确结论**）

这是唯一可能让路线 B 从"1–2 批"变成"不可做"的点。

- 统计 `UI` + `Systems` 下 `MonoBehaviour` 派生类数量。
- 回答：当 `MonoBehaviour` 类型从 `AirlineCEO.Runtime` 移到 `AirlineCEO.UI` 程序集后，
  场景 `.unity` 与预制体 `.prefab` 里按 GUID 存的 `m_Script` 引用**是否仍能解析**？
  给出依据（Unity 的序列化规则、GUID 与 assembly-qualified name 的关系），
  不要给"应该没事"这种判断。
- 若结论是"需要额外处理"，写出处理步骤与它是否会碰到
  `Codex_Phase2_指令_2026-10-31.md` §4.3「不得重命名主文件」的红线。
- 若结论是"必须先用最小样本验证才能定论"，**明确说出**这一点并给出最小样本的设计
  （选哪个 MonoBehaviour、验证什么、判定标准）。这条比猜一个结论更有价值。

### 2.4 测试程序集是否仍成立

- `Tests/EditMode/AirlineCEO.EditModeTests.asmdef` 与 `Tests/PlayMode/AirlineCEO.PlayModeTests.asmdef`
  当前 `references` 指向 `AirlineCEO.Runtime`。
- 拆成四层后，这两个 asmdef 需要加哪些引用？有没有测试文件同时引用跨层的 `internal`？
- `Editor/AirlineCEO.Editor.asmdef`（`LogicSelfTests.cs` 5555 行在里面）需要加哪些引用？

### 2.5 `internal` 可见性

- 复核上表的 8 处 `internal`。逐处判断：拆层后是否跨程序集失效？
- 结论要落到"需要 `InternalsVisibleTo`、需要改 `public`、还是无需处理"，
  并给出每处的最小改法。

### 2.6 增量编译收益的实际形态（**这条最容易被忽略**）

Unity 的增量编译规则是：改一个程序集 → 重编该程序集**及所有依赖它的程序集**。

- 据此建一个**编辑落点 → 重编译行数**的表：

| 编辑落点 | 路线 A 现在重编译 | 路线 B 拆四层后重编译 |
|---|---|---|
| 改一个 `UI` 文件 | 121,528 行 | ? |
| 改一个 `Logic` 文件 | 121,528 行 | ? |
| 改一个 `Systems` 文件 | 121,528 行 | ? |
| 改一个 `Data` 文件 | 121,528 行 | ? |

- 结合 Phase 2 的实际编辑分布（S46/S47 都改在 `Logic`/`Editor`），指出：**若日常改动
  集中在 `Logic`，拆四层能省下的重编译量是多少？** 如果 `Logic` 的下游是 `Systems`+`UI`
  （约 65,000 行），那么改 `Logic` 仍要重编约 100,000 行——**这时路线 B 的收益有多大？**
  这是本报告最关键的一个数字，请务必算出来。

### 2.7 沉没成本与批次数成本

- 路线 A 剩余约 11–12 批。按已完成批次的实际节奏（S46 一轮、S47 一轮，每轮含
  实现 + 自测 + 预检 + 用户签授权 + 你的独立复验）估一个**总轮次与总工期**。
- 明确：A 与 B 是**互斥**还是**可叠加**？（如果先做 B，A 的 13 个文件是否会自动
  变小/变得不那么必要？如果先做 A，B 的难度是否改变？）
