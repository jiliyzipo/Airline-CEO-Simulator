## 1. 病根：一格塞三件事

第 6 关原名 **「时刻协调与开航」**，同时承担三件互不相同的事：取得时刻、执行开航、排班开航。
后果是流程图上走到第 6 格就显示 **「已开航」**，而实际上：

- 运营部的航班计划**还挂在收件箱等 CEO 批准**（`route.schedulePending == true`）；
- 第 9 关（首班载客、票价生效）**从未出现在图上**；
- 「安排机型 / 机组 / 维修 / 定价」这些真正决定能不能飞起来的动作，全部没有落点。

`DisplayNode` 旧写法在 `StageGranted` 时直接 `return NodeSlot`（=6）封顶，
是所有展示层（邮件流程图、进度条、`ProgressLine` 行）共同的数据源 —— 换个界面也一样缺。

## 2. 改法：第 6 关拆开，后面补三关

| 关 | 名称 | 由谁办 | 为什么需要这一关 |
|---|---|---|---|
| 1–5 | 受理立案 → 材料与运力审查 → 航权额度核验 → 局方公示 → 批复与发证 | 局方 | 原有，未动 |
| 6 | 时刻协调（**改名**，去掉「与开航」） | 协调机场 / 战略部 | 只管槽，不再兼管开航 |
| **7** | **开航执行**（新增） | 运营部 + 机务 | 扣启动资金、核适航运力、**指派机型与机号、分配航班号**、航线建档 |
| **8** | **航班计划编排**（新增） | 运营部编班 → CEO 批准 | 班次 × 起飞时刻 × **机组产能** × **维修可用性** 四闸并行校验 |
| **9** | **投入运营**（新增） | 市场部 + 收益 | 首班载客，**票价按票价矩阵生效**，准点/维修/收益接入常规经营 |

`RoutePermitLogic` 新增 `NodeLaunch = 7` / `NodeSchedule = 8` / `NodeOperate = 9` / `NodeLast = NodeOperate`。
`NodeLast` 单独引入是为了让进度条改关数时不用再改第二处（旧代码到处写死 `NodeSlot` 当分母）。

### 状态判定（`DisplayNode`）

```
StageGranted 且 permitGate == "时刻"  → 6（已核准、缺槽）
StageGranted 且 effectPending        → 6（已发证、卡在开航执行：现金/运力）
StageGranted 且编班仍待批             → 8
StageGranted 且编班已批               → 9
```

「编班仍待批」用 `RoutePermitLogic.ScheduleStillPending`，判据是两者取或：

- 航线自己的 `route.schedulePending`；
- 收件箱里还有同 `routeId` 的 `ops_schedule` 待批件（新增 `InboxManager.HasOpenOpsScheduleFor`）。

只取其一都会错：只看邮件，会在「CEO 已批、邮件已结案、班次尚未执行」的空档里误报未完成；
只看 `schedulePending`，会漏掉「方案已递进来、CEO 还没点」那一段。

> 踩过的坑：判定里原本直接取 `GameState.Instance`，但回归里 `AddComponent<GameState>()` 的 `Awake`
> 发现已有 Instance 会立刻早退，`Instance` 仍是场景里那个壳层的状态 —— 于是 `DisplayNode` 读的是
> **别人的航线**（实测把 8 读成 9）。改成 `DisplayNode(InboxMail, GameState gs = null)` 显式注入，
> 缺省才退回 `Instance`。

## 3. 「定价 / 机组 / 维修 / 地勤」为什么不做成节点

这四项在本作里**不是开航硬闸**（硬闸只有：时刻、可用飞机、编班批准）。做成待办节点会有两个后果：

1. 节点永远不会转绿 —— 维修计划是滚动排的，机组产能是随编制变的，没有「办完」这一刻；
2. 若真把它做成闸门，等于给开航加了三道新前置，CEO 会卡在一个旧版不存在的检查上。

所以单列一节 **「开航后保障（并行，不阻塞开航）」**，如实报当前值（`InboxManager.LaunchSafeguardBlock`）：

| 项 | 报什么 | 什么时候会咬人 |
|---|---|---|
| 机组 | 每日 {n} 段，产能上限 {m} 段/日（`CrewCapacityLogic.MaxCrewedTrips`，与排班闸门同一套算术） | 加密时被排班拦下 |
| 维修 | 执飞飞机机号 + 型号 + 状态 + 停场窗口 / 下次定检排队依据 | 无机可派时航线自动停飞 |
| 地面 | 地勤编制 {n} 人（本机型建议 {m} 人） | 编制偏少影响周转与准点 |
| 运价 | 经济舱 ${x}/座（基础价 × 倍率），并指出可在「航班定价」调整 | 决定这条线赚不赚钱 |

### 10.1 崩溃栈把责任指得很清楚

```
Cleanup mono
GetManagerFromContext: pointer to object of manager 'MonoManager' is NULL (table index 5)
Fatal Error! → Crash!!!

========== OUTPUTTING STACK TRACE ==================
JsonUtility_CUSTOM_FromJsonInternal
  ← InitializeCoreScriptingClasses → GetManagerFromContext      ← 引擎侧：Mono 已拆
  ← UnityEngine.JsonUtility:FromJson<T>
  ← ExternalDataFetcher:ParseSinaFlash  (ExternalDataFetcher.cs:1290)
  ← ExternalDataFetcher:Parse          (ExternalDataFetcher.cs:1149)
  ← ExternalDataFetcher/<<RequestRefresh>b__0>d:MoveNext  (ExternalDataFetcher.cs:561)
  ← AsyncMethodBuilderCore/MoveNextRunner:Run      ← **线程池线程**
```

也就是说：`RequestRefresh` 里的 `Task.Run` 下载完，就在**线程池线程**上直接调
`JsonUtility.FromJson` 解析。`JsonUtility` 是引擎 API，只能主线程调；线程池拿到的是 NULL 的
MonoManager。平时它表现为「偶尔解析失败」，撞上编辑器退出就成了致命错误 + 非零退出码。
**与包管理器、TLS、首次导入都无关** —— 上一节把同类栈归给环境，是误判。

同样写法一共三处（`ExternalDataFetcher` 新闻/行情/汇率、`SigmetFeed`、`WeatherFeed`），
另外 `LoadTextAsync` 还在线程池上读 `Application.streamingAssetsPath`（同为引擎 API）。

### 10.2 改法：后台只下载，解析一律回主线程

新增 `Systems/MainThreadDispatch.cs`（主线程收件箱）：

| 成员 | 作用 |
|---|---|
| `Post(Action)` | 后台线程唯一出口：把「解析 + 入箱」整件投递到主线程队列 |
| `Drain()` | 主线程排空。调用点：`ExternalEventManager.DrainSource` 开头、`ExternalDataFetcher.FetchEvents`、各 `Request*Refresh` 开头 |
| 编辑器泵 | `[InitializeOnLoad]` 挂 `EditorApplication.update` 每秒排空一次 —— EditMode/批处理没有游戏时钟，不补这个泵结果会一直压在队列里 |
| `MarkQuitting()` | 退出钩子置标记：`Drain` 丢弃积压、`Post` 不再接手（退出后没有主线程会来执行它们） |
| `ShutdownToken` | 退出时 `Cancel()`：在飞 HTTP 立刻中止，免得线程池上还挂着 socket 回调 |

各管道改后形状统一为：

```csharp
Task.Run(async () => {
    var texts = new string[sources.Length];              // 只下载
    for (...) texts[i] = await LoadTextAsync(...);
    MainThreadDispatch.Post(() => AdoptDownloadedNews(sources, texts));   // 解析回主线程
});
```

顺带修掉两个隐患：
- 相对路径改在主线程用 `ResolveSource` 展开（`Application.streamingAssetsPath` 不再是线程池调用）；
- 在飞标记加了 300 秒陈旧超时 —— 否则一次丢件的下载会把整条管道永久卡死。

### 10.3 新增 `R49 main-thread-dispatch`（结构判据，不是行为判据）

只测「投递/排空」的行为还不够：这次事故发生在**断言全部跑完之后**，任何单测都会绿。
所以 R49 同时钉住源码结构：

| 断言 | 说明 |
|---|---|
| 投递不立即执行 / 排空按序 / 单件异常不连累 | `Post` + `Drain` 语义 |
| 退出中丢弃 | `MarkQuitting` 后 `Post` 不收、`Drain` 清空（用 `try/finally` 复位，避免污染同一编辑器） |
| 取数管道只在线程池下载 | 扫描三个管道文件里每个 `Task.Run` 的括号体：出现 `JsonUtility` / `Application.` / `Resources.` / `GameObject` 即判红；体内没有 `MainThreadDispatch.Post(` 也判红 |
| 判据自身的负面控制 | 用内联样本验证「带 JsonUtility 的 `Task.Run` 会被抓到、合法写法不会被误报」——否则这条扫描只是恒真的摆设 |
| 退出掐断在飞下载 | 五个取数文件都必须把 `MainThreadDispatch.ShutdownToken` 交给 `HttpClient` |

扫描前会剥掉注释，否则连「这里不能用 JsonUtility」这句说明本身都会命中（第一版就是这么误报的）。

### 10.5 为什么不能靠「复现崩溃」来证明修好了
