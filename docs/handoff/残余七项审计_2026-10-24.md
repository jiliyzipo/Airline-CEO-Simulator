### 3.2 为什么这条卡了 6 天：1× 就是 1:1 真实时间

`Systems/GameSpeed.cs`：

```text
GameMinutesPerRealSecond = { 1f/60f, 1f, 3f, 0f, 24f }
                           1×      2×  3×  ‖   DevDay
```

1× 下 **1 现实秒 = 1 游戏秒**，即 1 游戏分 = 60 现实秒。换算后果：

| 事件 | 常量 | 1× 真实等待 |
|---|---|---|
| 运力呈报 | `InboxCadence.ReportHours = 2` | **2 小时** |
| 决策回执 | `ReplyHours = 4` | **4 小时** |
| 节点进度 | `ProgressHours = 6` | **6 小时** |
| 一个游戏日 | — | **24 小时** |
| 一个季度（90 日） | — | **2160 小时 ≈ 90 天** |

任务书要求「新建与接管两类开局检查等待、读邮件、返回详情和继续推进」——
若按"完整一局"理解，那是**坐 90 天**。这不是测试成本问题，是**条款与实现不兼容**。

### 3.3 建议（需用户裁定，我不擅改）

把 T05.7 的证据标准从"完整 1× 会话"下调为**"单事件延迟实测"**：

> 两类开局各做一次：切 1×，记下游戏时刻与墙钟，等到**一封** 2 游戏小时的运力呈报到达，

### 5.2 两个需要裁定的点

1. **「歧义先确认」的口径**。现实现是「**不猜，退回要班号**」，不是「提出一个猜测让你确认」。
   两者都能满足「歧义不得擅自改台账」，但字面上「先确认」通常指后者。

## 6. T05.6 · 备选时刻件的六个字段

构件：`SlotCandidateLogic.FormatBody`（正文）+ `BuildProsCons`（利弊）；
邮件由 `InboxManager.QueueSlotCandidates` 生成。

| 要求字段 | 状态 | 实际渲染 |
|---|---|---|
| **机场** | **有** | `　各停站　本场端 FRA 到场 17:00 · 离场 06:30 …　对端 …`，经停站另有 `　经停端　…` |
| **时刻** | **有** | `候选 1　06:30 起飞的往返（运营部推荐）`；逐站 `到场 HH:mm · 离场 HH:mm`；回程时刻由轮挡+过站推出并吸附系列 |
| **逐停站需求** | **有** | 本场端 + 对端 + 每个经停各一行；状态词 `即刻可排 / 需申请 / 需改时 / 拿不到 / 无需槽`；并有 `经停站一趟往返停两次，故要 2 对` 的解释 |
| **优缺点** | **有** | `　有利　…` / `　代价　…`，且**只写台账能算出来的事实**（持仓、机队、宵禁、间隔、位移分钟数） |
| **费用／免费渠道** | **有** | `　取槽成本　协调池申请 0（排队）／二级市场约 N 万`；口径段列出三条渠道（协调池免费下季 / 二级市场付费同期 / 改时免费批准即用） |
| **预计办理时点** | **缺（只有相对说法）** | 全文只有 `本季即可排班` / `免费，下季交割` / `批准即用，不必等新槽`；**没有「第X年 QY」**。对照：许可类邮件是印 `预计 第{ey}年 Q{eq} 批复` 的 |

### 6.1 可行性：已经能被真实约束检验

选项只从 `viable` 生成；逐站状态取自**实时持仓与池容量**；机队来自真实轮挡规划器；
宵禁、串飞间隔都参与计算；所有时刻吸附到 30 分钟系列网格。回归断言 `opts.Count >= 2`
且每一条都 `AllSeriesAligned`，正文含 `有利`/`代价`。

**一个诚实的边界**：只有「槽」这一侧会被过滤。某条备选如果**派不出机**（`aircraftOk == false`）
或撞宵禁，**仍会列出来**，只是写在「代价」里、按钮写着 `无机可派`。
所以「每条都可检验」成立，「每条都可行」不成立——条款要的是前者。

### 6.2 这条的修法很小

`FormatBody` 手里就有 `gs`，`InboxManager.NextQuarter(year, quarter, out ny, out nq)` 是现成的公开助手。
把「下季交割」换成「第{ny}年 Q{nq} 交割」即可；利弊文本里的同一句需要在构建期一并带上这个标签。
**不需要新增数据结构，也不需要动可行性判定。**

### 8.5 两个从矩阵里读出来的结构性问题（比"逐项裁定"更要紧）

**① 难度只改期初现金，几乎不改损益。**
对照同一（航司类型, 宏观）的三档难度：净利**逐位相同**——全服务/繁荣 = 1248/1248/1248，
低成本/滞胀 = −1122/−1122/−1122，支线/滞胀 = −805/−805/−805。60 组合实际是
**20 个损益情景 × 3 个起始现金**。

原因查实：`StressTestRunner` 传入的 `irropsSeverity`（简单 0.80 / 标准 1.00 / 困难 1.25）
只作用于**一次性的 IRROPS 现金冲击**（`OpsIrropsLogic.Resolve` 的 `cashDeltaWan`），
而这次冲击的 0.8 / 1.0 / 1.25 倍在全年净利里只值 ±6 万，相对 400–625 万的期初现金差
（±125 万）可以忽略。

**② `TotalNetProfit` 不含 IRROPS 现金冲击，所以「净利」和「期末 − 期初」对不上。**
`AirlineYearSimulator` 里 `totalProfit += pnl.NetProfitWan` 只累加月度损益，
`irropsCash` 直接进 `cash` 却不进 `totalProfit`；破产组合另有跑道告急贷款（日志里
`[FIN] 跑道告急→银行贷款 294 万`）也进现金不进损益。
验证：全服务/繁荣三档 —— 期初 625/500/400、净利均 1248、期末 1853/1723/1616，
`期末 − 期初` = 1228 / 1223 / 1216，比 1248 少 **20 / 25 / 32**，
恰好是 −25 万 IRROPS × 0.80 / 1.00 / 1.25。

> 这条对 T04.3 有直接影响：如果将来有人拿这张矩阵当"现金对账 oracle"，会得出
> 「净利 ≠ 现金变化」的错误结论。**矩阵是情景投影，不是台账。** 这跟 §7 的结论一致。

（它不构造 `GameState`）。第一版直接在 `ThisQuarterLabel` 里读 `gs.year` 就把离线校验打崩了

先想一遍离线工具会不会传 `null`** —— 否则「Unity 里全绿、工具里崩」会来回拉锯。
