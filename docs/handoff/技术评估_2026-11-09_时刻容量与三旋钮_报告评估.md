## 1. 代码事实核查（报告 §7 的 P0 五项，逐条答复）

### 1.1 有没有写死「81」？

**没有。** 全库 `rg "\b81\b"` 只命中两处注释与一处 `MenuItem` 优先级，没有数组长度、循环上界或枚举依赖。

但「81 可扩充」只做到了**一半**：新增一座机场要同时改 **4 张按 IATA 字符串对齐的表**，编译器不管它们是否一致：

| 表 | 作用 | 缺了会怎样 |
|---|---|---|
| `Data/AirportCatalog.cs` 的 `All[]` | 机场名、等级、协调属性 | 机场不存在 |
| `Data/AirportRunways.cs` 的 `Counts` | 跑道数（= 当前容量） | **静默落回「按等级猜 3/2/1」**（回归 ⑨ 会报警，但只对协调机场） |
| `Data/AirportGeoCatalog.cs` 的 `All[]` | 经纬度 | 地图/距离类功能失效 |
| `Data/CityEconomyCatalog.cs` 的 `All[]` | 客货吞吐、城市 | 等级推成 0 → 掉成支线 → 协调属性丢失 |

> 结论：报告要求「新增机场只录入数据、不改算法」——**算法确实不用改**，但「只录入一处」不成立。这是可接受的现状，但必须在新增机场流程里写成检查单（现有 `AirportCatalogRegression` ⑨ 已覆盖「协调机场必须有显式跑道数」这一条）。

### 1.2 容量的唯一权威在哪里

```
AirportCatalog.QuarterCapacityRaw(code, tier, coordWindow, minutes)
  → 协调窗口外 / 宵禁 → 0
  → 否则 return RunwayCountOf(code, tier) * SlotsPerRunwayPerQuarter   // SlotsPerRunwayPerQuarter = 1
```

调用链（**只有一个入口，这是好消息**）：

```
QuarterCapacity(code, minutes)            ← 逐刻容量（唯一判据）
   ├─ HourCapacity → DayCapacity           ← 报表 / 界面日总量
   ├─ BandCapacity → slotCapacity[4]       ← 四个池的总量（段宽 40/20/20/16 刻）
   ├─ RoutePermitLogic.SlotPoolCapacity    ← 申请/买入/满池判据
   ├─ RoutePermitLogic.SlotsAvailableAt    ← 逐刻余量（玩法的硬闸门）
   ├─ IndustryAirlineLogic.ClockCaps/Chips ← 他航铺排上限
   └─ tools/slotreport/Program.cs          ← 只读报表（CSV/HTML）
```

**`RunwayCount` 除了 `AirportCatalog` 内部与回归之外，没有任何业务代码直接读它**（全库仅 6 处命中，全在 `AirportCatalog` 与 `AirportCatalogRegression` 里）。

这意味着「把容量从跑道数换成申报值」的**改动面极小**：只要换掉 `RunwayCountOf` 的返回值，整条链自动跟着变，UI 不需要动（UI 不显示跑道数）。

### 1.3 单位与 1:1 的真相

报告 §1.3 的单位推导是对的，但当前代码的实际口径比报告假设的还要「低」：

- `QuarterCapacity` 是**每刻、每方向**的槽数（离港池与到港池各取这个数）。
- 因此 `1 条槽/刻/方向` = `4 刻/时 × 2 方向` = **8 架次/时**。
- 现行 `SlotsPerRunwayPerQuarter = 1` ⇒ **一条跑道 = 8 架次/时**，而现实单跑道约 28–45 架次/时。

**规模阶梯（按每刻每方向合计，81 场，不含宵禁）**

| 口径 | 每刻每方向合计 | 占 1:1 | 日双向架次（名义） | 日双向（扣宵禁/窗口后，实测） |
|---|---|---|---|---|
| 现实 1:1（= 除数 8） | 855 | 100% | 164,160 | — |
| 除数 12 | 571 | 66.8% | 109,632 | 102,912 |
| **除数 16** | **435** | **50.9%** | **83,520** | **78,400** |
| **现状（跑道平铺）** | **249** | **29.1%** | **47,808** | **44,656** |

> **重要换算：现状 ≈ 除数 27.5**，不是 22。报告里「除数 16 作基准」意味着**世界容量要在现状上再放大 1.75 倍**——请按这个理解去判断是否接受，而不是按「砍到现实的一半」理解。

### 1.4 到港 / 离港同数：报告 §1.3 的风险是真的

```csharp
public static int SlotCapacity(string code, int band, string kind)
{
    _ = kind;                       // ← kind 被丢弃
    return SlotCapacity(code, band);
}
```

`QuarterCapacity(code, minutes)` 同样不带方向。所以「一格一个数、两个方向共用」是现状。

把它换成申报值后，取整会导致**双向总量超发**：

| 除数 | 对称取整（两池同数）每刻双向 | 按总动作取整 | 超发 |
|---|---|---|---|
| 8 | 1,710 | 1,714 | −0.2% |
| **16** | **870** | **855** | **+1.8%** |
| 12 | 1,142 | 1,143 | −0.1% |

即 D16 下全球约多出 **1.8%（≈1,500 架次/日）**，单场最多多 2 架次/时。报告说「不能给每格离港和到港都配 6 导致小时合计 48（应为 44）」——这个警告是准确的。

**但代价要先说清**：要做到严格守恒，`QuarterCapacity` 必须加 `kind` 参数，`SlotCapacity(code,band,kind)` 的两端要给出不同数（如 LHR 每刻 6/5），**这会同时改掉 `SlotsAvailableAt` 的签名与全部回归夹具**。若不做，就接受 1.8% 超发并在文档里注明。这是本次改造中**唯一一个「要么改签名、要么认误差」的硬选择**（见 §9 裁决项 B）。

### 1.5 存档：好消息与坏消息

- **好消息：容量不进存档。** `slotCapacity` 是静态构造期算出来的运行时字段，`GameState` 里没有它。改容量公式**不会**让旧档结构失效。
- **坏消息一：没有 schema 版本号。** 全库搜不到 `saveVersion` / `schemaVersion`；迁移靠 `MigrateSlotTimes` / `MigrateLegacyBudget` 这类**幂等补救函数**逐个调用。容量一旦变化，「旧档持仓超过新容量」没有任何地方会检测——不会崩，但会静默出现「池 12/10」这种读数。
- **坏消息二：`SlotsAvailable` 对负值做了钳 0**，所以超配不报错、只表现为「莫名其妙没有余量」。

### 2.1 差异的性质分类（这决定了工作量）

- **A 类·只缺数据，不缺结构（便宜）**：把跑道数换成申报值。因为 `RunwayCountOf` 是唯一出口，改动被 `AirportCatalog` 封死。
- **B 类·缺维度（中等）**：方向（DEP/ARR 不同数）、生效日期（航季）、时区。
- **C 类·缺机制（贵）**：容量演进事件、协调等级分化、AI 行为。
- **D 类·报告漏掉的（最贵也最关键）**：AI 占用分布算法（§2.3）。

### 2.2 报告 §1.4 的算法在本项目可以大幅简化

报告给的伪代码是：

```
S = 8 / 除数
M(h) = D(h) × S              # 小时总动作预算
把 M(h) 分到 4 个 15 分钟格（整数守恒）
每个格再分离港/到港
```

这套东西解决的是「**有小时曲线时，怎么在 4 个格里做整数分配且不超发**」。

但本项目的容量是**平的**（用户 2026-11-09 裁决：跑道数就是每刻容量，不设峰刻），且池的粒度是「4 个时段」，不是「96 个小时」。于是：

```
若 D(h) = D（常数）：
    每刻每方向 = D × S / 8 = D / 除数
```

**整条算法退化成一个整数常量**，不需要任何分配循环：

```text
每刻每方向槽数（单场） = max(1, round(申报架次/时 ÷ 除数))

数据侧只保留一条物理校核（防止把手填错）：
    申报架次/时 ≤ 60 × 物理跑道数        # 单跑吞吐物理上限约 45–55，60 是宽松天花板
```

于是实现上它**就是** `EffectiveRunways.Overrides` 已经在做的那个「等效跑道」机制，只是把值从「跑道数」换成「申报值换算值」。

> ⚠️ **注意：现有的「等效 ≤ 物理×2」这条护栏必须换掉。** 它成立的前提是「一条跑道 ≈ 8 架次/时」（现行口径），而申报值的量级是 28–45 架次/跑/时。实测会被旧护栏判红的至少有两家：
>
> | 机场 | 物理跑道 | 申报/时 | D16 每刻槽 | 旧护栏上限 |
> |---|---|---|---|---|
> | ATL | 5 | 220 | 14 | 10 → **判红** |
> | LHR | 2 | 88 | 6 | 4 → **判红** |
>
> 正确的护栏是「申报值本身 ≤ 60×跑道数」，不是「换算后的槽数 ≤ 2×跑道数」。

> 也就是说：报告 §1.4 描述的是一台**为将来留的**通用机器；当前只需要它的退化形态。建议先做退化形态（一个标量），把「逐小时曲线」「航季切换」留在接口里，等真的有分时数据再启用。这与报告 §5 的「P0 只做设计与低风险」是一致的。

### 2.3 报告没写、但代码里确实存在的一处结构性问题（最重要）

`IndustryAirlineLogic.FillWave` 的真实行为不是「先把高峰填满」，而是**轮转填充**：

```
for k in 1..want:
    for t in 0..n-1:
        j = order[cursor % n]; cursor++
        if perQ[j].Count < capAt[j]: 放一条; break
```

`order` = 该段所有刻按 `HourDemandCoef`（与槽价同源的小时需求系数）降序。于是：

- 每轮循环给**每个刻各加一条**（均匀底座 `m = floor(cap × 占用率)`）；
- 余数 `r = want − m × n` 只落在**权重最高的前 r 个刻**上。

由此得到一条**可验证的判据**（本轮实算确认）：

> 设每刻容量为 `C`、占用率为 `r`。底座 `m = floor(C×r)`；当 `C ≤ 1/(1−r)` 时 `m = C−1`，
> 段内余数会集中在权重最高的刻上，**最挤的那个小时恰好被填满（0 余量）**；
> 只有 `C > 1/(1−r)` 时（87% 下即 `C ≥ 8`），最挤的小时才留得出 1 条。

实测（87%）：

| 机场 | 每刻容量 C | 最挤小时的余量 | 有自由槽的小时 |
|---|---|---|---|
| XMN | 1 | 07/08/09/12/18 全 0 | **只有 04:30–05:45、10:00–10:45、15:00–15:45、23:00–23:45** |
| ATL | 5 | 07/08/09/12/18/20 全 0 | 其余每小时各留 1–4 条 |
| LHR（D16） | 6 | 07/08/12/18 全 0 | 其余每小时各留 4 条 |
| ATL（D16） | 14 | 08 时余 4（每刻 1） | 全小时都有余量 |
| ATL（D16·75%） | 14 | 全部有空 | 每小时 12–16 条 |

**三条结论：**

1. **「最挤的那小时永远没有免费槽」不是设计失误，是 `floor(C×r) = C−1` 的算术必然。** 只要 `C ≤ 1/(1−r)`，无论容量多大、除数是 12 还是 16，峰刻都会被填满。
2. **放大容量只对「大机场」有效**：C 越过 `1/(1−r)` 之后峰刻才出现余量。实测 D16@87% 下，
「08 时有空」的 15 家与「每刻容量 ≥ 8」的 15 家**完全同一集合，无一例外**——判据是精确的，不是近似。
3. **降低占用率是最直接的杠杆**：75% 时阈值降到 `C ≤ 4`，只有 25 家小机场峰刻仍满。

这不是 bug，是「按需求权重落位」+「段级比例占用」两条设计叠加的直接推论。它是本报告最需要你先裁决的一件事（§9 裁决项 A）。

## 4. 影响面（报告 §4.2 的五条，逐条核实）

### 4.1 机场时刻申请

**受影响，但都是「数值变、逻辑不变」。**

- 申请闸门 `SlotsAvailableAt` 只问 `QuarterCapacity − 我司 − 他航`，容量变大 ⇒ 余量变大 ⇒ 更容易申请。
- 免费协调池的申请是**按序分配、不收费**（`InboxManager` 的 `QueueSlotApplications`），所以容量放大直接等于「免费通道变宽」。
- ⚠️ **一个真实风险**：`NearestClaimableClock` 会把申请时刻吸附到最近的「当时真能申请」的刻。高峰锁死时，申请单可能被吸附到 03:00 这种刻上——排班器随后会认为「你有 03:00 的槽、却想 08:00 飞」，两者互相打脸。容量放大后这种现象**不会消失**（因为高峰仍满），只会把吸附距离缩短。

### 4.2 二级市场

**受影响，而且是「反向」的。**

- 挂牌量、叫价都来自 `SlotMarketLogic`，其中 `FairValueWan` → `StrategyEconomics.SlotValueWanAt` **只看机场等级与小时系数**，**完全不看容量**。
- 所以：容量放大 1.75 倍 ⇒ 槽的可获得性上升，但**同一条槽的价格一分不变** ⇒ 二级市场的稀缺溢价被稀释，市场存在感下降（除非占用率维持 87% 让高峰继续锁死）。
- 他航挂牌的溢价路径是 `fair × AskPremium(1.15)`，同样与容量无关。
- ⚠️ **不一致点**：如果将来容量按「富余档 F」上调（第三旋钮），而价格不跟着动，就会出现「TSN 的槽和 PEK 的槽一个价」——这是必须一起解决的经济耦合（见 §5.4）。

### 4.3 航线经营

- 排班四道闸门（时刻槽 / 值勤 / 机队 / 机组）中，只有第一道受容量影响。
- 容量放大 ⇒ `ApplyWaves` 能排出的波次变多 ⇒ 周班次上升 ⇒ 收入上升。
- ⚠️ **这是最需要警惕的连锁**：`RouteFrequencyModel` 的周班次上限由「市场需求的单机可飞量」决定，而需求是按**城市对**独立估算的，没有「机场总量预算」这一层。所以容量放宽 = 打开更多线 = **利润近似线性增长**，而成本侧（机组/机队/燃油）是按班次线性增长的，只有**地面与时刻成本**是准固定。报告 §4.2 的警示（「需求侧与收益模型未校准前，不得把放宽容量视为已完成经济平衡」）在此处**完全成立**。

### 4.4 财务结算

- 时刻购入是**一次性现金支出**（`cost = SlotValueWanAt(...)`），**不进资产负债表**（全库搜不到把 `slots` 计入估值的地方）。
- 因此容量变化对财务报表的影响是**间接的**：能买的槽变多 → 现金支出与折旧/摊销不变 → 但航线收入上升。
- **不受影响**：季度结算、董事会 KPI、税费、地面服务费的结构。
- ⚠️ **建议补一条**：既然槽是「无账面价值的准固定资产」，容量上调会放大「隐性资产」的规模而不体现在报表里。若将来做并购/估值，需要把 `slotValue × 持仓数` 计入非账面资产，否则估值会低估。这条**本轮不做**，只登记。

### 4.5 存档

| 项 | 结论 |
|---|---|
| 旧档能不能加载 | **能**。容量不在存档里 |
| 旧档持仓会不会丢 | **不会**（没有任何地方删槽） |
| 旧档会不会超配 | **会**：若某场容量下调，旧档持仓 > 新容量 → 池读数 `12/10`，`SlotsAvailable` 钳 0，不崩不报 |

### 5.2 五个关键读数

1. **除数几乎不改变「最挤那一小时」的可用性。** 87% 下，08:00 有空刻的机场从 1 家 → 15 家 → 25 家，但「06–22 余量/容量」稳定在 **11–12%**。原因是占用率是比例制：容量放大，AI 占用同比例放大。**报告「旋钮①不是难度旋钮」的判断被数据证实。**
2. **最挤那一小时是算术性锁死的。** 判据见 §2.3：`C ≤ 1/(1−r)` 时峰刻 `floor(C×r) = C−1`，余数挤进最高权重刻 ⇒ 恰好填满。87% 下阈值是 `C ≤ 7`，所以只有申报容量 > 约 112 架次/时的大机场（D16 下 15 家）才能在峰刻留出 1 条。**改除数解决不了这件事，只有改占用率或改取整方式才行。**
3. **D16 把「每刻只有 1 条」的机场从 5 家降到 1 家**（SAN/XMN/SYX/ZUH/TNA → 只剩 SYX）。这是除数真正的价值：**分辨率**。每刻 1 条时，玩家在小机场只有 4 个可用窗口（04:30–05:45、10:00–10:45、15:00–15:45、23:00–23:45）；每刻 2–3 条时窗口显著变宽。
4. **D16 让「全天有槽可申请」的机场从 2 家升到 20 家**（87% 下），平均可用小时 7.0 → 10.7（满值 17）。这是玩家真实感受到的改善，也是除数最值得买的那部分收益。
5. **现状 87% 下，06–22 约 11% 的槽是空的**，但分布不是「集中在午后」，而是「**除权重最高的那个小时外，其余每个刻各留 1 条**」（枢纽 C=5 时：07/08/09/12/18/20 全满，其余每小时余 1–4 条）。小机场（C=1）则只剩 4 个窗口。玩家想在最挤的小时开线，只能走二级市场。

> **更正一条旧结论**：`docs/handoff/阶段记录_2026-11-09_机场时刻容量模型调研.md` §10 写的「`cap = 1` 时 `floor(1×0.87)=0`，AI 占 0 条，玩家可稳定拿满 → 白送」**是错的**。
> 实测代码：`IndustryHeldOfKind` 用的是 `SlotPoolCapacity(airport, band)`（**段总量**，如 40 刻 × 1 = 40），目标是 `floor(40×0.87)=34`，再由 `FillWave` 摊到逐刻。所以 `cap=1` 的机场只是「40 个刻里 34 个被占、6 个空着」，**不存在整场白送**。除数 22 / 27 的「8 场 / 14 场白送」结论应作废。

## 8. 需要你裁决的事项（本轮就卡在这里）

### 裁决项 A：最挤那一小时要不要留出空槽？

数据事实（§2.3、§5.2）：87% 占用下，81 场里只有 1 家在 08:00 还有空槽，原因不是「AI 故意抢峰」，而是 `floor(C×r) = C−1` 的取整必然。**改除数解决不了**（只有申报 > 约 112 架次/时的 15 家大机场能越过阈值）。

- **A1（推荐先做）只把占用率做成可调**，用 75% 跑一版。阈值从 `C ≤ 7` 降到 `C ≤ 4`，只有 25 家小机场峰刻仍满，其余枢纽峰刻各留 1 条。**零算法改动，只改一个常量**，是验证「压力 vs 可进入性」最便宜的一步。
- **A2 把 `MustLeaveOpen` 从「整段留 1 条」升级为「每刻留 1 条」**：AI 每刻最多占 `C−1`。效果是**任何时刻都留 1 条免费槽**（哪怕是 08:00），代价是 C=1 的机场 AI 直接归零 → 必须限定 `C ≥ 2` 才启用，或与除数 16 一起上（D16 下只剩 SYX 是 C=1）。改动约 5 行。
- **A3 不改**：把「高峰必须买」当作核心玩法，靠二级市场入口与报价做得更好用来补偿。

> 说明：报告与本文早前设想的「改成逐刻比例占用」其实**就是现状**——`FillWave` 已经是「每刻各加一条、余数给高权重刻」，等价于逐刻比例占用。真正能改变峰刻的只有 A1（降占用率）与 A2（每刻硬留 1 条）。

### 裁决项 B：离港/到港容量要不要严格守恒？

- **B1（推荐）**：两池同数（现状结构），接受最高 2 架次/时/场的超发（全球 +1.8%），在文档注明。**零签名改动。**
- **B2**：按 `round(2D/除数)` 取整后拆成 `ceil/floor` 两端（如 LHR 6/5）。严格守恒，但要给 `QuarterCapacity` 加 `kind` 参数，全库夹具连锁。

### 裁决项 C：P1 上线时的默认除数

- **C1（推荐）**：默认 27（等价现状），先验证结构，再单独做 27→16 的平衡实验。
- **C2**：直接默认 16，一次到位（风险：结构问题与平衡问题同时出现，难定位）。

### 裁决项 D：M1–M6 的定位

- **D1（推荐）**：只作文档与「缺数据时的兜底估算」，不进算法。
- **D2**：做成代码里的枚举，参与容量估算。（会引入第二套容量来源，与「申报值为首选」冲突。）
