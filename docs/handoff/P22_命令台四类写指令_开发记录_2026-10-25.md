# P22 · 命令台四类写指令（开线 / 购机 / 招聘 / 融资）开发记录（2026-10-25）

## 一句话

命令台不再只有「问」：`开通北京—纽约`、`买 2 架 A320neo`、`招聘 10 名飞行员`、`申请银行贷款`
四类写指令都能认出来，并且**只把参数交给既有呈报管线**（`InboxManager` 的四个 Offer/Queue 方法），
产物是一封标准请示件，由 CEO 在收件箱批一次 —— 与页面按钮完全同一条路。

## 一、为什么不是「弹确认卡」

关线（`TopicCloseRoute`）走的是确认卡 → `RouteCloseLogic.Execute`，因为**那句话本身就是终局动作**：
认错一个机场，一条在营航线当场没了，且不可撤销。

这四类不是。它们的产物**本来就是请示件**，真正的决定点是收件箱里那封函 —— 批错了还能驳回、退回。
再叠一道确认卡等于同一件事问两遍（`DeptReportLogic.DeptAnswer.needsRun` 的注释里已写过这条理由，
运力调令就是这么定的）。所以四类走 `needsRun`：命令条上只回一行回执，信已经进了收件箱。

## 二、为什么不让命令台自己执行

这是本次唯一的结构性约束：**不另建第三套执行路径**。
购机批了要扣钱、招聘批了要占编制、融资批了要进负债表 —— 每一笔都有自己的账务口径，
命令台若自己算一遍，就会和页面按钮算出两个数。所以：

```
命令台一句话
  → CeoCommandRouter（只认意图与参数，纯函数）
  → DeptReportLogic.Build（只做参数快照，不写账）
  → DeptReportLogic.RunPending
  → 既有的 InboxManager.OfferFleetBuy / OfferHrRecruit / OfferFinanceLoan / QueueOpenRouteStudy
  → 收件箱请示件（CEO 批复）
  → 既有的批复管线（本次未改动）
```

`RunPending` 存在的理由：命令条（UI）不该知道「哪类指令走哪个方法」。否则壳层会长出第二张分派表，
与路由那张迟早对不上 —— 那种分叉通常只在某次改口径时漏一处，事后极难发现。

## 三、路由判据（一句话一张表）

四类共用一道闸 `LooksLikeRequest`：句子里出现
`汇报 / 报告 / 简报 / 情况 / 进度 / 现状 / 多少 / 多久 / 怎么样 / 如何 / 为什么 / 吗 / 呢 /
是否 / 能不能 / 可不可以 / 分析 / 评估 / 看看 / 说说`
就不是写指令，一律留在读类。

理由：「汇报融资情况」里有「融资」、「招聘进度如何」里有「招聘」，
若只看名词，CEO 会收到一封自己没下过的请示 —— **信是收不回来的**，
这比少认一句写指令严重得多，所以闸门宁可关得紧一点。

| 指令 | 正例（→ Act） | 反例（→ 仍是读类 / 退回引导） |
| --- | --- | --- |
| 开线 | `开通北京—纽约航线` → PEK/JFK | `分析开通北京—纽约航线的可行性` → 战略部分析件；`开通一条新航线` → 退回引导（缺两端机场） |
| 购机 | `买 2 架 A320neo`、`引进两架B737-800，融资租赁`、`采购 3 架 A321neo 经营租赁` | `买A320neo`（缺架数）→ 退回引导；`机队现在几架`、`为什么买飞机这么贵` → 读类 |
| 招聘 | `招聘 10 名飞行员`、`招五名乘务员，猎头挖角`、`紧急招聘 20 名机务工程师` | `招聘飞行员`（缺人数）→ 退回引导；`招聘进度如何` → 读类 |
| 融资 | `申请银行贷款` / `办理高息过桥` / `申请股东增资` | `汇报融资情况`、`贷款还剩多少` → 读类 |

### 三个刻意写死的细节

1. **机型最长命中**。目录里 `A320` 是 `A320neo` 的前缀、`B737-8` 是 `B737-800` 的前缀。
   取第一个命中会把 737-800 的订单记到 MAX 8 上 —— 两架飞机、两种航程、两个价。
   实现见 `CeoCommandRouter.MatchAircraftType`（取最长），回归里有 `B737-800` 与 `A320neo` 两条反例钉住。
2. **缺参数不猜**。没写架数/人数就不下请示（1 架和 10 架是两笔完全不同的钱）。
   `TryReadCount` 只负责读，不提供「猜一个」的选项；汉数字（两/五/十/十五）同样认。
3. **采购方式一字不差**。`自有资金买断 / 融资租赁 / 经营租赁 / 二手引进` 与购机决策会四个按钮同字，
   否则批准后会落到别的付款口径上（买断要全额首付，租赁只要 10%）。

## 四、开航研究会正文：从 UI 抽到 Logic

命令台说「开通北京—纽约」，与页面选完机场点「提交研究」必须是**同一份研究会纪要**。
原来那段正文（距离 → 引力模型 → RPM 评估 → 六部门意见 → 准入办理 → 请示事项）
长在 `OpenRouteDecisionFlow.BuildStudyMailBody` 里，是 UI 的私有方法。

本次抽成 `Logic/OpenRouteStudyLogic.Build(gs, origin, dest, via)`，返回 `Plan{ok, reject, path, subject, body, distanceKm, rpm}`：

- `OpenRouteDecisionFlow.SubmitStudy` 改为调用它（`_previewRpm = plan.rpm` 保持不变）；
- `DeptReportLogic.RunOpenRoute` 同样调用它，再交 `InboxManager.QueueOpenRouteStudy`。

距离口径也一并归位：`AirportGeoCatalog.GreatCircleKm`（`MapWidget.GreatCircleKm` 本来就是它的转发）。
**否决判据提前**：`RouteGeography.IsPlausiblePassengerOd` 先跑，不成立就不算日利 ——
否则会产出一封看起来很专业的信，却在推销一条不该存在的航线。

## 七、已知边界（明确不做）

1. **经停不解析**。命令台的开线一律直飞；要经停请用地图/弹窗选。`CeoAsk.via` 字段留着，等有真实需求再接。
2. **融资不带金额**。`OfferFinanceLoan(gs, kind)` 本来就没有金额参数 —— 额度由财务部按信用评级算。
   命令台只表达「走哪种融资」，不另立一个金额口径。
3. **机型必须写目录里的型号**（`A320neo` / `B737-800`）。不认「波音 737」这类俗称：
   目录里 737 有 NG / MAX 两族共十来个型号，猜错就是两个价。
4. **招聘渠道默认校招、紧迫度默认「较急」**。句子里写「猎头挖角 / 海外引进 / 内部转岗」才改；
   这两项不影响人数与成本口径，且请示件里原样写出，批复前看得见。
5. 写指令**不改台账**：所有扣款/占编/负债都发生在收件箱批复之后，走既有管线。
