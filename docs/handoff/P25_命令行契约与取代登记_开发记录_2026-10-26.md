## 一、这一阶段修的四件事

S14 收口后仍留下四处“工具说的和实际发生的不是一回事”，都属同一类：命令接受了它并不理解的输入，或者状态字段停在旧结论上。

### 1. 未知参数被静默丢弃（D3）

`parseArgs` 对任何 `--xxx` 都照单全收，没人校验。实际的代价是：`stage-review --dry-run`——`--dry-run` 只存在于 `stage-close`，但 `stage-review` 既不认识它也不拒绝它，于是一次读起来像“先预演一下”的调用，真的跑完了整场检测（`REV-20261026121713-f02d73`，见 `S14_误触检测事件_2026-10-26.md`）。

现在每个命令在 `COMMAND_FLAGS` 里声明自己认识的参数，`assertKnownFlags` 在分发前比对：

- 未声明参数 → `EXIT.USAGE(2)`；
- 错误信息同时给出未知参数名与**该命令**可用的参数清单（`allowed`），拼错时不用再去翻源码；
- `--json` / `--help` 作为全局参数保留。

### 2. `stage-review --dry-run` 没有只读语义

补上真正的预演：解析目标交付、profile、快照完整性、机器可判定条款、仍需检测者补证的条款，以及“已有终态结论（真实执行会直接返回它）”。它在**授权之后、加锁之前**返回，因此既不能用来绕过权限试探交付，也不写 review、不登记 issue、不动 revision、不留锁。

### 3. 通过之后 `devStatus` 停在 `rework`

`review-finish` 原本只在 `freshness=stale` 时把 `devStatus` 写成 `rework`，passed+current 分支完全不动它。于是一次失败过的任务即使后来通过，看板仍显示 `rework/passed`——`S06-BatchB` 和 `S14-CollabBinding` 都是这么来的。

现在的口径：

- `conclusion=passed` → `devStatus=ready_for_review`（`review-finish` 与之后的 `refreshFreshness` 都会这么做，历史遗留也一并healing）；
- 工作区变动只体现为 `freshness=stale`，待办里写“历史检测已通过，但工作区已变，需按当前代码复验”；
- 只有 `failed` / `blocked` 才回到 `rework`。

一开始我把 stale 也算作 rework，测试写完才发现那会把 S14/D2 引入的 stale 提示整段变成死代码（所有 stale 任务都掉进“按缺陷修复后重新 deliver”），于是改回“staleness 归 freshness，rework 归失败”。

### 4. 取代关系只能在交付当时声明

`stage-close --supersedes` 只能在写新交付的那一刻盖章。S13 先改 `tools/collab`、S14 继续改同一批文件并独立通过，S13 的交付在实质上是**被取代**，而不是“需要按当前代码复验”——但没有任何命令能这么说，于是它的任务永远挂在 `passed/stale` 上，还带着两次“需复验”的催促；真要复验，跑的也是旧快照，只会再得出一次 passed+stale。

新增 `stage-supersede`：

```powershell
node tools/collab/cli.mjs stage-supersede --delivery <旧> --by <新> [--actor cursor|codex|user] [--note <text>]
```

- 写共享 `deliveryStatus` 台账；跨任务时另写任务级 `supersededBy`；
- **不改写旧 review**（那份 verdict 对它自己的快照确实成立）；
- 幂等：同一对重复登记返回 `unchanged`，不动 revision；
- 拒绝自我取代、交付不存在、后继早于前驱（`EXIT.CONFLICT`）；
- 被取代任务从 `NEXT_CURSOR` / `NEXT_CODEX` 消失，`CURRENT.md` 与看板注明取代者。

`supersededBy` 不在 `stableContractPayload` 里，因此登记取代不会改动任何契约指纹。
