## 3. 缺陷：「只显示到 DFW，下面是空的」（用户 17:32 报障）

### 3.1 现象

滚动条只到页面上部三分之一左右（内容总高确实够 81 行，滑条比例约 7%，说明 Content 高度是对的），
但屏幕上只有开头的那几张卡，之后一片空白；再往下滚只会更空。

### 3.2 根因

为了不一次建上千个 GameObject，卡片只建「视口附近」的窗口，滚动时补建 / 回收。旧版窗口判据是

```csharp
float offset = -_cardsContent.anchoredPosition.y;   // ← 正负号反了
...
if (!force && _winLo >= 0 && first >= _winLo && last - 1 <= _winHi) return;
```

Content 的 pivot 在顶边，**向下滚时 `anchoredPosition.y` 变大（正）**，取负号后滚动距离被读成
「负的 / 恒为 0」：`first` 永远算成 0，`last` 只覆盖开头几行，于是早退判据恒真 —— 窗口建到初始
那一次（当时视口还没布局，按整页高度估出来的 20 多行）就再也不长个。窗口外的行永远不建，
屏幕上就是空白。

### 3.3 修法（不再靠任何缓存判据）

1. **可见行改成用真实几何算**：把视口 RectTransform 的四个世界角 `InverseTransformPoint` 到 Content
   本地空间，直接和每行顶边比大小。滚动是滑条拖、滚轮、还是代码改位置，算出来都一样，与
   `anchoredPosition` 的正负号无关。
2. **是否补建按「对象真的在不在」判**：`WindowReady()` 逐行查 `_live` 里有没有活着的 GameObject，
   记账错位也能自愈，不会再出现「判据恒真 → 永久早退」。
3. `LateUpdate` 每帧无条件跑一次窗口校准（不再依赖 `_cardsScroll` 是否拿到）；`onValueChanged`
   只是让拖动时同一帧就补建，省一帧空窗。
4. `RevealRow`（展开卡片后拉进视野）同样改成角点几何算，不再猜方向。
5. 行高预存 `_rowH`、角点数组复用，避免每帧分配。

窗口 = 可见行上方留 4 行、下方留 6 行；`_live` 之外的行即时回收。是否重建看
「已建窗口有没有把可见行（上下各 2 行余量）包住」——余量按表头 / 表尾夹紧，避免滚到最顶或
最底时「两行余量永远要不够」导致每帧重建。

## 6. 报表重写：逐刻容量 / 占用 + 跑道数（用户 18:23 要求）

### 6.1 做法

- 逐刻数据全部来自 `IndustryAirlineLogic.ChipsOf(null, code, band, out bandFreeDep, out bandFreeArr)` ——

  全天 96 个 15 分钟刻里，81 个机场共公布 **5862** 条。

  零警告通过；合计仍是 11944 / 10465 / 1479（离港）、10444（到港占），与上一版逐场逐段对得上。
