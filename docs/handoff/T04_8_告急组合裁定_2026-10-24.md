## 1. 先说清这张矩阵到底测的是什么

`AirlineYearSimulator` 跑的是**一个财年、玩家全程不操作**的自动年循环（OPS/FIN/FLEET/MKT/STG/MNT/HR/SAF）。
所以 15 个「破产」的真实含义是：

> **在给定的期初现金、机队与网络下，CEO 一整年不做任何决策，会被这两个最恶劣的宏观情景打到资不抵债。**

这不是「游戏太难」，是「不作为基线」——它恰恰是难度设计想要的锚点。
裁定表里的「预期设计」全部建立在这一句之上；任何把这份矩阵读成「玩家存活率」的解读都是错的。

## 3. 两个必须讨论的点

### 3.1 低成本在滞胀下比支线、包机都差（−1122 vs −805 / −753）

四类航司在**同一**滞胀情景下的净利：

| 航司 | 净利 | 相对最差 |
|---|---|---|
| 全服务 | −500 | 基准 |
| 包机 | −753 | ×1.51 |
| 支线 | −805 | ×1.61 |
| **低成本** | **−1122** | **×2.24** |

低成本的核心设定是「票价低 15%（`yieldMultiplier = 0.85`）、竞对运力更高（0.60–0.70）、靠高客座率摊薄」。
滞胀同时打两件事：**油价 1300 $/t 抬可变成本**、**衰退压低需求**。
两件事各打一次，乘起来就是 2.24 倍——这在直觉上说得通（现实中燃油暴涨时 LCC 受伤最重），
但**幅度需要一次对照实验才能定案**：把 `yieldMultiplier` 从 0.85 单独调到 0.90，看 −1122 收敛到哪；
再把 `CompetitorSupply` 单独回调到 0.55，看哪一个才是主因。**在没做这个对照前，不宜宣称「已验证」。**

同时注意 #5：**温和衰退（不是滞胀）就让标准难度低成本红到 1.9 月**，而同一情景下全服务是 **+83 万净利**。
两者差 587 万，这个落差比滞胀那组更难解释——衰退（GDP −1.5%、油价不变）不该把 LCC 打成全服务的反面。
**这一条建议优先查。**

### 3.2 全服务在滞胀下只剩 2.0 个月跑道（标准难度）

全服务是这份矩阵的**基线锚点**（`README` 里「全服务 15/15 全 GREEN」这条自检就以它为准）。
锚点在滞胀下从 GREEN 掉到 YELLOW，说明「滞胀」这一档的硬度可能高过设计预期。

两条出路，须由设计方裁定：

- **A（保留硬度，改口径）**：认定「标准难度 + 滞胀 + 一整年不操作」就该只剩 2 个月跑道，
  把这条写进 `README` 与难度说明，并**删掉**「全服务 15/15 全 GREEN」这类只在旧数据下成立的自检
  （`Program.cs` 里 `fscHealthy` 那一支当前**不会触发**，因为全服务已有 YELLOW）。
- **B（降硬度）**：滞胀的 `需求萎缩` 系数或 `油价 1300` 其中之一回调，
  目标是让标准/全服务/滞胀回到 ≥3 月跑道（GREEN），同时不把破产率压到 0（那会让矩阵失去张力）。

**建议 A**：矩阵的价值在于「有梯度」；把 25% 告急全部抹平成 0 反而失去压测意义。
但 A 必须配套一件事——**把「不作为基线」这句话印在报告抬头**，否则会被误读成玩家存活率。

> **裁定（2026-10-24，用户）：取 A。** 落地情况见 §6。

## 4. 一个独立缺陷：难度只改期初现金，不改损益

同一（航司类型, 宏观）在三档难度下的净利**逐位相同**：

| 航司 / 宏观 | 简单 | 标准 | 困难 |
|---|---|---|---|
| 全服务 / 繁荣 | 1248 | 1248 | 1248 |
| 低成本 / 滞胀 | −1122 | −1122 | −1122 |
| 支线 / 滞胀 | −805 | −805 | −805 |
| 包机 / 滞胀 | −753 | −753 | −753 |

60 组合实际是 **20 个损益情景 × 3 个起始现金**（625 / 500 / 400）。

**原因**：`StressTestRunner` 传给 `AirlineYearSimulator` 的 `irropsSeverity`（0.80 / 1.00 / 1.25）
只作用于**一次性的 IRROPS 现金冲击**（`OpsIrropsLogic.Resolve` 的 `cashDeltaWan`，全年 −25 万量级）；
0.8 / 1.0 / 1.25 倍的差值只值 ±6 万，相对 ±125 万的期初现金差可忽略。

**要不要改，是设计问题**：

- 若「难度 = 起始现金」是设计意图 → 把这句话写进 `tools/balance/README.md`，别再让人以为三档难度会改损益；
- 若不是 → 需要一个**真正作用于损益**的难度旋钮（例如事件频率、需求系数、维护成本系数），
  而不是只放大一次性 IRROPS。

**旁证（同一处的第二个口径问题）**：`TotalNetProfit` **不含** IRROPS 现金冲击与跑道告急贷款，
所以「净利」与「期末 − 期初」对不上。全服务/繁荣三档验证：

```
期初 625 / 500 / 400，净利均 1248，期末 1853 / 1723 / 1616
期末 − 期初 = 1228 / 1223 / 1216     比 1248 少 20 / 25 / 32
= −25 万 IRROPS × 0.80 / 1.00 / 1.25
```

**结论：这张矩阵是情景投影，不是台账。** 任何「拿矩阵做现金对账 oracle」的尝试都会得出
「净利 ≠ 现金变化」的错误结论（与 `残余七项审计_2026-10-24.md` §7 的判定一致）。

> **裁定（2026-10-24，用户）：是设计意图** —— 难度 = 起始现金。不需要新难度旋钮。
> 落地情况见 §6。
