## 1. 第 3 条：CDG—SIN 被当成第五航权（**真错误**）

### 病根

全仓只有一条口径：**国际线 = 要航权 = 第五航权 = 25 点**。
`InboxManager.QueueRightDecision` 的标题与正文把「第五航权」写死，`StrategyManager.RightCost(5)` 也写死，
交割环节同样按 5 档扣点。于是：

- 法国承运人从**自家基地 CDG** 飞 SIN（第三/第四航权，只受法新双边协定管）被标成第五航权；
- 更实质的是**成本错档**：「本国 ↔ 对方」这种最容易办的航权，和「他国 ↔ 他国」这种要三国点头的航权，
  在账上完全等价（都是 25 点）。

用户的两点判断都是对的：PEK—SIN 对巴黎基地确实是第五航权；CDG—SIN 不是。

### 改法

新增 `AirportRegions.CountryOf` / `AirportRegions.FreedomOf` / `AirportRegions.FreedomLabel`
（`Logic/AirportRegions.cs`），并以 `RoutePermitLogic.HomeCountry` / `FreedomFor` 接一层
「承运人本国 = 主基地所在国，主基地未定退回 CEO 国籍」。

| 航点关系（相对承运人本国） | 档位 | 成本 |
|---|---|---|
| 两端均在**本国**（PEK—SHA，中国基地） | 0 = 国内，不需双边航权 | 0（不递单） |
| **本国 ↔ 他国**（巴黎基地：CDG—SIN、CDG—PEK） | 3 = 第三/第四航权 | 21 点 |
| **他国 ↔ 他国**（巴黎基地：PEK—SIN） | 5 = 第五航权 | 25 点 |
| **他国境内两点**（巴黎基地：PEK—PVG） | -1 = 国内载权 cabotage | 拒绝递单 |

改动落点（标题、正文、闸门、扣点**四处同源**）：

| 位置 | 改动 |
|---|---|
| `InboxManager.QueueRightDecision` | 先算 `FreedomFor`；0 拒递（说明是国内容）、-1 拒递（说明国内载权）、否则标题与「档位」行按实际档位写 |
| `InboxManager.RightFreedomNote` | 新增：正文解释**为什么**是这一档、现实里要谁点头（第三/第四=双边协定；第五=须接在本国始发航段之后） |
| `InboxManager.TryQueueRightForPermit` | 点数闸门由 `RightCost(5)` 改为 `RightCost(实际档位)` |
| `InboxManager` 交割分支 | `ApplyRouteRight(o, d, 5)` → `ApplyRouteRight(o, d, 实际档位)`（旧档/未知国家退回 3 档） |
| `StrategySubpagePanel` 待批复/待交割列表 | 不再把每条申请都印成「第五航权」，按同一函数算档位 |
| `StrategySubpagePanel` 空态文案 | 补「第三/第四 21 点 · 第五 25 点」两档口径 |
| `MaybeOfferRightsAndSlots` | 硬编码提案的金额闸门同样按实际档位算 |

净效果：**同一对航点，信里写的、闸门判的、实际扣的是同一个数**，且这个数随承运人本国变化。

### 残留范围（如实写明，未改）

`RoutePermitLogic.IsInternational` 与 `AirportRegions.IsForeignEndpoint` 仍以**中国**为基准
（PEK—SHA 恒为国内）。也就是说巴黎基地飞「中国境内两点」不会走航权闸门。
彻底改成「相对承运人本国」会牵动税、EU ETS 碳配额、许可工期、多处回归，属独立立项，本轮不动。

## 2. 第 4 条：运力调令回复 2 个工作日 → 1 个工作日

`InboxCadence` 新增独立常量：

| 常量 | 值 | 用途 |
|---|---|---|
| `StudyBusinessDays` | 2（不变） | 开航可行性研究会 |
| `CapacityStudyBusinessDays` | **1（新增）** | 运力调令研究期 |
| `ReplyHours` | 4（不变） | 决策回执 / 加急会商 |

刻意**不共用**同一个常量：开航要跑引力模型、可行性、跟局方对口径；运力调令只是本线重排班、组环、
联动四个部门 —— 现实里一个工作日即可。绑在一起的话，调其中一个会顺手改掉另一个。

`QueueCapacityReport` 的拟定件延迟改走 `InboxCadence.CapacityStudyReady`；命令台回执、决策日志、
正文话术全部跟这个常量同源。

## 3. 第 5 条：重复下同一条令（**原来确实是 BUG**）

### 病根

`InboxManager.Schedule()` 遇到同一封待发件时做的是「**更新** `deliverUtcTicks`」，而
`QueueCapacityReport` 每下一条令都用「现在 + 研究期」重算一次到件时刻。于是：

- 1 号下令「加密到每天 3 班」→ 到件 2 号；
- 2 号再下一次同样的令 → 到件改成 3 号；
- 3 号再下一次 → 4 号……

**研究期被反复重置，CEO 越催越等不到回音。** 用户问的正是这一条。

### 改法（`QueueCapacityReport`）

在作废旧件（`Supersede*` / `DropPending*`）**之前**插入守卫：

```
正在研究的拟定件（pendingInbox 里 capDeferred=true、同 routeId）
  + 目标相同（比较 capTargetWaves、capTargetWeekly）
  → alreadyStudying = true，直接 return，不重排期、不换正文、不出第二份、不作曲废
```

- 「同一目标」按**拟定落点**比，不按原话字面比：「加密到每天 2 班」与「每天 2 班」算同一件事，
  「加密到 3 班」算改主意 —— 后者必须重新排期（新方案的到件时间当然要重算）。
- 守卫必须在作废**之前**：否则同目标重下会先把旧方案作废再早退，CEO 手上凭空少一封可批的呈报。

新增 `InboxManager.FindStudyingCapacityReport` / `CapacityStudyWaitText`（后者给命令台回执报
「原令预计 X月X日 HH:mm 送到」，而不是又喊一遍「1 个工作日后」）。

### 命令台回执话术

| 情形 | 回执 |
|---|---|
| 首次受理 | 「…运营部已受理：约 **1 个工作日**后进收件箱（原令预计 11月4日 17:00 送到）（班次此刻未动，批准后立即排班）」 |
| 同目标重下 | 「…这条调令运营部**已在研究中**（原令预计 11月4日 17:00 送到），本次不重复受理、不会顺延到件时间（若要改方案，请下达不同的目标）」 |
| 改目标重下 | 走「首次受理」话术，旧方案作废、新方案另起 |
