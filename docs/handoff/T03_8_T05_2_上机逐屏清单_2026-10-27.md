## 一、先纠一个会误报的口径问题（重要，先读）

「四地数字一致」在代码里的真实情况是：

| 视图 | 代码位置 | 格式 | 精度 |
|---|---|---|---|
| 列表（航线卡） | `RouteCard.cs:84` | `{route.dailyProfit:F1}` | **1 位小数** |
| 详情（航线面板） | `RouteDetailPanel.cs:297` | `{r.dailyProfit:F2}` | **2 位小数** |
| 邮件（部门报告/回执） | `DeptReportLogic.cs:1447` `ProfitText` | `{dailyProfitWan:N1}` | **1 位小数**（带千分位） |
| 地图 | `MapWidget.cs` 等 | **不显示任何日利数字** | — |

四处**都读同一个 `route.dailyProfit`**（同一个 float 字段，无第二套公式），所以「数值一致」
这件事在数据层是成立的。**不一致只可能来自显示精度。**

因此判定标准不是「四处字符串必须逐字相同」，而是：

> **把四处数字都退到 1 位小数后必须相等；差值 ≤ 0.05 万即视为一致。**

⚠️ **有一个会让人误判成 bug 的边界**：`F2` 与 `F1` 在「恰好落在 .x5」的值上会给出
看起来矛盾的结果。例如 `dailyProfit = 12.3499999`（float 存不下 12.35）：
详情显示 `12.35`，列表显示 `12.3`。拿 `12.35` 手工四舍五入到 1 位会得到 `12.4`，
于是看起来「列表少了一个 0.1」。

**这不是 bug**，是「对值取整」与「对已取整的字符串再取整」的差别。
判定一律以 **`route.dailyProfit` 本身**为准，不以屏幕上那个 F2 字符串为准 ——
这也是为什么本轮没有把四处格式统一（统一会丢详情页需要的精度），
而是把判定标准写清楚。

### ❌ 2.1 新 bug：`WEEKLY PROFIT` 把「加密」乘了两遍（已修）

`OpsEconomics.ToDailyProfit` 里 `dailyProfit` **已经**按 `weeklyFlights/7` 摊到日历日：

```117:121:Unity Project/Assets/Scripts/Logic/OpsEconomics.cs
        public static float ToDailyProfit(float singleFlightDailyBaseline, int weeklyFlights, ScheduleMetrics m)
        {
            float dailyFlights = Math.Max(0.1f, weeklyFlights / 7f);
            return Round2(singleFlightDailyBaseline * dailyFlights * m.profitMultiplier);
        }
```

旧公式又乘一次本班周班次：

```csharp
// 旧：单班日利 × 本班周班次 —— 20 班/周的航线虚高 2.86 倍
float weekProfit = r.FlightNetDailyProfit * Mathf.Max(1, FlightScheduleFormat.WeeklyOf(f));
```

实测 12.0 / 4.2 = 2.857 = 20/7，正好是周班次倍数。

**为什么长期无人发现**：`每班 7 班/周` 时 `WeeklyOf(f) == 7`，
旧式 = `dailyProfit/1 × 7` = 正确值。3 波 × 7 班的回归夹具、
每周 7 班的长航线（上一局 LHR）全都测不出来。**只有把班次加密到非 7 班才暴露。**

改法：公式收进 `RouteData.WeeklyProfitOf(f)` = `dailyProfit × 7 × 本班周班次占比`，
Σ 各班 = 航线日利 × 7，单班时 = `dailyProfit × 7`。

回归（`schedule-page` ⑪）三条，其中第 2 条是**反例**，专门证明它能抓住这个缺陷：

| 断言 | 实测 |
|---|---|
| Σ 各班周利 == 航线日利 × 7 | `2.45×3 = 7.35 vs 7.35` ✓ |
| 20 班/周 → 新值必须是 4.2、旧式必须是 12.0 | `新 4.2 / 旧 12.0` ✓ |
| 密班周利 == 摘要行周利（两处不许打架） | ✓ |

### ❌ 2.2 两条「假覆盖」断言（`SchedulePageRegression`，非产品缺陷）

把 `SchedulePageRegression.Run()` 从 `void` 改成 `bool` 并注册进触发桥后，
两条一直躺在日志里打 `✗` 的断言**第一次有了后果**。两条都不是产品缺陷：

**① `正文第3波带 #2`：测的是空对象，从来没执行到被测分支。**

`TermNavMap.WrapFlightNumbers` 内部取 `GameState.Instance`，而 `GameState`
**没有 `[ExecuteInEditMode]`** —— EditMode 下 `AddComponent<GameState>()` 不跑 `Awake`，
`Instance` 恒为 null → `activeRoutes` 为空 → 直接 `return s` 原文。
也就是说「邮件里的航班号能不能点」这条路径，**在 EditMode 回归里从来没有被覆盖过**。

修法不是让测试 hack 单例，而是解除耦合：

```csharp
public static string Decorate(string body) => Decorate(body, null);
public static string Decorate(string body, GameState host)   // 新增
{
    ...
    return WrapFlightNumbers(s, host ?? GameState.Instance); // 不传则行为不变
}
```

游戏内调用方一个字不改；回归传自己造的那台。修后实测：

```
正文第3波带 #2=True
[实际包裹] <color=#7EB6FF><u><link=flight:R-PEK-PVG-MULTI#2>NS104</link></u></color> 红眼班，请核对时刻。
```

**② `跨午夜标 +1`：夹具时刻写错，断言永远不可能通过。**

注释写「23:30-01:48」，代码写 `01:00 → 06:00`。`BlockMinutes` 取 `arr − dep`（300 分），
01:00 出发的 5 小时往返走不到午夜 → 实测回程 `07:14-12:14` 全程同一天。
红眼要跨天得**晚上**出发，写成凌晨就测不到跨天。改成 `23:30 → 01:48` 后：

```
跨午夜标 +1=True　[红眼回程实测] 02:38-04:56+1（23:30 出发 · 1080 km · A320neo）
```

**教训**：这两条断言的价值是负的 —— 它们让人以为排班页有覆盖。
`void` 签名是共犯：失败只打 `✗`，没有任何东西会因此变红。

### ❌ 2.3 同一张截图查出底栏两个缺陷（已修，已实跑）

底栏 `收入:2,455,650　支出:5,685,000　盈利:-3,229,350` 三个数互相减得通，
但「收入」其实是**已扣完成本的净贡献**（`gs.monthlyRevenue` 累的是 `dailyProfit`），
「支出」只算了**固定开销 + 机队维护两项**，而跑道算九项。
同一屏上两个数推出两条不同的烧钱速度。

已按用户裁定改成「季度净贡献 / 季度支出 / 季度盈亏」并把支出换成与跑道同源的成本基数，
新增 `StatusBarReconcileRegression` 七条断言（第 ④ 条专门抓这个缺陷）。
详见任务书 §30。

**✅ 2026-10-27 07:42 已实跑通过**：`status-bar-reconcile` → `passed`，7/7 全绿；
全量白名单 `all` → 18 项通过、失败 0。
底栏数值变化：支出**变大**（补上租赁/CEO/运行岗/人力/保费/本息），盈亏更负 —— 这是修正而非回归。

**用户实机反证**：截图底栏 `季度净贡献 6,097,830 − 季度支出 21,566,790 = −15,468,960`
分毫不差等于显示的 `季度盈亏`。旧口径漏六项，绝不可能算平。

## 二、T03.8 逐屏步骤

### 前 置：造一个数值可预期的航线

1. 进 Play 模式。
2. 菜单 **`AirlineCEO` → `场景夹具` → `运行夹具回归（EditMode 自检）`**，确认夹具可用（EditMode 下即可跑，不必进 Play）。
3. 任选一条**有执飞飞机**的航线，进详情页，把 **「日利」** 那行的 2 位小数值记下来（记为 `X`）。

### 步骤 1 · 详情 ↔ 列表

- 回列表（航线卡），找到同一条航线，读卡上的「日利 N.n 万」。
- **判定**：`|卡上值 − X| ≤ 0.05`。✅ 通过 / ❌ 记录两个数。

### 步骤 2 · 详情 ↔ 邮件

- 让系统出一封与该航线相关的邮件（**部门报告**或**容量指令回执**最容易触发；
  菜单里若有「生成部门报告」的夹具入口直接用）。
- 邮件正文里的「日利」「单班日利」两个字段。
- **判定**：
  - 邮件「日利」与 `X` 差 ≤ 0.05 → 通过；
  - 邮件里的「单班日利」与 `X / 班次` 差 ≤ 0.05（`班次` 见详情页「N 班合计」）→ 通过。
- ⚠️ 若邮件里的「单班日利」等于 `X`（而不是 `X / 班次`），那是**口径错**，必须记 bug ——
  这是 T04 系列反复出现过的那类「把航线级当单班级」的错误。

### 步骤 3 · 地图

- 地图上确认该航线**存在**、两端城市名对得上。
- **判定**：存在且城市正确即通过。地图**不承担数值口径**，不要在地图上找日利。

### 步骤 4 · 四处同框截图

- 一次截「列表 + 详情 + 邮件」三处，作为交叉证据留档。
- 命名建议：`out/t03_8_four_ways_<航线>.png`。

### 已机器验完的部分（不必手测）

- 四处均读同一个 `route.dailyProfit`，无第二套公式（全仓 grep 已确认，
  唯一例外是 `AdvisorModalUI.cs:1190` 的教程态合成赋值，那条在 T05.5 单独管）。
- `RouteDetailPanel.cs:419` 的注释明确记录过「旧版用 `f.dailyProfit`（毛贡献份额）
  当航线日利」这个已修的历史错误，当前用 `r.FlightNetDailyProfit` —— 不要再按旧版对照。

## 三、T05.2 逐屏步骤（停飞 / 停场维修 / 缺员）

用夹具直接造状态，不用手工裁人/退租。

### 3.0 入口（旧版这份清单写的「工具 → 场景夹具」是错的）

真实路径：Unity 顶部菜单栏 **`AirlineCEO` → `场景夹具`**，或先点 `打开面板` 开一个小窗口
（三个按钮 + 日志都在里面，比反复点菜单省事）。

三个菜单项的真实名称：

- `单机进入维护（T05.2 维护停场）`
- `全机队停飞（T05.2 无机·停飞）`
- `客舱缺员（T05.2 缺员提示）`

**前置**：必须已在 Play 里**进入游戏**（`GameState.Instance != null`）。
停在开始界面 → 提示「场景夹具需要在 Play 模式下运行」。

### 3.1 ⚠️ 顺序必须是「缺员 → 维护 → 停飞」，不能反过来
原清单写的「维护 → 停飞 → 缺员」**执行不通**，两个独立的死因：

1. **`全机队停飞` 之后机队里没有在役机**，`单机进入维护` 直接拒绝（「机队里没有在役飞机」）。
2. **`全机队停飞` 会把乘务编制清零**：`GameState.GetFleetStaffing` 只累 `isActive` 的飞机，
   编制归 0 后 `CabinFilled 207 ≥ 编制 0` → 游戏判定「**不缺员**」，缺员提示凭空消失。

所以三项各一次、按此顺序走完，一个 Play 会话够用。

### 3.2 逐项判定

| # | 动作 | 生效判据（对话框） | 该看到什么 |
|---|---|---|---|
| 1 | 缺员（多半**不需点**） | `客舱缺员已构造：…` 或 `已经是缺员状态：在职 N / 编制 M` | 见 3.3 —— **注意没有顶部横幅** |
| 2 | `单机进入维护` | `B-200x 状态 在役 → 维护中` | 航线详情的机号后缀出现 `（停场维修）`；航线卡标题 `⚠ 飞机停场维修` |
| 3 | `全机队停飞` | `已停飞 N 架（…）` | 航线卡标题 `⚠ 飞机已退役或退租…`；日利位置变成 `停飞不计营收` |

⚠️ 第 2、3 步的 `⚠` 文案**长得像但不是一回事**：维护是 `飞机停场维修`，
停飞是 `飞机已退役或退租（自有转售 / 租赁交还出租人）`。
判定看**括号里的病因词**，不要只看「有个 ⚠ 就算通过」。

### 3.3 缺员的可见出口只有两处（旧清单的「顶部常驻提示」不存在）

上一版把判定写成「顶部常驻提示出现『机组不足』类文案」，**这份 UI 里没有这个东西**。
把 `UI/` 全量搜过：乘务缺员**没有任何顶部/常驻横幅**，真实链路只有：

1. **人力 → 招聘**：乘务员那一行带缺口标签（`RecruitmentOfficePanel` 的 `cabinShortage`）。
2. **航线 → 单航线 → 运力调整**：提交一次**加密**请求，呈报正文应出现：
   ```
   机组需求　…
   …排不出：**机组不足** —— …
   本条线机组口径最多排 N 段/日，现值 M 段，本次要排 K 段。
   ```

⚠️ 第 2 条必须在**停飞之前**做：机队全停后其它航线占用归零，207 名乘务足够覆盖，缺员消失。

### 3.4 仍适用的判定要点

1. **同一状态在卡片/详情/呈报里不许互相矛盾**（两处口径是这类问题的经典错法）。
2. **提示必须常驻**：切到别的页签再切回来，状态还在。
3. **文案不许出现伪数字**：任何百分比/金额都要能在详情页找到同一个数。
4. **不自动消失**：状态没解除前，提示不得自己消失。
5. **退出 Play 即恢复**：夹具只改内存态、不写存档。若要重来，退出再进即可。

### 3.10 「适航 → 在役」改名（已修，下次上机可核）
