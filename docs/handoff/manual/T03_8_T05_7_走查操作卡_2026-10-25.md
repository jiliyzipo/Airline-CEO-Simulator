## 0. 先读这三条硬事实（决定了哪些能测、哪些测不完）

### 0.1 1× 是 1:1，不是"慢一点"

```39:39:Unity Project/Assets/Scripts/Systems/GameSpeed.cs
            1f / 60f, // 1×：1 现实分 = 1 游戏分
```

也就是说 **1× 下 4 游戏小时 = 4 现实小时**。收件箱的所有等待常量都是游戏小时：

| 事件 | 常量 | 1× 现实等待 | 3× 现实等待 |
|---|---|---|---|
| 决策后回执 | `ReplyHours = 4` | **4 小时** | ≈ 80 秒 |
| 节点进度汇报 | `ProgressHours = 6` | 6 小时 | ≈ 120 秒 |
| 运力调令呈报 | `ReportHours = 2` | **2 小时** | ≈ 40 秒 |
| 局方受理回执 | `AdmitBusinessDays = 1` | ≈ 1 个工作日 | ≈ 1 个工作日的 1/3 |

**所以 T03.8 §4（回执延迟）和 T05.7 的"等待"部分，1× 下不可能坐着等完。**
这不是缺陷，是设计比例。处理办法见 §3 与 §4 的"替代口径"。

### 0.2 顶栏有四个倍速按钮，但只有三个是正式档

顶栏：`帮助 / 设置 / 1× / 2× / 3× / 日(DevDay)`。

- `1×` `2×` `3×` = 正式档，写进存档；
- `日`（DevDay，图标右下角一个"日"字）**只在编辑器/开发包出现**，是开发档，
  **T05.7 的 1× 结论不得用它**，也不得把它的观感写成正式玩法体验。

### 0.3 地图线宽现在**真的**随班次变了（旧清单那条判据已作废）

```36:42:Unity Project/Assets/Scripts/UI/MapWidget.cs
        public static float RouteThickness(RouteData r)
        {
            if (r == null) return RouteScreenThickness;
            int w = Mathf.Max(0, r.WeeklyFlightsDeparture());
            if (w <= 7) return 2.0f;
            if (w <= 20) return RouteScreenThickness;
            return 3.0f;
        }
```

判据：**≤7 班 → 2.0 px；8–20 班 → 2.4 px；>20 班 → 3.0 px**。
旧清单写的"地图不表达班次 = 现状，记设计缺口"已经过期，**按新判据判**。

> 0.2 px 的差在地图缩放下肉眼很难分，正确做法不是"盯细看"，而是
> **拿两条差距最大的线对比**：一条 ≤7 班的支线 vs 一条 >20 班的干线，并排看。

### §5 执行回执（真起飞 → 真落地）

现界面**没有**"运营页/执行记录页"，执行痕迹只有两处：

1. 时钟放到某班计划离港前几分钟（时刻见 n43）；
2. **机队**页看该机状态：`适航` → `飞行中`，机号应是实际分配那架；
3. 落地后状态回 `适航`；进「飞机详情 · 履历」看 `累计 X FH / Y FC`，**一趟往返 FC 恰好 +2**；
   一次 +1 或 +4、或飞了但 FC 不动，都是结算漏/重。
   > 口径更正（2026-10-25）：本卡上一版写「一班 +1」是错的。代码里每次**落地**记 1 次循环
   > （`LiveClockSimulator.Land` → `flightCycles += 1`），而一条航线班是「去程 + 过站 + 回程」
   > 两段，故一趟往返 = 2 次起落循环、航时按两段累加。单看一个航段才是 +1。
   > 机器证据：`T038UiAcceptancePlayModeTests.OneRoundTrip_WritesExactlyTwoFlightCycles`。
4. 有停飞线的局：列表该线显示 `⚠ 停飞不计营收`，地图/日历上不应还有这班。

📸 `05-ops.png`

### §6 数字对照（逐格抄，别写"一致"）

同一条航线，把四处数字抄进表。**先对齐口径再判断**：

- 列表 `日利` = 航线级日净利（Σ 各班日毛利 − 航线日固定成本）；
- 详情 `WEEKLY PROFIT` = **单班**日毛利 × 该班周班次，**不含**航线固定成本；
- 详情顶部 `周利` = `dailyProfit × 7`（航线级）—— 与上面那个**本来就不等**，差的就是固定成本；
- 地图没有数字，只表达疏密；财务页只有公司级汇总，没有单条航线日利。

| 项目 | 航线列表卡片 | 单航线详情 n41 | 主页地图 | 收件箱邮件 |
|---|---|---|---|---|
| 三字码 | | | | |

## 3. T05.7 · 1× 实时体验（新建 + 接管各一轮）

### 3.1 这一项到底要证明什么

任务书原文：「从新建与接管两类开局检查等待、读邮件、返回详情和继续推进的体验，
**记录真实游戏时间和现实等待**；加速测试只作模拟证据，不能冒充完整 1× 实时手测。」

拆成三条可执行判据：

1. **映射对不对**：1× 跑 10 现实分钟，游戏时钟应恰好走 10 游戏分钟；
2. **1× 下能不能干正事**：读信、返回、下单、批准这些**不依赖等待**的操作是否顺畅、是否卡表；
3. **1× 下等得起吗**：把各条等待换算成现实时间（§0.1 那张表），给出"可接受 / 不可接受"的判断。

### 3.2 操作（每轮 15–20 分钟，两轮共约 40 分钟）

**第 1 轮 · 新建局 `T057A`**

1. 进游戏后**先确认顶栏高亮在 `1×`**，再记下开始时刻（现实时间，精确到分）与游戏日历；
2. 什么都不做，**静置 10 现实分钟**（手机计时），结束后读游戏时钟：
   - 走了 10 游戏分钟 → 映射正确；
   - 走了别的量 → 记缺陷（写清实际走了几分）；
3. 打开收件箱，**读一封**长信（滚动到底），再返回列表，再点同一封：
   - 正文是否每次回到顶部（已知现状）；
   - 有没有明显卡顿、闪烁、正文与列表不同步；
4. 下一**一条不涉及等待的指令**（如询问类），看按键到邮件的延迟；
5. 再下一**条会产生呈报的指令**（运力/排班类），记下按下时刻：
   - `ReportHours = 2` → 1× 下应 **2 现实小时**后到；
   - 你**不必**等满，就记「已按下，理论上 2 现实小时后到，本次未等待」；
6. 切 `3×` 等约 40 秒，确认呈报确实到 → 记「**3× 模拟证据**」；
7. 回到 `1×`，点"推进到下一季"，记：季度结算是否卡住、有没有跳帧、推进后时钟是否仍在 1×。

**第 2 轮 · 接管局 `T057B`**

重复 1–3 步（映射、读信、返回），再补两条接管特有的：

4. 开局那封"接管交底/资产清单"长信能否在 1× 下顺畅读完（这是接管局的第一印象）；
5. 接管局初始就有的待批件，点开 → 返回 → 再点开，看有没有状态错乱。
