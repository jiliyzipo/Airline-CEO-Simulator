# 外部消息的发件人：新闻官还是顾问？（2026-10-24 分析底稿）

> **性质**：设计分析 + 落地规格。§1–§8 为裁决前的分析与规格（保留原文，便于回看当初的取舍）；
> **§9 是裁决与实施记录**（已落地，含证据与未闭合项）。
> 相关现状证据行号均以符号名为准（会随改动漂移）。

---

## 0. 结论

**用「新闻官」，不复用「顾问」。** 但不是把 `sender` 字段换个字符串就完事，
而是新增一层「转呈」身份：**人具名、职位固定、原文不动、来源不隐**。

一句话理由：顾问回答的是「**我建议你怎么做**」，新闻官回答的是「**外面有人递了这个进来**」。
这两个问题在这款游戏里被刻意分开了（见 §1 的「来文原文 / 公司内部标注」分隔线），
合并会把「谁的判断」这件事搞糊。

## 1. 现状：外部信为什么是机构名（代码事实）

| 事实 | 位置 | 含义 |
|---|---|---|
| 外部来文 `sender = ev.source` | `ExternalEventManager.PushReceiveMail` / `PushTriggerMail` | 收件箱列表第一行直接是「中央气象台 / 局方（时刻协调）/ 某银行 / 某制造商」 |
| 内部邮件 `sender = 运营部 / 战略发展部 / …` | `InboxManager`（十余处） | 但**显示时会被换成真人** |
| `InboxLetter.Identify`：部门 → 现任负责人姓名 + 职位 | `Logic/InboxLetter.cs` | 先取部门负责人，空缺退副手，再退在职人员；所以内部信是「人写的」，署名与人事名单逐字一致 |
| 同样这条路径对**外部机构**走不通 | 同上 | `DeptCodeOf("中央气象台")` = null、`OrgRoster` 无命中 → `post = role`、`name = ""`。**外部信在当前模型里没有署名的人** |
| 正文其实完整保留了来源 | `Logic/OfficialBulletin.Compose` | 按 `StyleOf(ev.source)` 分四种体例：政府公文（关于…的通知 / 特此通知 + 落款机关）/ 通讯社电讯（【社名】+ 电头）/ 企业公告 / 机构提示函。落款打的就是 `ev.source` |
| 体例判定**硬编码**「顾问」= 提示函 | `OfficialBulletin.StyleOf`：`Has(s,"顾问") → Style.Advisory` | 这是方案 A 的致命点，见 §3 |

**结论**：现在的数据模型里，「机构 → 个人」这一跳只有内部部门走通了，外部没有。
用户的直觉是对的：外部信看起来像「气象台直接把公文发给 CEO 本人」，而这在现实里不成立。

## 2. FM 的实际结构（截图实证，不是记忆）

对用户提供的 FM 截图做了逐字识读，结果如下：

| 位置 | 显示 |
|---|---|
| 左侧列表「发件人」 | **人名**：安萌、安萌、安萌、张康…… **没有机构名** |
| 右侧详情顶部 | 姓名 **张康**；姓名下方职位 **新闻官** |
| 右侧详情第二行 | 动作 **转发**；下方是原标题「中甲联赛：东莞市体育场之战结果出乎意料」 |
| 资料页 | **没有**。点不出履历、属性、薪资 |

也就是 FM 的三段式是：`姓名` ＋ `新闻官` ＋ `转发：{原标题}`。
它解决的不是「消息从哪来」，而是「**谁把这封放到我桌上**」。

## 3. 方案 A：复用现有「顾问」—— 不建议（4 条理由，第 1 条是硬冲突）

### A1（硬冲突）会让四种公文体例塌成一种

`OfficialBulletin.StyleOf` 的第一条分支就是 `Has(s, "顾问") → Style.Advisory`。
一旦把外部来文的 `sender` 设成「顾问」：

- `RoleLabel("顾问", 气象)` → **「提示」**（不再是「预警通报」）；
- `DocType` 的「气象/台 → 预警通报、银行 → 公告、局/署/部 → 通知」全部失效；
- `KindOf` 仍返回 `official`，但 `Compose` 会走 **Advisory 的「提示函体」**，不再有「特此通报」与右对齐落款；
- 台风公报、央行公告、制造商公告、通讯社电讯 → **同一副模样**。

要绕开，只能给 `Compose` / `RoleLabel` 额外传「真实来源」参数 ——
那等于承认「sender 已经不是来源」，也就等于承认该新增一个转呈层，而不是复用顾问。

### A2 职责混同：顾问是「教练」，不是「收发室」

顾问目前是 **开局引导线 S0–S6 的宿主**（`AdvisorTutorialScript.AdvisorTitle = "航空顾问"`），
正文里 12+ 处是第一人称台词（「我在这里待命」「我给您快速过一遍」「引导即将结束 · 顾问进入待命」）。
它说的是**建议**。让它转发台风公报，玩家会分不清：
这句是「我的顾问判断台风会影响我」，还是「气象台原文」？

而 `ExternalEventManager` 已经专门画了一条分隔线：
`——以下为公司内部标注，非来文内容——`。
这条线的存在本身就说明：**来文原文与公司自己的话必须是两个主体**。
顾问站在「公司自己的话」那一侧。

### A3 顾问「有资料」，与需求相反

用户要的是「只有姓名，没有任何资料」。顾问恰好相反：有头像（圆形「航」字）、
有独立弹窗、有引导脚本、有建议语气、有「遗留问题按紧急程度排列」的行为。
它是**全游戏资料最多的一个角色**，没有之一。

### A4 署名机制对不上

`InboxLetter.Identify` 对非部门发件人的兜底是：
`if (LooksLikePersonName(role)) { name = role; post = "负责人"; }`。
把 sender 设成「顾问」、role 设成「预警通报」，会走到 `post = role`、`name = ""`，
署名变成「**顾问 · 预警通报**」——读起来像一个人的职位叫「预警通报」。
要修就得给「顾问」写特判，那和写「新闻官」特判的工作量完全一样，却多背了 A1–A3 三条债。

## 4. 方案 B：新增「新闻官」（推荐）

### 4.1 身份定义

| 属性 | 规格 | 为什么 |
|---|---|---|
| 姓名 | 由存档内稳定量派生（公司名 / 基地 / 开局年份），**同一存档任何时刻取到同一个名字** | 读档换人会让「新闻官」变成随机 NPC |
| 职位 | `新闻官`（固定，不晋升、不调岗） | FM 的就是固定职位 |
| 履历 | **不存在**：不进 `DepartmentManager`、不进人事名单、无薪资、无职级、无属性、无头像模型 | 「没有任何资料」由**结构**保证，而不是靠少写几个字段 |
| 出现在哪 | 只出现在收件箱的 `sender` + 详情页 `role` | 顶栏不加入口（顾问已经占了） |
| 能否互动 | 不能：没有对话、不能解雇、不能任命 | 它就是一层邮路 |

### 4.2 数据接线（三处）

```text
sender  = 新闻官姓名            ← 列表第一行（FM 同款）
role    = "新闻官"              ← 详情职位行；生效通报写 "新闻官 · 后续通报"
glyph   = "闻"                  ← 头像字，不再按机构变色
subject = 不变（{日期} · {标题}）← 列表第二行仍是事由，一眼能看出是台风还是银行
```

**关键约束：`kind` / `StyleOf` / `DocType` / `Compose` 全部继续用 `ev.source` 算。**
也就是说：信是新闻官递来的，**公文还是那个机关的公文**——四种体例一个都不塌。

### 4.3 正文加一行「转呈」

在 `Compose` 产出的原文之前加一句（不动 `Compose` 本身）：

```
以下为中央气象台来文原文，林越整理转呈。
```

这一句同时解决三件事：① 说明为什么是这个人寄的；② 让「以下为原文」有明确边界；
③ 与既有的「以下为公司内部标注，非来文内容」形成对照。

### 4.4 `InboxLetter.Identify` 加一条特判

```text
sender == 新闻官姓名  →  name = sender, post = "新闻官"
```

不这样的话，会落到兜底分支签成「负责人 某某」或「某某 · 预警通报」。
这条特判是**唯一**需要碰署名逻辑的地方，且是新增分支、不改既有分支。

## 5. 必须由设计方裁定的一条边界

**政府 / 监管来文要不要也走新闻官？**

| 选项 | 说明 | 优点 | 代价 |
|---|---|---|---|
| **B1 全走**（FM 式，用户描述的形态） | 台风、央行、局方、制造商、通讯社，全部由新闻官转呈 | 心智最简单：CEO 的收件箱只有一个「外部入口」 | 列表里全是同一个名字，扫读靠第二行事由；连续 10 封会像系统通知 |
| **B2 只转媒体与气象** | 局方 / 民航局 / 监管指令仍署原机关 | 更真实：监管指令本来就是直接下给公司的 | 「谁转的」变成两套规则，玩家要记 |
| **B3 全走 + `role` 保留原文种**（推荐） | `sender=新闻官`，但 `role = "新闻官 · 预警通报 / 通知 / 公告"` | 「谁递来的」与「这是什么文」两件事同时可见；不需要玩家记规则 | 职位行略长 |

推荐 **B3**：它同时满足用户的「发件人不应是发布单位」与「不能丢掉文种」两个诉求，
且实现上只是把 `RoleLabel(ev.source, category)` 的结果拼到 role 里，零额外逻辑。

## 7. 一条反向检查（避免自我说服）

如果只把 `sender` 粗暴替换成字符串「新闻官」（不具名），会怎样？

- 满足「发件人不是发布单位」；
- **不满足**「只有姓名」——因为根本没有名字；
- 列表里连续多封「新闻官」，观感更接近「系统通知」而不是「人来信」；
- 且会在 `StyleOf` 上再踩一次坑：`Has(s,"顾问")` 不命中，但也会落进 `Style.Corporate`
  或 `Style.Government` 的判定里，体例仍是错的（因为判定输入是 sender）。

所以「只换字符串」不是最小改动，而是**看起来最小、实际最错**的那条路。

## 9. 裁决与实施（2026-10-24 晚）

**用户裁决**：采**新闻官**；**B3**（`role` 保留原文种）；姓名**按存档派生**（同存档恒定、不同存档不同名）。

### 9.1 与 §6 预算的差异（实施时改了 3 处）

| 原预算 | 实际 | 原因 |
|---|---|---|
| `role = "新闻官"` 或 `"新闻官 · 后续通报"` | 统一 `PressDesk.RoleLine(原文种)` → 「新闻官 · 预警通报 / 通知 / 公告 / 消息 / 施行通报 / 后续报道」 | B3 裁决；把「谁递来的」和「这是什么文」一次说清 |
| 名单里加 `name = sender, post = "新闻官"` | `dept = 新闻官, post = ""`（落款「新闻官 卢曦」） | 若 `dept` 取姓名、`post` 取「新闻官」，`Sign` 会拼成「卢曦 · 新闻官 卢曦」 |
| 新闻官姓名常量「林越」 | 存档派生（`FNV-1a(身份字段) → PersonnelGenerator.SingleName`） | 裁决要求同存档恒定；**不能用 `string.GetHashCode`**（.NET 进程随机化，读档就换人） |

### 9.2 两条实施中发现的口径

1. **存档标识只能取开局写入、之后不再变的字段**（公司中英文名 / IATA / ICAO / 基地 / CEO 姓名 / 国籍 / 出生年）。
   取 `year / quarter / simDay` 会让新闻官按季换人 —— 回归里专门有一条「跨年不改名」钉这个。
2. **`gs == null` 在进程外恒为 true**（`UnityEngine.Object` 的 `==` 重载）。
   `PressDesk` 因此用 `ReferenceEquals(gs, null)`，并把取名核心拆成纯函数 `NameOf(key, nation)`，
   这样 `tools/cmdcheck` 这类离线探针也能验「同 key 同名 / 换 key 换人」。

### 9.3 证据

- `tools/cmdcheck`：ALL PASS（同 key「卢曦」恒定、换公司名换人、角色行、转呈抬头、空来源兜底）
- Unity EditMode `PressDeskTests`：**Passed**（发件人=新闻官、角色=「新闻官 · 预警通报」、头像「闻」、
  正文含原机关落款、`sender != ev.source`）；结果文件 `out/press_editmode.xml`
- Unity EditMode **全套 36/36 Passed**（工程内 `out/editmode_run3.xml`；交付快照内预检同为 36/36 Passed）
- 隔离基线 `out/b17-accept-1024`：EditMode 36/36、**PlayMode 105/105 Passed，skipped=0**
