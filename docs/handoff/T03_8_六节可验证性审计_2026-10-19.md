### §3 批复

**串信**有明确的清空逻辑，且只清"换信"那一次：


所以"切到另一封还残留已批准字样"这条**应当不出现**；若出现就是缺陷。

**按钮隐藏条件**（`RequiresDecision`）：`action` 为空 → 不显示；`permit_progress` / `news` / 过渡进度 / 财务进度 → 不显示；已上会裁决 → 不显示；只有 `pending`/`deferred` 才显示。

**幂等缺口（代码层可判）**：`Approve` 开头**不检查 `IsOpen`**，也不看状态是否已是 approved：

```278:306:Unity Project/Assets/Scripts/Systems/InboxManager.cs

        {
            ...
            Normalize(mail);
            if (mail.action == "open_route") return AcceptRoutePermit(gs, mail, out message);
            ...
                Mark(gs, mail.id, "approved");
```

防重复靠的是"点完立刻 `RefreshDecisionButtons` 把按钮隐藏"，**不是业务层守卫**。正常单击没问题；同一帧连点两次理论上会走两遍。清单 §2.3 让你"再点一次"，按钮已隐藏就点不到 —— 记"按钮消失"即通过；**不要为了测幂等去绕过 UI 直接调接口**。

**现金是否只动一次**：取决于各 action 分支。`open_route` 走准入办理（本季不扣开航资金）；`buy_slot`/`apply_slot`/`change_slot` 走 `effectPending` + 下季交割，**批准当场不动现金**。清单说的"开航才扣启动资金的，此时不应扣"与实现一致。

### §4 回执延迟投递

节奏常量（`Logic/InboxCadence.cs`）：

| 场景 | 延迟 | 常量 |
| --- | --- | --- |
| 决策后回执 | **4 小时** | `ReplyHours = 4` |
| 节点进度汇报 | 6 小时 | `ProgressHours = 6` |
| 局方受理回执 | 1 个工作日 | `AdmitBusinessDays = 1` |
| 部门会商成稿 | 2 个工作日 | `StudyBusinessDays = 2` |

投递由游戏时钟驱动，不是协程：

```111:111:Unity Project/Assets/Scripts/Systems/TimeManager.cs
                InboxManager.DeliverDue(gs, gs.SimUtc);
```

`DeliverDue` 只投递 `deliverUtcTicks <= now` 的信，且 `Schedule` 会按 id 去重。

**关键换算**：1× 下 4 游戏小时 = **4 现实小时**；3× 下约 **80 秒**。清单 §3 说"让时钟走一格"，若你停在 1× 等 4 小时，会误判成"回执没来"。**必须切 3×，或推进到下一季。**

延迟队列确实在**存档与静态内存**里两处：`GameState.pendingInbox` 存盘；这也是为什么本次禁止改 `.cs` —— 域重载会清静态状态，让这条验证失真。

### §6 数字对照

三处"日/周"的**定义各不相同**，这是最容易把正确当错误的点：

| 位置 | 公式 | 代码 |
| --- | --- | --- |
| 列表 `RouteCard` | `route.dailyProfit`（航线级日净利） | `RouteCard.cs:81` |
| 详情 `n41` 顶部 | `日利 = route.dailyProfit`、**`周利 = dailyProfit × 7`**（航线级） | `RouteDetailPanel.cs:261` |
| 详情 `n41` 班次卡 | **`WEEKLY PROFIT = f.dailyProfit × 该班周班次`**（单班级，不含航线固定成本） | `RouteDetailPanel.cs:382,390` |
| 邮件 | `预估日利润 X 万`（下订时冻结的估值） | RPM / 提案正文 |

也就是说 **`n41` 一屏里同时有"周利"和"WEEKLY PROFIT"两个不同的周数字**，差的就是航线固定成本。清单只提醒了"列表日利×7 ≠ 详情周三"，**没提醒"详情周利 ≠ 详情 WEEKLY PROFIT"** —— 逐格填表时请把这两个分别记。

## 2. 清单预期与实现不一致（必须先改清单，否则误报）

### ❗ 2.1 地图线宽**不**按班次加权

清单 §5 表格写"地图：线宽（越粗越密）…判定标准：线宽顺序应与班次顺序一致（粗 = 班次多）"。

实际实现是**恒定 2.4 屏幕像素**，所有航线一样粗：

```26:26:Unity Project/Assets/Scripts/UI/MapWidget.cs
        const float RouteScreenThickness = 2.4f;                                      // 屏幕像素，不随缩放变粗
```

```389:390:Unity Project/Assets/Scripts/UI/MapWidget.cs
        // ── 航线：深紫色细线，线宽按屏幕像素补偿（放大缩小不改变粗细），无光晕 ──
        static void DrawRoutes(Transform map)
```

`DrawRoutes` 对所有航线都用同一个 `RouteScreenThickness`，没有任何按 `FlightCount` 加权的分支。

**结论：地图上"线宽越粗越密"是设计预期，当前实现没有。** 你要么把它记成"设计缺口"（等裁决），要么先把清单那一行改成"地图不表达班次"。**不要按现在的清单判成"线宽顺序不一致 = 缺陷"**。

### ❗ 2.2 正文滚动必然回顶

见 §2 第 1 点。清单把"滚动位置没回到顶部"和"回到原来那封邮件"写成一个结论，会混。建议拆成"列表滚动"与"正文滚动"两行。

### ❗ 2.3 `航权与时刻槽` 的落点是 `n12` 的页签，不是独立页

见 §1。清单"应打开 `n77 航权与时刻槽`…页面标题对"这一栏，实际会看到"航线网络"。按页签名判断，不按标题判断。

## 3. 判定规则（从现象反推）

| 现象 | 属于 | 处理 |
| --- | --- | --- |
| 点关键词无反应 | 缺陷（白名单没覆盖该词，或链接被 `InsideMarkup` 误判） | 记原词、原句、截图 |
| 跳到的页面标题是"航线网络"但页签对 | 正常 | 通过 |
| `n12` 里出现 `PEK-SHA` 整串当城市 | 缺陷（串键） | 记三字码与邮件 id |
| 返回后列表滚到顶 | 需确认（代码无保存逻辑，但也没强制） | 记当时列表长度、是否期间来过新信 |
| 返回后正文滚到顶 | **现状** | 记"已知"，不算缺陷 |
| 批复后底栏残留上一封的字样 | 缺陷（`_hint` 未清） | 记两封邮件的 id |
| 批准后立刻出现回执 | 缺陷（未走 Schedule） | 记游戏时刻差 |
| 1× 下等 10 分钟没回执 | 正常（需 4 游戏小时） | 切 3× 再等 |
| 地图所有线一样粗 | **现状** | 记设计缺口，不算缺陷 |
| 列表显示"停飞不计营收"但详情仍有日利 | 正常（详情保留设计口径并标注） | 通过 |
