## 2. 本轮新发现的两项工具缺陷（转 S14 验收条件）

### D1 · 检测证据只绑定实现指纹

`review-evidence` / `review-finish` 只校验 `evidence.subjectImplementationFingerprint`，而 review 记录本身保存了 implementation / verification / contract 三份指纹（`subjectFingerprints`）。

同时 `tools/collab/lib/fingerprint.mjs` 的 `IMPL_EXCLUDE_PREFIXES` 明确把 `tools/collab/tests/` 排除在实现指纹之外，理由是“验证自有工具测试不应改变实现身份”。两者叠加的后果：对“交付物本身就是测试”的阶段，实现指纹恒定不变，仅靠实现指纹无法区分两份只差测试的交付。

本次未触发，因为 AC6 同时改了 contract（`a6735b2…` ≠ `fc0d11a…`），使旧通过自动 stale。但若将来出现“只差测试、不改验收条件”的交付，`classifyChange` 只会给出 `needsReverification`，`staleForCurrentCode=false`，证据层无法区分。

### D2 · NEXT_*.md 只按 devStatus 生成

`tools/collab/lib/state.mjs` 的 `refreshFreshness` 末尾写 `NEXT_CURSOR.md` / `NEXT_CODEX.md`：

- `NEXT_CURSOR` 过滤 `devStatus ∈ {todo, developing, rework, ready_for_review}`，`ready_for_review` 一律输出“已交付，等待 Codex”。
- `NEXT_CODEX` 过滤 `devStatus === 'ready_for_review'` 或 `reviewStatus ∈ {queued, running, interrupted}`。

均未考虑 `reviewStatus=passed && freshness=current`。后果：已通过且与工作区一致的阶段仍永久留在双方待办里，读清单的一方可能重复发起检测或误以为还有活。本次会话中“`stage-review` 返回既有通过结论”“S13 仍在 NEXT_CURSOR 等待列表”两处误导都与此同源。
