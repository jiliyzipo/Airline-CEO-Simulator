## 1. 主题与时间「一高一低」

### 病根

列表行是两条文字带（52px 行高）：上带写发件人，下带写主题。旧版把**时间**钉在上带
（`[0.52,0.95]`）右侧，与发件人同一行；而发件人常常只有三个字（「运营部」「新闻官 沈其昌」），
主题又长，于是列表看上去只剩「主题」和悬在它上方的「时间」两截 —— 正是报障截图里的错行感。

时间与主题本来就是同一条信息（这封信、这个点到的），分在两条带上没有人会读成「时间属于主题」。

### 改法

| 位置 | 改动 |
|---|---|
| `InboxPanelUI` | 新增 `SenderBand* / SubjectBand* / SubjectRight / TimeLeft / TextLeft / TextRight` 常量与 `SenderAnchor() / SubjectAnchor() / TimeAnchor()` 三个锚点函数 —— 行内四个标签全部改由这三条函数定位，排版口径只有一处 |
| `InboxPanelUI.CreateRow` | 时间从「上带右」移到「下带右」，与主题**共用同一条上下沿**；上带整条留给发件人（它不再和时间抢宽度，长姓名/长部门名更不容易被截） |
| `SubjectRight` = `TimeLeft` = 0.82 | 主题在下带里截到 82% 处，右侧 18% 留给 `HH:mm`；两者不重叠，也不会互相压字 |

净效果：发件人一行、主题 + 时间一行，主题与时间同基线。

## 2. 「经常几封邮件同时到达」

### 病根（不是某一条投递路径，是投递模型本身）

1. 天级工期（`InboxCadence.StudyReady`、准入节点、合同节点…）算出来的到达时刻一律是本地 **00:00**；
2. 玩家一次推进好几天，所有到期的信在**同一个 SimUtc 瞬间** `DeliverDue`；
3. `StampReceived` 一律拿「现在」当落箱时刻 —— 于是十几封并列 00:00，或并列在玩家点「推进」的那一分钟。

截图里 `20:57 / 20:57 / 06:02 / 06:00 / 00:00…` 的重分钟就是这么来的。

### 改法（两步，都在 `StampReceived` 里，且都是确定性的）

| 位置 | 改动 |
|---|---|
| `InboxTime.OfficeMoment` | 非办公时段（凌晨/深夜）挪进当日 **08:30–18:30**，具体分钟由邮件 id 的稳定散列派生；可用窗口取 `[上班, min(下班, 现在)]`，绝不制造「未来时间」。现在还没上班（凌晨）时窗口落在**前一天**的办公时段 —— 「昨天下班前发的信，今早才看到」 |
| `InboxManager.SpreadMinute` | 与已有邮件撞同一分钟的，按 id 派生 **3–9 分钟**错开，最多 24 次；不跨日（跨日会换日期分组）、不早于当日 08:00 |
| `InboxManager.AddDue` / `DeliverDue` | 到期投递改为按**计划送达时刻**记账（`AddDue(gs, mail, dueUtc)`），不再用「玩家点推进的那一瞬」—— 一堆同时到期的信因此各自落在自己的时刻上 |
| `InboxTime.StableHash` | 邮件 id → FNV-1a 32bit。**不用** `string.GetHashCode`：它在不同运行时/版本取值不同，会让同一份存档每次打开给出不同的落箱时刻 |

只动**显示用的落箱时刻**：`deliverUtcTicks`、`deadlineQuarters`、收件季度、状态一律不碰
（回归 ④ 专钉这一条 —— 错开的只是「几点几分到的」，不该借此改变任何期限判据）。

## 3. 第 5 条问询：开航线时各部门到底检查什么（审计，未改动）

### 已经存在的规则

| 环节 | 现有实现 | 会不会拦住 CEO |
|---|---|---|
| 航线本身成立与否 | `RouteGeography.IsPlausiblePassengerOd`（同城、超航程） | **会**，直接退回、不发请示 |
| 需求 / 收益 | `RouteGravityModel` + `RpmPreview`/`RPMCalculator` → 评分、评级、预估日利润 | 只写进研究会正文，不拦 |
| 现金 | 正文「现金充足 / 不足」；开航执行 `ActionExecutor` 硬判 300 万启动资金 | **会**，执行失败、现金不动，许可继续有效待重试 |
| 运力 | 执行时 `HasSpareAircraftForNewRoute` + `OpsScheduleLogic.ApplyDraft`，失败退回启动资金 | **会** |
| 航权 | `RoutePermitLogic.MissingPrerequisite`：国际/地区航线须占双边航权额度 + 国际运行资质；缺口写进许可单，未办妥许可挂起 | **会**（软拦：许可停在节点上） |
| 时刻槽 | `NeedsSlot` = 国际/地区 **或** 基地始发干线；许可受理时**并行**发起时刻办理；发证后仍缺槽则停在第 4 节点并再提方案 | **会** |
| 准入工期 / 通过率 | `PermitTimeline`：国内非协调 12 天 / 国内协调 21 天 / 国际 49 天；`PassChance` 受竞对运力、安全评级、局方/政府关系影响 | 只写进正文 |

### 缺的三个口子（就是用户问的那几项）

1. **「买/申请哪个时刻收益最大化」——没有。** 自动提案固定用 `ScheduleSlots.DepTimes[1]`＝
   **12:00**（中峰，需求系数 0.90），从不比较其它波次。而项目里本就有两套可比的数：
   `ScheduleSlots.Demands = {1.00 早, 0.90 中, 1.10 晚, 0.80 夜}`、
   `StrategyEconomics.SlotValueWan` 的时段倍率 `{1.4 早, 1.0 中, 0.85 晚, 0.6 夜}`。
   以枢纽机场（基价 600 万）为例：12:00 是「0.90 需求 / 600 万」，18:00 是「1.10 需求 / 510 万」——
   **晚高峰又便宜又旺，现规则一次都没有推荐过它**。
2. **「买」还是「免费申请协调池」——没有比价。** 两条渠道都在（`buy_slot` / `apply_slot`），
   但自动请示永远写「建议购入」，不告诉 CEO 免费渠道排队要多久、这个价买下来值不值。
3. **「现金是否支持」没有合账。** 启动资金 300 万、时刻槽 200–900 万、协调费/违约金是三次分开的决策，
   研究会正文没有一行「这条航线开航前一共要先掏多少、手上够不够」。

### 建议（等裁决后再动）

1. `RoutePermitLogic` 增加 `BestSlotClock(gs, airport, ...)`：按「需求系数 ÷ 该时段槽价 × 池余量」排序，
   取最划算且有余额的一条；`QueueSlotDecision` 与许可节点两处调用点改用同一函数（现两处都写死 `DepTimes[1]`）。
2. 研究会正文加一节「开航前置条件（现在就有 / 还缺什么）」+ 一行「全链条现金：启动 300 + 时刻 X + 协调费 Y」。
3. 时刻提案正文加一行「免费渠道对比：协调池按序分配、不收费，预计排队 N 天；二级市场即买即用」。

## 4. 自测（开发自测，非验收）

| 项 | 结果 |

| `inbox-row-layout` 追加 ⑥ | 主题与时间上下沿完全相同、左右不重叠、「特大」字号下主题带仍装得下；canary＝旧口径必须被判不同带 |

### 负面控制

把 `TimeAnchor()` 还原成旧口径（时间回到发件人带 `[0.68,0.52]–[0.97,0.95]`），重编后专项立刻转红：

```
[Error] 列表行-⑥ 主题与时间没对齐：主题 y[0.08,0.55] x≤0.82，时间 y[0.52,0.95] x≥0.68（须同带且不重叠）
```

恢复后 `--suite all` 29/29 全绿 —— 说明这条判定抓的正是玩家看到的错行，不是摆设。
`inbox-arrival` 的 canary 用「原样返回」当错开实现喂进同一条判定，判定必须拒绝它（回归 ⑤）。

> 过程记录：编辑器失焦时不编译脚本，桥检测到「程序集比源码旧」会拒绝运行而不是报假绿；
> 本轮靠「最小化 → 还原」让编辑器重获焦点完成重编。
