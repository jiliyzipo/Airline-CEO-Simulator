# P24 · 检测证据三指纹绑定与待办收敛（2026-10-26）

阶段：`S14-CollabBinding`
来源：S13 收口时发现的两个窄口子（见 `docs/handoff/S13收口与S14立项_2026-10-26.md`）。

## 一句话

这两处都不报错、不弄脏数据，只会**让人看错**：一处让「只改了测试」的新交付可以捡走上一份交付的检测证据；一处让已经通过且与工作区一致的阶段，永远留在双方的待办清单里。

## 一、D1 · 证据只绑了实现指纹

`review-finish` 原来只校验一个字段：

```
evidence.subjectImplementationFingerprint === delivery.fingerprints.implementation.fingerprint
```

而 `tools/collab/lib/fingerprint.mjs` 的 `IMPL_EXCLUDE_PREFIXES` 明确把 `tools/collab/tests/` 排除在实现指纹之外（理由正当：验证方自己的测试不该改变实现身份）。

两者叠在一起就出现一个洞：**交付物本身就是测试的阶段，实现指纹是恒定的**。`DEL-20261026063907-c4218e` 与 `DEL-20261026092125-d3b2a1` 的实现指纹都是 `26b4144…`，真正区分它们的是 `verification`（`8753be1…` → `eedfd8e…`）和 `contract`。

更糟的是 `classifyChange` 对这种变化只给 `needsReverification`，不给 `staleForCurrentCode`——所以「旧走过、新交付只差测试」时，账本层不会把旧结论判 stale。S13 那一轮之所以没出事，是因为 AC6 顺手改了契约（`fc0d11a…` → `a6735b2…`）把旧结论顶掉了，纯属运气。

### 改法

- `commands.mjs` 新增 `FINGERPRINT_PARTS` 与 `deliveryFingerprintTriplet(delivery)`：**一个交付的身份就是三份指纹，不接受子集。**
- `cmdReviewEvidence` 在草案里写入 `subjectFingerprints: {implementation, verification, contract}`，同时保留旧的单字段便于阅读。
- `cmdReviewFinish` 改为三段校验，任一段失败都是 `EXIT.EVIDENCE`(6)：
  1. `review.subjectFingerprints` 与交付记录三份对不上 → 拒绝（并要求重开 review）；
  2. 证据缺 `subjectFingerprints`、缺任意一段 → 拒绝；
  3. 某一段与交付不一致 → 拒绝，并回显 `expected/got`。
  另外还挡了自相矛盾的证据：`subjectImplementationFingerprint` 与 `subjectFingerprints.implementation` 不一致也拒绝。
- `stage.mjs` 自动生成的证据同步写三份指纹，`stage-review` 路径不需要人工补字段。
- run 记录也带上 `subjectFingerprints`，事后能看出这一次到底在什么身份上跑的。

## 二、D2 · 待办清单只按开发状态生成

`state.mjs` 里 `NEXT_CURSOR.md` 与 `NEXT_CODEX.md` 的筛选条件分别是 `devStatus ∈ {todo, developing, rework, ready_for_review}` 和 `devStatus === 'ready_for_review' || reviewStatus ∈ {queued, running, interrupted}`。

`reviewStatus=passed && freshness=current` 完全不参与判断。于是：

- 已通过、与工作区完全一致的阶段（S13）仍显示「已交付，等待 Codex」；
- 反过来，历史通过但工作区早已变化的 18 个阶段，也仍显示「等待 Codex」，看不出它们其实需要按当前代码复验。

### 改法

判定一个任务「已收口」= `reviewStatus === 'passed' && freshness === 'current'`，双方清单都跳过这类任务；其余情况保留并写明原因：

| 情形 | NEXT_CURSOR | NEXT_CODEX |
| --- | --- | --- |
| passed + current | 不出现 | 不出现 |
| passed + stale | 历史检测已通过，但工作区已变（freshness=stale），需按当前代码复验 | …（历史通过仅对应旧快照，需按当前代码复验） |
| rework | 按缺陷修复后重新 deliver | 开发=rework 检测=… |
| ready_for_review（未通过） | 已交付，等待 Codex | 开发=… 检测=… |
| queued/running/interrupted | 按 devStatus 归类 | 保留 |

`rework` 分支放在 `passed` 之前：一个已经回到返工态的任务，给开发看的应该是「去修」，不是「去复验」。

缺陷行也改成按真实状态输出（`[status/severity]` + 归属 + task），不再是「仍开放」四个字——`fixed` 与 `open` 现在在清单上能分开。

## 三、回归怎么验

新增三条 daily 用例（`tools/collab/tests/daily.test.mjs`），都走真实管线，不做纯函数打桩：

| 用例 | 验的是什么 | 怎么造 |
| --- | --- | --- |
| `D22` | **只差验证指纹的两份交付不可互换证据** | 交付 → review → 通过；然后在 `tools/collab/tests/` 写一个文件（该路径被实现指纹排除），再次交付。断言两次交付 implementation 相同、verification 不同，且拿旧证据去 finish 新 review 必得 exit 6；用新证据则正常通过 |
| `D23` | **缺字段证据被拒** | 用同一份草案改出三种残缺：整段缺失、只留 implementation、三段中 verification 被改；三种都必须 exit 6；原样草案仍能通过（避免把「严格」写成「一律失败」） |
| `D24` | **待办清单反映真实待办** | 通过后 sync：`NEXT_*.md` 不再出现该任务；在 pinned 根目录制造漂移后 sync：任务以 `freshness=stale` 重新出现并带「需按当前代码复验」；再置回 rework：文案变回「按缺陷修复后重新 deliver」 |

`D22` 的见证点写在测试里：先断言 `implementation` 两份相同，再断言 `verification` 不同——如果哪天指纹策略改了实现口径，这条用例会立刻以「fixture must not move the implementation identity」失败，而不是悄悄失去意义。

## 四、覆盖边界

- 没有把证据改成「快照清单哈希」：交付已由 `verifySnapshotIntegrity` 逐文件比对，重复做一遍只是把同一件事写两处。证据层的缺口是**身份**，不是**字节**。
- 没有放宽 `IMPL_EXCLUDE_PREFIXES`：把 `tools/collab/tests/` 算进实现指纹会让「验证方改测试」污染实现身份，那是更坏的口径。缺的只是证据要绑全部三段。
- 没有顺手改 `classifyChange`：`needsReverification` 的语义本身正确（交付身份不变、基线变了）。真正要补的是证据层不认旧证据——这正是 AC3。
- 旧证据不会追溯改写：`review-finish` 是一次性终点，历史 review 记录保持原样。
