EXECUTIVE SUMMARY

总体判断

Cursor 的技术评估有价值，应采纳其主要发现及分阶段开发思路；但不建议按它提出的 P1 方案直接修改正式游戏。

Cursor 对照现有代码发现：机场容量仍基于跑道数、背景航司占用分配会系统性填满热门时刻、放宽容量还将改变航线扩张、时刻交易及经济平衡。相比概念性方案，这是更有操作性的诊断。

最重要的纠偏：“除数27 ≈ 当前总容量”不等于“81个机场的容量逐场保持不变”。不能把它当作无风险的架构迁移方案。

02 · CRITICAL CORRECTION

除数27不是安全的“数值不变”过渡方案

Cursor 建议先把申报容量按27缩放，保持世界总规模与现状相近；等确认迁移成功后再切到16。分离架构与平衡变更的原则正确，但具体做法无法真正保留现有机场容量。

复核方式：从 Cursor HTML 附带的81机场记录读取跑道数、申报小时架次，以 max(1, round(D÷27)) 对比逐场现值，得到总量248、45场变化。

建议新增 C0 方案：迁移首期保留旧跑道平铺容量的显式兼容模式，保证所有机场逐场数值不变。新申报容量模式独立开启，用除数16和12做平衡试验。这样“先结构、后数值”才是真正可验证的。
03 · CAPACITY CONSERVATION

离港、到港同数取整：全局误差小，不等于局部误差小

Cursor 建议暂时接受双方向对称取整带来的全行业约1.8%超发，以避免一次性修改多个接口。短期兼容测试可接受，但不应作为“贴近现实”的最终模型。

裁决建议 B2：正式启用申报容量模型前实现双方向与总容量守恒。可考虑添加分方向查询接口/兼容重载，逐步替换旧调用，而不是预设必须“一次修改全部函数签名”。
04 · CROSS-MIDNIGHT

凌晨时刻必须归入夜班，不应改掉既定 UI

Cursor 发现后台早班池覆盖00:00–09:45共40刻，而夜班池仅20:00–23:45共16刻；界面却按06:00开始显示早班。这是后台池归属和界面语义不一致，并非简单文字问题。

正确工作：先审计跨午夜池、航班时刻、已持有槽、申请与二级交易的映射，再制定安全迁移方案，保持现有已确认的四时段界面和96格总量。

05 · DOMAIN SEPARATION

跑道数量、申报容量与游戏容量应分层

Cursor 找到集中入口 QuarterCapacityRaw → RunwayCountOf × SlotsPerRunwayPerQuarter，说明初步接入有机会做到局部改造。但不能为了减少代码行数而改变 RunwayCountOf 的原始语义。

数据概念含义建议职责
物理跑道数机场基础设施属性继续由跑道数据查询提供
申报时刻容量机场在某个口径/日期/协调条件下的可用能力独立数据表、带来源和有效日期
游戏可分配容量缩放、时段限制、离到方向分配后的最终容量统一容量查询接口计算

应提供 CapacityOf 或同等专用接口，显式选择兼容模式或申报容量模式。数据缺失时必须可诊断，禁止默默回落到按机场等级猜测的数值。

06 · EXTENSIBILITY

81个机场是初始数据集，不是固定上限

Cursor 表示没有“81”的硬编码循环上限，但新增机场需同时维护四张通过 IATA 字符串关联的数据表。

现有数据表职责
AirportCatalog机场身份、等级、协调属性
AirportRunways跑道数量
AirportGeoCatalog地理坐标
CityEconomyCatalog城市及经济数据

现阶段无需强行把四表合并，但要新增数据完整性检测与统一机场容量接入接口，保证未来扩充至更多机场时不会因漏填而无声失败。

第三旋钮继续采用“机场容量演进机制”：适用于任何现有或未来机场，不限于报告标记的5座富余机场。当前只设计扩展接口，完整扩建玩法等经营闭环稳定后再做。
07 · DECISIONS

四个待裁决问题：建议 A1 / B2 / C0 / D1

A
高峰时刻是否必须留空？

先用75%的初始占用率进行测试，不强制每刻硬留一条。允许热门机场满池，但应验证玩家是否仍有合理可执行的开线方案。

B

正式新容量模型以分方向及总架次守恒为目标；可先保留旧接口作兼容测试，之后渐进迁移。

B2 · 目标
C
新架构的过渡默认值？

不在原C1/C2中选：新增C0，采用旧跑道平铺兼容模式保证逐场值不变，不能用除数27假装无变化。

D

保留为机场运行特征、容量可信度核查及缺失数据时的估算参考；可靠申报容量优先，不另做六套重复算法。

P0
可开始

P1-A
审批后
新容量数据层 + 显式兼容模式
引入申报容量、来源、有效日期；保持旧机场逐场容量不变；新增容量查询接口；确认缺数据时不会无声猜测。
P1-B

P1-C

P1-D

P2
暂缓
容量演进、真实AI竞对、多人

10 · FINAL RECOMMENDATION

最终结论

项目判断
真实容量 + 三旋钮的总体架构建议采纳
Cursor九组离线模拟可用于后续验证
用除数27作为“数值不变”迁移建议否决
除数16 × 75%初始占用优先测试，未定稿
完整AI竞争及机场扩建玩法暂缓开发
当前应批准：Cursor开展P0数据审计、模拟复核与测试工具建设。当前不批准：整套P1直接上线，更不应直接将“除数16×75%”写死到正式存档或经济平衡中。

三个旋钮的最终职责：①世界容量比例，决定能提供多少时刻；②初始市场占用率，决定开局已有多少资源被背景航司持有；③机场容量演进机制，决定所有机场未来如何变化。

资料与验证边界：本报告以 Cursor《时刻容量与三旋钮_技术评估_2026-11-09.html》及此前架构建议为依据。报告中引用的代码路径、业务行为、Unity兼容性结论来自 Cursor 的代码审查叙述；本报告未直接执行Unity测试。另对上传的评估HTML内嵌81机场表的“除数27”逐场计算进行了复核。所有参数结论均为候选或开发建议，非正式上线确认。
