02 / DISPUTE 1 · OVER-ALLOCATION

争议一：撤回「旧档必然超配」，并给出构造性证明

我方错在哪

原报告写「ORD 早班池 320 → 128，玩家持有 200 条即当场超配 72 条」。这是拿旧早班的总持仓去比新早班的池容量，两个集合不同源：00:00–05:45 的持仓在 B 下改归夜班，必须从早班分子里剔除。对方指出的正是这一点。

为什么代码层面根本不会超配

// IndustryAirlineLogic.IndustryHeldOfKind  (第 142–168 行)
int cap  = RoutePermitLogic.SlotPoolCapacity(airport, band);
int ours = RoutePermitLogic.PoolUse(gs, airport, band, kind);
int room = cap - ours;
if (room <= 0) return 0;
...
if (want > room) want = room;        // ★ 他航在池级先让位

// DepLayout (第 543–552 行)
var perQ = OursLayout(gs, airport, band, DEP, grid, capAt);  // ★ 我司先落位
int industry = IndustryHeld(gs, airport, band);
FillWave(perQ, capAt, grid, airport, industry, ...);         // ★ 只填到 capAt 为止

两条约束叠加后，我司 + 他航 ≤ 容量 在逐刻与池级两个层级都恒成立，与班次如何划分无关。OursLayout 里还有 Place(...) ? : break——放不下就停，不会「为凑数超发」。所以班次边界移动只改变账怎么分，不改变总量守恒。

03 / DISPUTE 2 · ECONOMY

争议二：撤回「不冲击经济平衡」，并交出比对方更不利的数据

我方原话是「总余量 9,800 → 9,800 几乎不变，所以不冲垮经济平衡」。对方指出：把藏在凌晨的余量移到营业时段，会改变可开航线、周班次与二级市场依赖。这条批评成立，我方撤回。

总量守恒被验证了（3,116 → 3,108，差 −8 来自各池 floor 取整），但守恒的代价被上一版藏起来了：

机理：这不是「搬余量」，是「他航余数换落点」

FillWave 把同一批槽按需求权重降序摊开，摊不完的余数必然落在该池内权重最低的刻。

  • 布局 A 的早班池含 00:00–05:45（权重 0.27），余数落那里 → 06:00–09:45 被填满。
  • 布局 B 的早班池只剩 06:00–09:45，池内最低权重变成 06:00（0.77），余数就落到 06:00 → 102 场「有余量」，但每家每刻通常只有 1 条。
  • 反向：夜班池内最低权重是 00:00–05:45，余数落那里；20:00–23:45（0.36–0.64）优先被填满 → 22:00/23:00 塌陷。
结论：B 的实际效果是「每场每刻让玩家多拿约 1 条早晨槽，代价是晚间可用性塌陷」，不是容量增加。这比「总余量不变所以安全」更接近真相，也更需要实测——所以我方主张：P1 之前补一轮 Unity 内 A/B 经营实测，而不是直接按 B 开工。

05 / DISPUTE 4 & 5

争议四、五：接受，并给出限定后的准确表述

峰值闭式判据的适用范围（按对方要求加限定）

原式 floor(n·C·r) ≤ (C−1)·n + 3 成立的前提有四条，缺一即失效：① 每刻容量恒定（= SlotPoolCapacity / 刻数）；② 他航按 FillWave 权重轮转铺排；③ 段级 MustLeaveOpen = 1；④ 余数按 HourDemandCoef 降序落在至多 4 个峰刻。因此它只是当前算法的代数结论，不是机场容量的物理定律；换铺排算法、换容量曲线，该式需重推。1,440 组穷举 0 反例只证明「与当前实现一致」，不证明「普遍为真」。

单一容量真相源（接受，并明确迁移边界）

层职责与现有 int[4] 的关系
CapacityService唯一权威：输入机场数据 + 航季 + 生效日期 + 容量变更事件，输出「单机场 / 单刻 / 单方向」可发布容量—
派生缓存15 分钟容量、四班次池容量、已占用/余量AirportInfo.slotCapacity 降级为只读派生缓存，可失效重建；不再是真相源
兼容读取AirportCatalog.SlotCapacity(code, band, kind) 签名不变，内部转调 service迁移期保留，便于回退；但不得与 service 并存两套独立计算

注意一个现存缺陷：SlotCapacity(code, band, kind) 的 kind 参数当前被忽略，到港与离港返回同一组数。做单一真相源时必须顺手修正，否则「到港已满、离港还有」这种情况永远算不出来。
