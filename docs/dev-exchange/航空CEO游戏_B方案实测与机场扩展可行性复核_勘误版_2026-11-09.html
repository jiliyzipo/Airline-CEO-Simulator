三个结论

  1. 峰刻几乎没有改善。固定占用率下 08:00 完全不变（56 → 56、27 → 27）。真实哈希下 12 → 17，多出的 5 场全在临界容量 C = 7–8。

02 · CRITERION

峰刻能否留出余量：闭式判据（已穷举验证）

上一轮我用「C ≤ 1/(1−r)」这个粗判据，它差一位。精确判据是：

设段内 n 刻、每刻容量 C、占用率 r：
他航占用 want = ⌊n·C·r⌋（段级 MustLeaveOpen = 1 之后）

峰刻留得出余量 ⟺ ⌊n·C·r⌋ ≤ (C−1)·n + 3

直觉：轮转底座每刻铺 C−1 条，共占 (C−1)·n；余数只有落在「权重最高的一个高峰小时（4 刻）」时才填满，
故上限是 (C−1)·n + 3 —— 第 4 条余数溢到次高峰，第一个小时的最后一格才空出来。

验证方式：对 n ∈ {13,16,20,40}、C ∈ [1,40]、r ∈ {0.55…0.92} 共 1440 组做逐刻仿真与判据比对，反例 0 组。

03 · COST OF B

重分布的真正形状：拿晚间换早晨

总量守恒不等于分布无害。逐小时统计「至少还剩 1 条可申请」的机场数（103 场，out/analysis/b-impact-sim.mjs）：

结论修正：B 不是「把看不见的凌晨余量搬到白天」，而是用晚间可申请量去换早晨可申请量。总量 3,116 → 3,108 几乎不变，但 20:00–23:45 的可用性大幅下降。这解释了为什么不能只用「全天余量不变」判断经济影响——本报告原「不冲击经济平衡」的说法一并撤回，必须做同种子 A/B 经营对比。

再补一刀：06:00 的收益是「他航余数换了落点」，不是容量增加。FillWave 把同一批槽按权重降序摊开，摊不完的余数必然落在**该池内权重最低的刻**。布局 A 的早班池含 00:00–05:45（权重 0.27），余数落那里；布局 B 的早班池只剩 06:00–09:45，池内最低权重变成 06:00（0.77），余数就落到 06:00。所以 102 座机场在 06:00「有余量」，实际每家每刻通常只有 1 条——够开一条新线，不够扩张。反过来，夜班池内权重最低的是 00:00–05:45，余数落在那里，而 20:00–23:45（0.36–0.64）优先被填满，这就是 22:00/23:00 塌陷的机制。

B 的真实代价改判：不是超配，是他航被挤出。早班池容量从 10,756 缩到 4,860（−5,896），夜班池等量膨胀。由于他航必须让位，被挤掉的 5,268 条全部落在背景航司身上：他航占用 9,565 → 4,297（早班）、4,097 → 9,373（夜班）。玩家持仓一条不掉，但「机场看起来变空了」——这是画面与竞争强度的变化，不是存档损坏。

上一版「告警之后怎么办」的产品问题因此作废：不需要强制退槽、不需要宽限期、不需要自动删除，因为根本没有超配发生。仍需保留的只有真正的异常档处置（见下）。

仍需单独处理的三种真实残留：① 持仓 slotTime 不在 15 分钟网格上（数据模型不强制，FormatClock 只格式化不对齐，BandOfClock 按小时归档 → 该持仓占池容量却没有对应刻），此时 OursLayout 的 Place 会失败并 break，界面上「静默少显示几条」；② 配对持仓的 arrTime 跨班次边界时，到港池归属会跟着变，本版只逐刻验证了离港池；③ 早于 f41de9d「跑道经济重解」的远古存档，其持仓是按更早的容量曲线取得的，与今日平铺口径本就不可比——这与 B 无关，属历史遗留。
04 · EXTENSIBILITY

「机场不设上限」：一项通过，四项阻断

已通过：无固定数量上限

全仓检索 81 / 103 / 104，没有定长数组、没有遍历上限、没有「超过 N 就拒绝」的分支。所有枚举都是 All.Length；AirportCatalog.Filter 已支持按关键词检索并有 limit 参数；TryResolve 已支持按名称解析。反馈验收第 1 条现在即可通过。

阻断项（按修复顺序）

#阻断代码事实后果
1机场只有 IATA 主键，无 airportId、无 ICAOAirportInfo.code 即 IATA；跑道 / 地理 / 城市经济三表、以及存档里的 SlotHolding.airport 全部用 IATA 字符串关联验收第 6 条「只有 ICAO 没有 IATA 的机场」无法录入；且小机场 IATA 可能变更，主键不稳定
2All 是静态只读字面量、元素是 structstatic readonly AirportInfo[] All = { … }，在静态构造时一次性填 tier / coordWindow / slotCapacity没有运行时 add 路径；无法「玩家启用附近机场」
3容量在静态构造时烘焙成 int[4]a.slotCapacity = new[]{ BandCapacity(…) × 4 }，SlotCapacity() 直接返回该数组第三旋钮（容量随时间演进）无处挂载；且 FindByCode 返回 struct 副本，改不动原数组
4没有机场时区游戏时钟是全局 UTC；LocalUtcOffset = DateTimeOffset.Now.Offset 是运行机器的时区，与机场无关「机场当地 06:00」当前不成立；跨午夜、航季边界、夏令时无法正确判定
5检索是线性扫描FindByCode 遍历 All；TierOfCode → FindByCode → QuarterCapacity 在逐刻循环里被反复调用（全仓 26 处 FindByCode、11 处 TierOfCode）5,000 场时是 O(n²) 级；必须先建 Dictionary 索引

05 · ACCEPTED

接受的两条批评

1. 统计口径混用上一轮报告把 81 场样本的 248／+2.32% 与 103 场的 15,392／39.0% 并列，读者会误以为是同一世界总量。以后每个数字必须带分母与算法版本。接受
2. 不得把中国机场峰刻未解锁全归因于申报值应三分：① 每刻容量 C 太小（数据根因）② 占用率 r 太高（参数）③ FillWave 顶权重优先（算法）。用 §02 的判据可逐场分解，而不是笼统归因。接受
06 · TRAPS

B 实施时必踩的三个代码陷阱

#陷阱说明
1BandGrid 按分钟升序生成B 的夜班网格会是 [00:00 … 05:45, 20:00 … 23:45]，不是从 20:00 开始。矩阵列序会错；FillWave 的 index 平局排序也用这个顺序
2MatrixGrid 的裁剪不支持跨午夜hour >= h0 && hour <= h1，当 h0 = 20、h1 = 5 时恒 false。现在只靠「有 chip 就补一列」的兜底在显示，改 BandHourStart/End 前必须先改裁剪逻辑
3WindowStart/WindowEnd 是需求波窗口（6:30–9:30 等）与班次池无关，但它同样按「早班含 00–05」的旧假设写就。改 BandOfDep 后必须一并审计，否则「需求波」和「池归属」会说两套话

已复核《对 Cursor 复核的反馈及机场无限扩展要求 v1.1》。以下为实测结论，请据此更新方案。 一、B 方案（早16/中20/晚20/夜40）：可采纳，但收益与代价要写清 1. 峰刻几乎无改善：固定占用率下 08:00 有余量的机场数完全不变（D16·75% 为 56→56，现状·75% 为 27→27）；真实哈希下 D16·87% 为 12→17，多出的 5 场全在临界容量 C=7~8。 2. 真正收益在 06:00：现状 22→102 场、D16·87% 36→80 场。原因是早班池从 40 刻缩到 16 刻后，AI 的余数不再溢进界面不显示的 00:00–05:45。 3. 全天余量几乎不变（D16·75% 9800→9800），B 是余量重新分配，不是放宽稀缺度，因此不冲击经济平衡。这是采纳 B 的主要理由。 4. 宵禁机场完全不受影响（PEK 16→16 / 12→12），受影响的是 24 小时非宵禁机场加贵阳。 二、B 的代价：早班池超配（必须提前承认） 5. 24 小时非宵禁机场早班池 40R→16R，即 −60%；受影响 84/103 场，其中早班池原容量≥100 的 46 场（ORD 320→128、DFW 280→112、CAN/ATL/IAH/YYZ 200→80、PVG/PKX/LAX/JFK 160→64）。 6. 老存档**不会**超配：他航在池级先让位（want > room → want = room）、OursLayout 先铺我司持仓，故「我司 + 他航 ≤ 容量」恒成立；逐刻三策略复核为 0 / 0 / 503。B 的真实代价是他航被挤出早班（−5,268 条）以及 22:00–23:45 可申请量塌陷（71→22、84→3）。 7. 存档 schema 确实不用迁（SlotHolding 只存 airport/slotTime/kind，band 由 BandOfClock 反推），但池容量变了，所以兼容风险存在。上一轮「没有兼容风险」的说法作废。 三、峰刻判据修正 8. 精确判据：峰刻留得出余量 ⟺ floor(n·C·r) ≤ (C−1)·n + 3（n=段内刻数，C=每刻容量，r=占用率）。粗判据 C ≤ 1/(1−r) 差一位。 9. 已对 n∈{13,16,20,40}、C∈[1,40]、r∈{0.55…0.92} 共 1440 组穷举验证，反例 0。 10. 87% 下 n=40 需 C≥7，n=16 只需 C≥6 —— 这是 B 唯一的数学收益。 11. 修正上一轮：D16·87% 下 08:00 有余量的是 12 场（真实哈希），不是 15 场；「欧亚门户一座都没有」作废，CAN 在 B 下可拿 2 条。 四、机场不设上限：一项通过、四项阻断 12. 通过：全仓无 81/103/104 定长数组或遍历上限，全部用 All.Length。验收第 1 条现在即可通过。 13. 阻断 1：机场主键只有 IATA，无 airportId、无 ICAO；四表与存档全用 IATA 关联。验收第 6 条（只有 ICAO 的机场）无法录入。 14. 阻断 2：All 是静态只读字面量、元素为 struct，静态构造时一次烘焙，无运行时 add 路径。 15. 阻断 3：容量烘焙成 int[4]，第三旋钮无处挂载；FindByCode 返回 struct 副本，改不动原数组。 16. 阻断 4：无机场时区，LocalUtcOffset 是运行机器的时区，与机场无关，「机场当地 06:00」不成立。 17. 性能：FindByCode 为线性扫描且被逐刻调用，5,000 场是 O(n²) 级，必须先建 Dictionary 索引。 18. 四表覆盖：目录 104、地理 104、城市经济 104、跑道 88 —— 缺 15 座（SHE/LHW/WUX/NGB/WNZ/NNG/TYN/HET/MFM/ACC/CPT/LOS/NBO/AKL/PER）目前按等级静默回落，正是「缺数据必须可诊断」要针对的实例。 五、接受的批评 19. 统计口径混用：上轮把 81 场样本的 248/+2.32% 与 103 场的 304/39.0% 并列，以后每个数字必须带分母与算法版本。 20. 不得把中国机场峰刻未解锁全归因于申报值，应三分：容量 C、占用率 r、FillWave 算法；可用判据逐场分解。 六、B 实施的三个代码陷阱 21.
