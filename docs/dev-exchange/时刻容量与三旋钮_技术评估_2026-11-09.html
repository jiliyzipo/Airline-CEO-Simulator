1 · 代码事实核查

1.1 有没有写死「81」？——没有，但「只录入一处」不成立

全库 rg "\b81\b" 只命中两处注释与一处 MenuItem 优先级，没有数组长度、循环上界或枚举依赖。 但新增一座机场要同时改 4 张按 IATA 字符串对齐的表，编译器不管它们是否一致：

表作用缺了会怎样
AirportCatalog.All[]机场名、等级、协调属性机场不存在
AirportRunways.Counts跑道数（= 当前容量）静默落回「按等级猜 3/2/1」（回归 ⑨ 会报警，但只对协调机场）

1.2 容量的唯一权威 —— 改动面极小

// AirportCatalog.cs:593
static int QuarterCapacityRaw(string code, int tier, string coordWindow, int minutes)
{
    if (string.IsNullOrEmpty(coordWindow)) return 0;
    int m = ((minutes % 1440) + 1440) % 1440;
    if (!InCoordWindowText(coordWindow, m)) return 0;      // 协调时段外：免槽
    if (InCurfewWindow(code, m)) return 0;                 // 宵禁：物理禁飞
    return RunwayCountOf(code, tier) * SlotsPerRunwayPerQuarter;   // = 1
}

调用链只有一个入口：

QuarterCapacity(code, minutes)            ← 逐刻容量（唯一判据）
   ├─ HourCapacity → DayCapacity           ← 报表 / 界面日总量
   ├─ BandCapacity → slotCapacity[4]       ← 四个池的总量（段宽 40/20/20/16 刻）
   ├─ RoutePermitLogic.SlotPoolCapacity    ← 申请 / 买入 / 满池判据
   ├─ RoutePermitLogic.SlotsAvailableAt    ← 逐刻余量（玩法的硬闸门）
   ├─ IndustryAirlineLogic.ClockCaps/Chips ← 他航铺排上限
   └─ tools/slotreport/Program.cs          ← 只读报表（CSV / HTML）

RunwayCount 全库仅 6 处引用，全在 AirportCatalog 与 AirportCatalogRegression 里，没有任何业务代码直接读它，UI 也不显示跑道数。 所以「把容量从跑道数换成申报值」只要换掉 RunwayCountOf 的返回值，整条链自动跟着变。

1.3 单位与 1:1 的真相

QuarterCapacity 是每刻、每方向的槽数（离港池与到港池各取这个数）。 因此 1 条槽/刻/方向 = 4 刻/时 × 2 方向 = 8 架次/时。 现行 SlotsPerRunwayPerQuarter = 1 ⇒ 一条跑道 = 8 架次/时，而现实单跑道约 28–45。

现实 1:1（= 除数 8）855100%164,160—
除数 1257166.8%109,632102,912
除数 1643550.9%83,52078,400

关键换算：现状 ≈ 除数 27.5，不是 22。 「换成除数 16」意味着世界容量要在现状上再放大 1.75 倍 —— 请按这个理解去判断是否接受， 而不是按「砍到现实的一半」理解。

1.5 存档：好消息与坏消息

  • 好消息：容量不进存档。slotCapacity 是静态构造期算出来的运行时字段，GameState 里没有它。改容量公式不会让旧档结构失效。
  • 坏消息一：没有 schema 版本号。全库搜不到 saveVersion / schemaVersion；迁移靠 MigrateSlotTimes / MigrateLegacyBudget 这类幂等补救函数逐个调用。容量一旦变化，「旧档持仓超过新容量」没有任何地方会检测。
  • 坏消息二：SlotsAvailable 对负值钳 0，所以超配不报错、只表现为「莫名其妙没有余量」。

2.1 差异的性质分类（决定工作量）

  • A 类 · 只缺数据，不缺结构（便宜）：把跑道数换成申报值。因为 RunwayCountOf 是唯一出口，改动被 AirportCatalog 封死。
  • B 类 · 缺维度（中等）：方向（DEP/ARR 不同数）、生效日期（航季）、时区。
  • C 类 · 缺机制（贵）：容量演进事件、协调等级分化、AI 行为。
  • D 类 · 报告漏掉的（最贵也最关键）：AI 占用分布算法（见 §2.3）。

2.2 报告 §1.4 的算法在本项目可以大幅简化

// 报告的通用机器
S = 8 / 除数
M(h) = D(h) × S              # 小时总动作预算
把 M(h) 分到 4 个 15 分钟格（整数守恒）
每个格再分离港 / 到港

这套东西解决的是「有小时曲线时，怎么在 4 个格里做整数分配且不超发」。但本项目容量是平的， 且池的粒度是「4 个时段」而不是「96 个小时」：

// 若 D(h) = D（常数）
每刻每方向 = D × S / 8 = D / 除数

整条算法退化成一个整数常量：

每刻每方向槽数（单场） = max(1, round(申报架次/时 ÷ 除数))

// 数据侧只保留一条物理校核（防止把手填错）：
申报架次/时 ≤ 60 × 物理跑道数        # 单跑吞吐物理上限约 45–55，60 是宽松天花板
注意：现有的「等效 ≤ 物理×2」这条护栏必须换掉。 它成立的前提是「一条跑道 ≈ 8 架次/时」（现行口径），而申报值的量级是 28–45 架次/跑/时。 ATL 5 跑道 220 架次/时 = 44/跑，D16 换算是 14 槽/刻，14 > 5×2=10，会被旧护栏直接判红。 正确的护栏是「申报值本身 ≤ 60×跑道数」，不是「换算后的槽数 ≤ 2×跑道数」。

2.3 报告没写、但代码里确实存在的结构性问题（最重要）

IndustryAirlineLogic.FillWave 的真实行为不是「先把高峰填满」，而是轮转填充：

for k in 1..want:
    for t in 0..n-1:
        j = order[cursor % n]; cursor++
        if perQ[j].Count < capAt[j]: 放一条; break

order = 该段所有刻按 HourDemandCoef（与槽价同源的小时需求系数）降序。于是： 每轮循环给每个刻各加一条（均匀底座 m = floor(C × 占用率)）， 余数只落在权重最高的前 r 个刻上。由此得到一条可验证的判据：

判据：设每刻容量 C、占用率 r。底座 m = floor(C×r)； 当 C ≤ 1/(1−r) 时 m = C−1，段内余数集中在权重最高的刻上， 最挤的那个小时恰好被填满（0 余量）；只有 C > 1/(1−r) 时（87% 下即 C ≥ 8）， 最挤的小时才留得出 1 条。
机场每刻容量 C最挤小时的余量有自由槽的小时（87%）
XMN107 / 08 / 09 / 12 / 18 全 0只有 04:30–05:45、10:00–10:45、15:00–15:45、23:00–23:45
ATL507 / 08 / 09 / 12 / 18 / 20 全 0其余每小时各留 1–4 条
LHR（D16）607 / 08 / 12 / 18 全 0其余每小时各留 4 条
ATL（D16）1408 时余 4（每刻 1）全小时都有余量
ATL（D16·75%）14全部有空每小时 12–16 条

三条结论：

  1. 「最挤的那小时永远没有免费槽」不是设计失误，是 floor(C×r) = C−1 的算术必然。 只要 C ≤ 1/(1−r)，无论容量多大、除数 12 还是 16，峰刻都会被填满。
  2. 放大容量只对「大机场」有效：C 越过 1/(1−r) 之后峰刻才出现余量。 实测 D16@87% 下，「08 时有空」的 15 家与「每刻容量 ≥ 8」的 15 家 完全同一集合，无一例外——判据是精确的，不是近似。
  3. 降低占用率是最直接的杠杆：75% 时阈值降到 C ≤ 4，只有 25 家小机场峰刻仍满。

4 · 影响面

4.1 机场时刻申请 — 数值变，逻辑不变

  • 申请闸门只问 QuarterCapacity − 我司 − 他航，容量变大 ⇒ 余量变大 ⇒ 更容易申请。
  • 免费协调池是按序分配、不收费，所以容量放大直接等于「免费通道变宽」。
  • 一个真实风险：NearestClaimableClock 会把申请时刻吸附到最近的「当时真能申请」的刻。 峰刻锁死时，申请单可能被吸附到 03:00 这种刻上——排班器随后会认为「你有 03:00 的槽、却想 08:00 飞」，两者互相打脸。 容量放大后这种现象不会消失（因为峰刻仍满），只会把吸附距离缩短。

4.2 二级市场 — 受影响，而且是反向的

  • 挂牌量、叫价都来自 SlotMarketLogic，其中 FairValueWan → StrategyEconomics.SlotValueWanAt 只看机场等级与小时系数，完全不看容量。所以容量放大 1.75 倍 ⇒ 可获得性上升，但同一条槽的价格一分不变 ⇒ 稀缺溢价被稀释，市场存在感下降（除非占用率维持 87% 让峰刻继续锁死）。
  • 他航挂牌的溢价路径是 fair × AskPremium(1.15)，同样与容量无关。
  • 不一致点：若将来容量按「富余档 F」上调而价格不跟着动，就会出现「TSN 的槽和 PEK 的槽一个价」。

4.3 航线经营 — 最需要警惕的连锁

  • 排班四道闸门（时刻槽 / 值勤 / 机队 / 机组）中，只有第一道受容量影响。
  • 容量放大 ⇒ ApplyWaves 能排出的波次变多 ⇒ 周班次上升 ⇒ 收入上升。
  • RouteFrequencyModel 的周班次上限由「城市对需求 ÷ 单机可飞」决定，没有「机场总量预算」这一层。 所以容量放宽 = 打开更多线 = 利润近似线性增长，而成本侧按班次线性增长，只有地面与时刻成本是准固定。 报告 §4.2 的警示（「需求侧与收益模型未校准前，不得把放宽容量视为已完成经济平衡」）在此处完全成立。

4.4 财务结算 — 间接影响

  • 时刻购入是一次性现金支出，不进资产负债表（全库搜不到把 slots 计入估值的地方）。
  • 所以容量变化对报表的影响是间接的：能买的槽变多 → 现金支出与摊销不变 → 但航线收入上升。
  • 不受影响：季度结算、董事会 KPI、税费、地面服务费的结构。
  • 建议补一条（本轮不做，只登记）：槽是「无账面价值的准固定资产」，容量上调会放大隐性资产而不体现在报表里。若将来做并购/估值，需把 slotValue × 持仓数 计入非账面资产。

5.2 五个关键读数

  1. 除数几乎不改变「最挤那一小时」的可用性。87% 下，08 时有空刻的机场从 1 家 → 15 家 → 25 家， 但「06–22 余量/占比」稳定在 11–12%。原因是占用率是比例制：容量放大，AI 占用同比例放大。 报告「旋钮①不是难度旋钮」的判断被数据证实。
  2. 最挤那一小时是算术性锁死的。判据见 §2.3。改除数解决不了，只有改占用率或改取整方式才行。
  3. D16 把「每刻只有 1 条」的机场从 5 家降到 1 家（SAN/XMN/SYX/ZUH/TNA → 只剩 SYX）。 这是除数真正的价值：分辨率。每刻 1 条时玩家在小机场只有 4 个可用窗口；2–3 条时窗口显著变宽。
  4. D16 让「全天有槽可申请」的机场从 2 家升到 20 家（87% 下），平均可用小时 7.0 → 10.7（满值 17）。 这是玩家真实感受到的改善，也是除数最值得买的那部分收益。
  5. 现状 87% 下，06–22 约 11% 的槽是空的，但分布不是「集中在午后」，而是「除权重最高的那个小时外， 其余每个刻各留 1 条」（枢纽 C=5 时：07/08/09/12/18/20 全满，其余每小时余 1–4 条）。

8 · 需要裁决的四项（本轮卡在这里）

A · 最挤那一小时要不要留出空槽？

数据事实：87% 占用下 81 场里只有 1 家在 08 时还有空槽，原因是 floor(C×r) = C−1 的取整必然， 改除数解决不了。

  1. A1（推荐先做）只把占用率做成可调，用 75% 跑一版。阈值从 C ≤ 7 降到 C ≤ 4，只有 25 家小场峰刻仍满。零算法改动。
  2. A2「每刻硬留 1 条」（MustLeaveOpen 从段级升到刻级，需限定 C ≥ 2，约 5 行）。任何时刻都留 1 条免费槽，代价是 C=1 的场 AI 归零。
  3. A3不改，把「峰刻必须买」当核心玩法，改好二级市场入口。

B · 离港 / 到港容量要不要严格守恒？

  1. B1（推荐）两池同数（现状结构），接受最高 2 架次/时/场的超发（全球 +1.8%），文档注明。零签名改动。
  2. B2严格守恒：按 round(2D/除数) 拆成 6/5 两端，给 QuarterCapacity 加 kind 参数，全库夹具连锁。

C · P1 上线时的默认除数？

  1. C1（推荐）默认 27（等价现状）：先验证「结构换了、数值没漂」，再单独做 27→16 的平衡实验。
  2. C2直接默认 16 一次到位（结构与平衡问题会同时出现，难定位）。

D · M1–M6 的定位？

  1. D1（推荐）只作文档与「缺数据时的兜底估算」，不进算法。
  2. D2做成代码枚举参与容量估算（会引入第二套容量来源，与「申报值为首选」冲突）。
