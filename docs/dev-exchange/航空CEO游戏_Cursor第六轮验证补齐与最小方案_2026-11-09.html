02 / ARR FIXTURE

ARR 专属夹具：跨班次配对与双池合法性

配对到港时刻的池归属规则（源码口径）

// RoutePermitLogic.PoolClocksAt 第 783–805 行
bool wantArr = IsArrivalKind(kind);
if (KindOf(s) == Arrival) {                       // 只到港持仓：slotTime 即落地钟点
    if (!wantArr) continue;
    if (BandOfClock(s.slotTime) == b) list.Add(s.slotTime);
    continue;
}
string c = wantArr ? ArrClockOfHolding(s) : s.slotTime;   // 配对持仓：ARR 用 arrTime
if (BandOfClock(c) == b) list.Add(c);             // ★ 按「该时刻所在段」过滤 → 配对可跨段分发

因此一条配对持仓会分别落进「离港时刻所在段的 DEP 池」和「到港时刻所在段的 ARR 池」。若两时刻跨段，这一对就横跨两个池——这正是评审要求覆盖的情形。

四种轮挡（73 / 333 / 733 / 240 分）× 两个池 × 两个布局，丢弃全为 0、break 全为 0、三层计数全部守恒。故上一版「B 丢 343 条」的说法撤回。脚本：place-consistency.mjs。

但 ARR 的「原刻位」不守恒——这与丢弃是两件事：到港时刻 = 离港 + 轮挡，通常不在 15 分钟网格上（73 / 333 / 240 分都不是 15 的倍数），NearestGridIndex 必然吸附。所以 ARR 池「原刻不变」比例是 0%（轮挡=240 时 96.8%），显示位移 ≤ 15 分属正常折算，不是缺陷。
03 / SEAM & PRESSURE

接缝：B 不增加压力，只是放大后果

评审要求分清「显示排序、邻刻选择、背景铺排」，并要求不得为修正显示而改写原持仓时刻。以下为分离后的量化。

① ARR 逐刻超容压力（A 与 B 都存在，与接缝无关）

轮挡A 超容刻 / 全部B 超容刻 / 全部单刻最大溢出B − A
短程 73 分60 / 9,888（0.61%）80 / 9,888（0.81%）1–2 条+20
中程 333 分94 / 9,888（0.95%）94 / 9,888（0.95%）1 条0
长程 733 分196 / 9,888（1.98%）197 / 9,888（1.99%）1–2 条+1
跨段 240 分100 / 9,888（1.01%）100 / 9,888（1.01%）1 条0

关键判读：逐刻超容是既存现象，B 几乎不改变其规模（+0 到 +20 刻，占 0.2%）。它来自「到港时刻按轮挡偏移后向某一刻聚集」，与班次如何划分无关。

② 接缝放大后果：同样溢出，位移差 39 倍

布局同一持仓在 05:45 溢出后的落位位移
A（早班连续）06:00（下标 24 就是 06:00）+15 分
B（夜班有接缝）20:00（下标 24 是 20:00）+585 分

ARR 侧同理：在轮挡 240 分场景下，最大位移 A 为 315 分、B 为 555 分；中程 333 分时 A 为 327 分、B 为 543 分。

符合评审三项要求的分层结论：① 显示排序——B 夜班数组按下标排列会把 00:00–05:45 排在 20:00 之前，属显示层缺陷；② 邻刻选择——Place 用下标距离而非时刻距离，是接缝放大的直接原因；③ 原持仓时刻——SlotHolding.slotTime 不被任何路径改写（OursLayout 只往 perQ 里放名字，不回写存档）。故修复方案必须只改显示与选择策略，不动 slotTime，与本轮建议一致。

③ 修复方案（不改容量、不改存档、不改持仓时刻）

项最小改动风险
夜班网格顺序BandGrid(3) 返回时按「日序」重排：20:00…23:45 → 00:00…05:45低。BuildBandGridCache 是纯函数，仅顺序变化；需与 MatrixGrid 列头同步
Place 候选顺序把「下标 ±d」改为「时刻距离 ±15d」，用 ClockDiff 排序候选中。Place 被 OursLayout 与 PlaceCount 共用，需回归全部时刻表用例
跨午夜区间判据BandHourStart/End 增加 wraps 语义；MatrixGrid 改环状判据低，纯显示

脚本：arr-tick-pressure.mjs、seam-case.mjs、place-consistency.mjs。

04 / AIRPORT IDENTITY

机场身份迁移：最小实施方案

受影响面（代码事实）

层当前键改动方式
AirportInfo.codeIATA 3 字母，兼作主键新增 airportId（稳定串），code 降为「可选外码」；新增 icao（可空）
AirportRunways / AirportGeoCatalog / CityEconomyCatalogIATA三表保持 IATA 键不变，由 AirportCatalog 在加载时按 airportId 建索引，不改表结构
SlotHolding.airportIATA不迁移。读档时经 ResolveAirport 把 IATA → airportId；写出时仍写 IATA（若已存在则写 airportId，见下）
RouteData.origin/destinationIATA同上，读时解析，不批量重写
FindByCode（26 处调用）线性扫 All增加 Dictionary<string, int> 索引（IATA / ICAO / airportId 三张），FindByCode 保留签名转调字典

分三步，每步都可独立回退

步内容不做会怎样回退
M1只加索引与 airportId 字段，不改任何读写路径。行为完全不变。5,000 场时 FindByCode 退化为 O(N²)删掉字典与字段，零影响
M2读档时经 ResolveAirport 解析（IATA → airportId，失败则回退 IATA 直查）。写出仍用原键。只有 ICAO 的机场无法录入关掉解析开关，走原直查
M3支持「仅 ICAO」机场注册；IATA 变更加别名映射（旧 IATA → 新 airportId），不丢记录。玩家无法启用附近小机场别名表为空即退化为 M2
硬约束（评审已认可）：不得静默丢记录。任何解析失败必须显式告警并保留原键，不得把无法解析的持仓过滤掉。别名映射表本身要能回滚——它是纯数据，不进存档结构。

单一容量服务：最小接口与兼容层

接口（只读，替换现有烘焙值）

public static class CapacityService
{
    // 唯一权威查询：单机场 / 单刻（0–1439）/ 单方向

}

与现有 int[4] 的关系

层角色迁移期做法
CapacityService唯一真相源先只实现「平铺模式」：内部按 runwayEff × 1 算，输出与今日逐值相同
AirportInfo.slotCapacity派生缓存改为 CapacityService.PoolCapacity 的懒填充缓存，Invalidate 可重建
AirportCatalog.SlotCapacity(code, band, kind)兼容读取签名不变，内部转调 service；顺带修 kind 被忽略的缺陷
必须避免的坑（评审已明确警告）：不能让「可变容量数组」与「覆盖表」并存为两个可互相矛盾的权威。判据很简单——全仓只有一处计算容量，其余都是它的缓存或转调。若出现第二处独立算容量，即视为回归失败。

验证方式（不需要 Unity 也能做一半）

  • 等价性：平铺模式下，CapacityService.PoolCapacity 对 104 座机场 × 4 班次 × 2 方向的输出，必须与今日 AirportInfo.slotCapacity 逐值相等（0 差异才算迁移成功）。
  • 缓存失效：Invalidate 后重建的值与首次计算一致。
  • 单一真相：静态检查「除 CapacityService 外，无第二处 runwayEff × 1 计算」。
