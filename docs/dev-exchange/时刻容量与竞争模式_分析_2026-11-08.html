时刻容量、竞争模式与「平台」——设想分析（2026-11-08）

本文性质：纯分析，未改任何代码。用于裁决「引入 AI 竞对 / 线上多玩家全面竞争」与「时刻容量贴近现实」这两件事的先后与边界。

触发问询（用户原话）：「如果将 AI 竞对航司或者线上多玩家引入各个模块的全面竞争模式，那么时刻容量越贴近真实，玩家的平台就越大吧？」

前一轮问询：「目前时刻槽容量的数量没有贴近现实，严控容量是为了让玩家有压力，对吧？」

0. 一句话结论

方向对，但「平台越大」不会自动成立。

  • 在决策空间的意义上成立：容量贴近现实会让「同一刻站得下多家航司」，竞争才有名次，grandfathering / 新进入者配额 / use-it-or-lose-it 才有意义。
  • 在玩家可及槽位的意义上不成立，甚至可能变小：稀缺度降 3.5 倍，AI 也会扩张去吃新增容量，玩家相对份额可能不变。
  • 而且它有三个前提，目前两个是缺的（需求侧、AI 持仓账）。顺序做反会白做，且很难回头（槽价、二级市场行情全部要重标）。

2. 真正的机制：不是「槽变多」，而是「同一刻能站下更多家」

这是这个设想里最关键、但最容易被说漏的一层。

压缩比 K 只改一件事：每个格子里能放几条。格子本身不变 —— 81 场 × 96 刻 × 2 池 = 15,552 格，这个数永远不变。K 从 1/3.5 放到 1/1，变的是每格能站几家：

K=1/3.5（现在）K=1/2K=1/1（现实量）
全游戏单池日容量11,944≈ 20,902≈ 41,802
全游戏最大单刻6 条（仅 3 处）10 条21 条
峰刻 ≥3 条的机场45 / 8181 / 8181 / 81
峰刻 ≥5 条的机场3 / 8145 / 8181 / 81
PEK 07:002≈ 4≈ 7
LHR 07:003≈ 5≈ 8
ATL 峰刻61021

（K=1/2 与 1/1 两列为按小时容量等比外推，非代码实测；当前 K 列为报表实测。）

「2 → 7」的含义不是「你更容易拿到」，而是「这一刻可以同时有五家航司在飞，而你要争的是那第五个位置」。

  • 容量 2 时，竞争是二元的：你或他。
  • 容量 7 时，竞争才有名次：谁拿了 07:00 第一个、谁是第四个、谁只能退到 07:15。

这是真实的枢纽竞争形态，也是 WASG 里四条规则唯一有意义的前提：

规则代码落点现在为什么空转
grandfathering 历史优先权SlotUsageLogic §8.7每刻 1–2 条，没有「历史」可保
use-it-or-lose-it 80%SlotUsageLogic §8.6同上，失格释放只在自己跟自己比
新进入者 50% 配额未做（设计文档 §13.8 明确不做）没有「进入者」概念
拍卖 / 二级市场定价SlotMarketLogic（确定性定价）卖方由哈希挑，无对手方出价

准确的说法是：贴近真实不是一个「让玩家更舒服」的改动，而是让竞争系统从「无意义」变成「有意义」的开关。

3. 三个必须同时成立的前提

前提 ①：需求侧也得贴近真实 —— 目前不成立（这是最容易被忽略的一环）

引力模型（Logic/RouteGravityModel.cs:3-14）：

G = (gdpA × gdpB) / (km/1000)^1.2
P = (popA × popB)^0.3
H = (liveA × liveB / 10000) × (odA × odB / 10000)
周客流 = G × P × H × 3.5        （BalanceK = 3.5）

代入实际数据（Data/CityEconomyCatalog.cs）：

航线GPH周客流每班（7 班/周）
PEK–SHA390,0616.610.6866,189,531884,219
LHR–JFK149,9605.430.8492,420,091345,727
HRB–URC1,1193.050.1061,259180

而 MarketPaxPerFlight 是「周客流 ÷ 周班次」，再被座位数封顶（Logic/CapacityEconomics.cs:68-84）。代入结果：

  • PEK–SHA：每班市场容量 88 万人次，飞机只有 180 座 —— 需求封顶永远不起作用。
  • HRB–URC：每班正好 180 人 —— 恰好卡在 180 座机上。
  • LHR–JFK：每班 34.5 万 —— 同样完全不构成约束。

也就是说：干线需求不构成约束，支线需求恰好卡在临界点。 现实里 PEK–SHA 周客流约 20 万（本作高约 30 倍），而真正的瓶颈从来是时刻与运力，不是客流。

后果：容量放到 1/1 之后，枢纽的每一个新增槽都等于纯利润，因为需求永远吃不完。游戏会变成「谁拿到枢纽高峰槽谁赢」，而不是「谁经营得好谁赢」。

容量贴近真实必须与需求贴近真实同时做，否则扩出来的空间不是「平台」，是印钞机。

前提 ②：AI 必须有会演进、可被剥夺的持仓 —— 目前明确拒绝过

行业航司 39 家（Data/IndustryAirlines.cs:55-96，国航 / 东航 / 南航 / 国泰 / 汉莎 / 法航 / 荷航 / 英航 / 阿联酋 / 卡塔尔 / 新航 / 全日空 / 日航 / 大韩 / 达美 / 美联航 / 美航 / 土航 / 澳航 / 海航 / 厦航 / 深航 / 川航 / 长荣 / 泰航 / 马航 / 北欧 / 芬兰 / 西班牙 / 瑞士 / 俄航 / 印度 / 埃塞俄比亚 / 南非 / 华夏 / 天津 / 首都 / 山东 / 乌鲁木齐）。

它们占着槽，但从不行动。代码里写下了理由（Logic/IndustryAirlineLogic.cs:15-22）：

为什么他航的持仓是推导出来的而不是存盘状态：

  • 存档里只有我司一家。给 38 家他航建持仓表，等于凭空多出一份要随季度演进、要处理旧档迁移、还要防止与「时刻池容量」打架的账 —— 收益只是让表格好看一点。
  • 推导可以做到确定性：同一存档、同一季度、同一机场，看到的是同一张表。

这个判断在单机下完全正确，在竞争模式下完全错误。 理由是同一个：那本「要随季度演进的账」，在单机里只是让表格好看，在竞争里就是全部玩法 —— 持仓不再是展示数据，而是可以被抢、被买、被 lost 的资产。

而且现在有两套互不相通的他航名单，这是竞争化最硬的障碍：

名单数量占槽会行动典型名
IndustryAirlines.All39是否国航、东航、汉莎、美联航
AIManager 运行时生成5否是云翼、青鸾、银燕、北辰、新加坡航空

（Systems/AIManager.cs:44-58）

会占槽的不会动，会动的不会占槽。 竞争化第一步必须把这两张表合成一张 —— 否则「AI 抢槽」这件事在数据结构上无处安放。

顺带一处已存在的数据重复：新加坡航空 同时出现在两张表里（Data/IndustryAirlines.cs 的静态目录 + AIManager 的 AI-SQ），是同一个实体被复制成两份。

前提 ③：槽必须可交易、可剥夺、有价格 —— 部分成立

SlotMarketLogic 已做二级市场，但与池容量解耦（成交不查池容量，因为航司间转让不增加机场总起降），机制设计是对的。缺的是对手方：

  • 卖方由 IndustryAirlineLogic.SellerAt(gs, airport, clock, year, quarter) 挑，但该函数的 year / quarter 两个形参在实现里完全未被使用 —— 定价不随赛季变化。
  • 没有「谁缺槽谁出价」，只有「这一格谁在卖」。
  • 被收回的槽（80% 使用率失格）直接退回池，没有进入新一轮分配的市场过程。

WASG 那套规则已经实现了一半（80% / HBD / 失格释放），缺的正是对手方。

4. AI 与多玩家：两种完全不同的工程问题

门槛差一个数量级，不能混为一谈。

AI 竞对是内容问题：合并名单、给 AI 建持仓账、写一套「何时扩张 / 退让 / 卖槽」的策略、平衡数值。改动大但不涉及架构。

多玩家是并发问题：

项现在多玩家需要
时间粒度90 天/季（GameState.DaysPerQuarter = 90），季度结算需要权威分配器；一季内多人的抢槽必须原子
槽获取StrategyManager.AcquireSlotsAt 本地检查后写入，无锁无事务两个客户端都能通过检查、都写入 → 同一刻超卖
他航占用hash(机场, 时段) 推导，无状态这一条反而是资产 —— 所有客户端算出同一结果，零同步
状态单份 GameState 本地存档服务端权威 + 增量同步

值得单独说第三行：哈希推导在单机里是「无奈的近似」，在多玩家里却是「免费的确定性」。如果所有玩家都对同一套确定性的他航持仓竞争，服务器只需广播玩家的操作，不必同步 39 家的全量状态。这是现有设计的一个隐藏优势，竞争化时不要顺手把它拆掉。

但第一、二行是真障碍：「检查余量 → 写入持仓」现在是一个非原子的两步（QueueApplySlots 递交时判一次，AcquireSlotsAt 交割时再判一次，中间隔 7–18 天）。这一条不修，多玩家第二天就会超卖。

5. 一个反直觉的点：真实容量会削弱竞争，不是加强

这是动工前最需要想清楚的地方。

容量放到 1/1，稀缺度立刻降 3.5 倍。竞争要补回这个压力，但竞争压力是弹性的：AI 也会扩张去吃新增的容量。如果 AI 策略是「尽量占满」，玩家的相对份额可以完全不变 —— 从「7 个空刻里挑」变成「20 个空刻里挑，但另外 7 家也在挑」。

那时候真正变好的不是「能拿到多少」，而是三件别的事：

变化现在竞争化之后
可读性你拿不到 07:00，因为撞上一个哈希函数因为国航持有它，且你有价格可以谈
方差 / 重玩价值hash(机场, 时段, "occ")，每局开局完全一样路径依赖，每局不同
策略深度只有「申请 / 买 / 改时」三个动作抢、换、卖、弃、等新进入者配额

第二项可能比「平台变大」更有价值：现在这套哈希是全局确定性的，意味着第 100 局和第 1 局的时刻表完全相同。

所以判断是：「平台越大」在「决策空间」的意义上成立，在「玩家可及槽位」的意义上不成立，甚至可能变小。 若要的是后者，贴近真实是错的方向；若要的是前者，它是对的，且必须配竞争。

6. 建议的推进顺序

依赖关系是单向的，反过来做会白做：

步做什么为什么必须在这一步
1合并他航名单 + 给 AI 建持仓账没有对手，容量放多少都是空的
2让 AI 的占用率内生 —— 从 0.85 + 0.05×hash 改成「按盈利预期决定持多少」87% 这个魔法数字才会自己找到位置
3放容量 K（1/3.5 → 1/2 → 1/1），每档观察玩家可及槽位这是唯一「可回退」的一步，应放在有对手之后
4需求侧同步校准否则第 3 步变成印钞（见前提①）
5多玩家的原子性单独作为工程项与 1–4 步无耦合，混在一起会拖死前四步

若顺序反过来（先放容量）：会得到一个「槽很多、谁都能拿、但没有人跟你抢」的世界 —— 压力彻底消失，而且很难回头，因为槽价与二级市场行情全部要重标。
