## 二、三处修正的具体内容

### 2.1 K19：修场景构造，不改规则

`Unity Project/Assets/Scripts/Editor/SlotCashHintRegression.cs`

旧写法的病灶：把「请求 TNA 12:00」当成必然成交的时刻，并用写死的 300 万报价反推现金。
容量改「跑道数平铺」后 12:00 常被占满 → 运营部按既有规则改刻 → 报价掉到 177 万 →
跑道变成 3.68 月 → 风险行本就不该出现。**旧用例考的是过期前提，不是规则**。

按裁决改成「先问真话，再按真话构造」：

1. `FirstProposableClock` 用真实查询（`QuarterCapacityAt` / `SlotsAvailableAt` / `SlotPoolFull`，
   与 `QueueSlotDecision` 三条前置判据同源）挑一个**真的能递交**的刻；在可提交的刻里取
   `StrategyEconomics.HourDemandCoef` 最高者 —— 让场景仍是「黄金时刻报价」，而不是退到凌晨冷门刻。
2. 探针提案（`m_k19_probe`）问出**最终采用的时刻**（含改刻情形）与**该刻报价**（`SlotValueWanAt`）。
3. 正例：`现金 = 报价 + 2 × EffectiveMonthlyBurn` → 付得起、付完 2.00 月；
   反例：`现金 = 报价 + 10 × EffectiveMonthlyBurn` → 付完 10.00 月。
4. **先断言前提**（`q1 && m1 != null && cash >= quote && |跑道 − 2| < 0.01 && 跑道 < 3`），
   再断言正文与渲染文本的风险行有无。前提不成立直接判失败，不再让「偶然落在边界附近」蒙过。
5. 风险断言、3 个月阈值、「跑道充足不得出现风险行」的反面钉法、渲染链路
   （`InboxLetter.FrameIfNeeded` → `TermNavMap.Decorate`）全部保留。

实测（当前实现与重建对照**同值**）：

```
K19 时刻槽提案现金跑道 → 紧口径=True 紧文案=True 足额=True 差额=True 前提成立=True
                          信件正文=True 风险行=True 风险行渲染后仍可见=True 风险行不滥发=True　✓
　真实信件：请求=10:15 最终时刻=10:15 报价=177.0 万 正例现金=258.0（跑道 2.00 月） 反例现金=582.2（跑道 10.00 月）
```

### 2.2 申请序列：N/A 即失败 + 方向各管各的

`Unity Project/Assets/Scripts/Editor/SlotSequenceRegression.cs`

**(a) N/A 不能满足必测场景**（裁决 3.1）

- 九项场景 ①–⑨ 逐项登记覆盖标记 `Covered`；任一场景因前提缺失走 `Na()` 时，**记 FAIL 而不是记 N/A**。
- 收尾追加九条「场景 X 已实际执行」，`all = fail == 0 && covered == 9`。
- 断言总数**没有写死**（现在是 39 条，随场景增减浮动），判据只认「零失败 + 九项全覆盖」。

**(b) 容量同值 ≠ 余量同值**（裁决 3.2）

旧第 ⑨ 项断言 `SlotsAvailableAt(DEP) == SlotsAvailableAt(ARR)`。实测两方向本就不同 ——
同一次运行里 **离港他航 52 / 余 8，到港他航 53 / 余 7**，旧断言只是「两边都满在 09:00」的偶然相等。

现在改成：

| 断言 | 内容 |
|:--|:--|
| 保留 | C0 两方向**池容量**同值（60 = 60） |
| 保留 | 逐刻容量不分方向（`CapacityService.Quarter(…,"DEP") == …,"ARR"`） |
| 新增 | 离港「段余 = Σ 逐刻 max(0, 容量 − 我司 − 他航)」 |
| 新增 | 到港同一条口径的独立核对 |
| 新增 | 09:00 这一刻意**两个方向各自**与「容量 − 各自我司 − 各自他航」对齐 |
| 记录 | 两方向的 `poolCap / ourUse / industry / available / sumOpenByClock` 全部写进 transcript 供前后比对 |
| **删除** | 「两方向余量必须相等」这条错误断言 |

另按裁决「必测场景不得因条件分支少执行」，⑤⑥ 的挑刻从「固定中班段」改为**按段扫描**：
到港取第一个存在可申请到港刻的段；配对场景取第一个「两端都有可申请刻」的段 ——
避免因某段恰好占满而静默跳过。

transcript 尾行（两版本相同）：

```
check.summary=pass=39 fail=0 covered=9/9
check.all=true
```

**(c) 反向控制：新判定确实会红**（只改测试文件、只改一次性快照副本，生产代码与仓库源码未动）

| 控制 | 改动 | 结果 |
|:--|:--|:--|
| `Batch1NegCtrlCover` | 注释掉 `Covered_("⑦")` | **Failed**：`场景 ⑦ 已实际执行` 记 FAIL，`pass=38 fail=1 covered=8/9` |
| `Batch1NegCtrlNa` | 把 `FirstFullClock(...)` 强制成 `null` | **Failed**：`必测场景无法执行（N/A）—— ②满刻驳回`，`pass=35 fail=2 covered=8/9` |

对照旧版「只统计 fail、N/A 静默算过」，这正是裁决 3.1 要堵的口子。XML 与说明在
`…/batch1-r2/negctrl/`；控制结束后副本文件已还原，哈希回到 `d5b70475…`（与
