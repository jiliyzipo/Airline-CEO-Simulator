0. 执行摘要与最终裁决

最重要的修正：103 座协调机场是 Cursor 当前核查到的项目状态，不是游戏上限。 游戏机场数量不得设置固定值；未来可以增加更多真实机场，既包括由开发团队导入的机场，也应逐步支持玩家按所在地、城市、半径搜索并启用原本未在初始游戏清单中的附近机场。

正式要求： 机场名录、协调资格、容量、地理位置、城市经济、航线市场和存档应能随数据扩展；新增机场走统一接入流程，不需要为每座机场编写特例。对“无限扩展”的定义是不设人为的机场数量上限，不是允许无限占用机器内存或伪造现实机场。

1. 机场数量：请纠正“103座是否最多”的误解

1.1 三个数字的不同含义

数字 含义 能否作为系统上限
81 原机场容量研究表中的机场样本 不能
104 Cursor 在最新项目源码中报告的已录入机场数 不能
103 上述机场中被当前代码标记为协调机场的数量 不能

Cursor 还报告：目前有 15 座协调机场缺少显式跑道数据，使用按等级回退推算。以上代码与数量结论来自 Cursor 的报告，尚须以当前项目工作分支重新核实；不能把一次审计快照当成长期业务规则。

1.2 面向玩家的新增附近机场需求

游戏应逐步支持这样的使用场景：玩家想从自己居住地附近的小机场起步，但机场没有出现在初始清单中；玩家通过城市、机场名称、IATA/ICAO 代码或地图范围查找真实存在的机场，选择“加入本局可经营机场”；系统加载该机场的可用资料，验证是否可用于航线运营与时刻处理。

特别区分： “添加现实中存在的机场”与“玩家凭空创造机场/建设新机场”是两种不同玩法。本轮仅要求前者在架构上可行；后者涉及机场建设，当前不开发。

建议保留两层概念：

  • 机场主数据目录（Airport Master Catalog）： 收录已知真实机场，可持续扩展；采用稳定内部 ID，IATA 和 ICAO 均为可选外部标识，不能假设每座小机场都有 IATA 代码。
  • 本局已启用机场（Active Airports）： 当前存档中需要经营、计算、展示的机场集合；玩家搜索并启用的机场加入该集合。目录更新不得自动改写既有存档持仓。

新增机场不得自动被视为协调机场。对不同规则的机场分别实现：有正式时刻协调规则的机场进入容量与申请机制；非协调机场依据其运行许可、运行时段和设施约束处理，不能错误显示为“协调时刻已满”；规则未确认的机场明确标注“待核实”，不得静默猜测。

1.3 数据模型及接入要求

每个机场至少应有：稳定内部 airportId；iataCode?、icaoCode?；名称、城市、国家、经纬度、时区；机场类型（枢纽／干线／支线等）；协调级别与适用时段；跑道和运行限制；容量来源、日期、估算标志及可信度；数据版本。扩展属性不必一次开发完，但需要具备可诊断的缺失处理。

应提供统一、幂等的“录入/更新—验证—启用—计算—搜索/地图—航线/时刻—报表—存档”流程。缺少任意关键字段要给出错误清单或限制功能，而不是默默回退到“按等级猜3条跑道”。

不要为了赶进度把四张现有表立刻强行合并。 短期可以建立统一聚合视图、接入层和跨表完整性检查；等扩展机场进入实施阶段，再评估是否迁移为单一记录体系。

1.4 性能与规模原则

“不设上限”指业务逻辑没有固定数量限制。实现上应通过按地区/视图加载、缓存、分页搜索、增量生成、按需模拟已启用机场及增量存档避免内存和结算时间随全球所有机场无条件线性增长。建议为 103、300、1,000、5,000 个机场的合成数据建立性能基线，阈值由测试确认，而非直接以某个数字拒绝新增。

2. 对最新 Cursor 复核的接受与修正

2.1 已确认采纳

  1. C0 优于 ÷27 过渡： Cursor 的逐场复算指出，81场研究表与引擎跑道表口径略不同；在其引擎口径下，÷27 后总和仍为 248，但46座机场的逐场容量发生变化。因此绝不能以“总量相同”证明现状保持不变。兼容模式必须逐机场、逐时段、逐方向核对。
  2. 局部整数误差不能被全局平均掩盖： 报告将 D16 对称取整总偏差修正为 +2.32%（在其81场样本口径），单机场小时偏差可达到 ±4 架次。严格守恒方案必要。
  3. 凌晨归属不是文案错误： 00:00–05:45 的容量已产生，但仍被 BandOfDep 划入早班；不得仅把早班标题改成 00:00–09:45。
  4. 扩大审计对象： Cursor 报告称当前为 104座录入、103座协调，且其中15座协调机场没有明确跑道数据。P0首先确认完整清单与缺数据现状。

统计口径警告： 81场研究表、81场引擎复算子集、103场协调机场、104场录入机场并非同一个分母。包括 248、304、2.32%、15/81 等指标必须在输出时同时标注来源、覆盖范围和算法版本，不能并列当成同一世界总量。

将凌晨 00:00–05:45 归入前一日20:00开始的夜班。必须审计 BandOfDep、BandCapacity、ScheduleSlots、申请与交易、AI占用重铺、存档加载、日结算及报表。Cursor 认为 SlotHolding 只存 airport/slotTime/kind，所以可能不用改存档 schema；但这仍需通过跨日持仓与池容量回归证明，不能据此宣布“没有兼容风险”。

尤其要测试“周日23:45—周一00:00”、航季边界及机场当地日期切换时，夜班是否被错误分成两个不相干的经营池。在时区/夏令时尚未完善时，报告要明确现有游戏时间轴的局限，而非伪称已实现全部现实规则。

2.3 容量守恒 B2 与非高峰曲线

正式容量方案应先得出某机场某小时的游戏总起降架次预算，再把整数架次分配至四个15分钟格、分别分配到港与离港。按 D16 的50%世界容量示例：若申报88架次/时，小时预算44，四刻可以各给11，离港/到港为6/5交替，合计恰好44。

现阶段维持用户已确定的不额外创建高峰/谷底容量曲线的设计，但允许为保证整数守恒，在四个15分钟格之间进行最多一单位的均匀余数分摊。不能用“每方向同数四舍五入”制造小机场的显著虚增或虚减。建议优先实现新方向查询而保留旧查询兼容，迁移的函数范围以代码检查为准。

对未来没有统一小时申报值或小时限制不同的机场，应允许数据层提供对应时段/航季的真实限制；这项能力只预留，不意味着当前要开发完整空管调度模拟。

2.4 初始占用率 A1 与真实模拟口径

A1 指 D16×75% 是优先验证候选，不是已经验证的正式默认值。保留 87%及60% 做对照，且需使用生产代码当前的确定性哈希（报告称 0.85 + 0.05×Unit()、枢纽另加2%）对所有现有协调机场重跑，而不是只用固定87%替代。

需要单独拆解三种因素：基础容量是否有可信来源；占用率多大；FillWave 如何把已占用容量分布在每刻。不得把“中国机场08:00未解锁”全部归因于官方容量偏低，也不得强制给每刻留一个免费槽来制造虚假的现实开放程度。

未来引入AI经营后，旋钮②只决定开局背景航司持仓基线，不能持续用全局百分比强制调整、撤销真实航司的持仓。

2.5 三旋钮最终定位

调节项 正式名称 控制什么 不应控制什么
① 世界容量比例 真实申报能力映射到游戏的规模；D16与D12为测试参数 不直接制造需求或经营利润
② 初始市场占用率 开局他航持仓与资源稀缺程度；87/75/60隔离测试 不在每季度强制重置AI持仓
③ 机场容量演进机制 所有当前和未来机场因设施、政策、航季变化发生的容量调整 不限“5座富余机场”，也不是简单统一加成百分比

第三旋钮在当前开发阶段只需预留 capacityRevision、有效日期、变化原因/来源与重新评估/存档兼容机制；机场建设工期、成本、审批、动态AI竞争等完整玩法暂缓。

4. Cursor 必须提交的验收标准

  1. 无固定数量限制： 检索并证明运行时代码、配置、API、UI和导出不存在以 81/103/104 为上限的固定大小数组、遍历条件或默认拒绝规则；测试夹具中的当前样本量允许固定但必须标注版本。
  2. 现状可重复： C0兼容模式在当前协调机场（据报告为103座）逐机场、逐时段、逐方向结果与 golden 快照一致；包括 DayCapacity、四池容量、背景航司持仓及关键申请判据。若发现快照与源码不符，先解释再修改。
  3. 模拟无过配： B2中任一小时的离港+到港总数等于已整数化的小时预算，且不得超出运行限制；允许各15分钟格为保证守恒交替±1，不人为增加峰刻容量曲线。
  4. 凌晨归属正确： 96格全部覆盖一次且仅一次；夜班 20:00–次日06:00 含前一夜跨日格；原有持仓不被静默删除、重算时不能重复申请或交易。
  5. 数据缺失可诊断： 未提供跑道/容量/地理/协调信息时必须有明确告警、可信度标记与受限功能策略；不得静默用等级推算伪装真实参数。
  6. 玩家新增机场试验： 在隔离测试目录中加入至少一座现状之外的协调机场和一座非协调机场，包括无IATA仅ICAO的测试实例；无需修改容量算法即可搜索、展示、确定协调规则、保存并再次读取，既有机场数据保持不变。测试机场可为纯夹具，不能冒充真实机场对外展示。
  7. 规模测试： 使用300、1,000、5,000座合成机场验证搜索、机场地图、容量查询、存档和季度结算的增长曲线；报告性能瓶颈及建议优化，不设置新的硬性数量限制。
  8. 经济联动： 对比可开航线数、航班频次、客座率、季度净利润、现金流、二级市场价格与成交量，不得以“容量增大=利润更多”作为成功标准。
  9. 回退和权限： 提交改动文件清单、快照对比、测试结果和回退方案；在用户批准前不得更改正式世界容量、初始占用率或已持有时刻。

5. 建议直接发送给 Cursor 的执行指令

请依据本报告更新《时刻容量与三旋钮》技术实施方案。

第一，确认 103 只是当前已识别的协调机场数，而不是任何系统限制。游戏机场数量不得设置固定上限；未来需要支持玩家按所在地、城市、位置半径查找并启用附近的真实机场，协调机场和非协调机场均可接入。先审查机场目录、地理、容量、市场和存档的扩展路径，不开发完整新增机场界面。

第二，接受 C0、B2、D1 及凌晨归夜班 B 的原则；将四个时段定为早16／中20／晚20／夜40，不得将早班直接改为00:00开始。D16×75%仅作为重点测试候选，保留D12、87%和60%的对照。

第三，先执行P0只读审计：复核104录入／103协调与81研究表的范围差异，查清15座缺少跑道数据机场，记录现有容量与背景占用 golden 基线，按真实哈希算法重算，评估跨午夜归属、容量守恒和新增机场数据接入。

第四，提供清晰的P0审计结果、代码影响面、测试脚本、接口草案、风险、P1候选实现和回退方案。未获单独批准，不修改生产容量、不改存档、不更改实际占用率、不开发完整AI竞争或机场扩建玩法。
